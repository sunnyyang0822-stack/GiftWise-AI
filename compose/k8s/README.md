## 2. 验证到了什么程度（说清楚边界）

做过：
- **YAML 语法**可以被解析（`yaml.safe_load` 通过，4 个文档对象）；
- 引用的**环境变量名**与 `deploy/server.py` 实际读取的一致
  （`GIFTWISE_BIND` / `GIFTWISE_PORT` / `GIFTWISE_READ_TIMEOUT`，见 `deploy/server.py:40,151,152`）；
- 引用的**端点** `/healthz` 真实存在（`deploy/server.py:105`，且已实测返回 200）。

**没有**做过：
- 没有对任何 K8S API 版本做过兼容性校验（例如 `autoscaling/v2` 在目标集群是否可用）；
- 没有验证过 `readOnlyRootFilesystem: true` 是否会让应用启动失败。
  ⚠️ 这里有**已知风险**：`deploy/server.py` 会向 stdout 写日志，
  而 Python 在 `readOnlyRootFilesystem` 下通常仍可写 stdout，但 `PYTHONDONTWRITEBYTECODE=1`
  已在 `Dockerfile:6` 设置，**这降低了风险但没有在本集群验证过**；
- 没有验证过 `runAsUser: 10001` 与挂载卷的属主关系；
- 没有验证过探针在真实负载下会不会误杀（尤其是 `/healthz` 在全绿的半开缺陷下**不会**报警）；
- 没有做过分层镜像的拉取时间测试；
- 没有测过 HPA 是否真的会触发（需要 metrics-server，本机没有）。

## 3. 为什么现在上 K8S 是过度设计

### 3.1 单容器 + 无多副本需求

交付物是**一个**容器：`deploy/Dockerfile`，`CMD ["python","-m","deploy.server"]`。
它的职责是"确定性规则校验"，不保存请求、不调用模型、不访问外部网络
（`deploy/server.py:1-4`）。本机实测：

- 启动到 `/healthz` 200 只需 **0.750~0.939 s**；
- 常驻内存 **14.45~17.08 MiB**；
- 冷构建 **1.720 s**，镜像 177,918,474 B。

这个体量用 K8S 的最小可用形态（控制面 + 至少一个工作节点）来托管，
**编排系统本身的资源开销会显著大于被编排的应用**。用一台 UHost 跑一个容器就够的事，
引入 K8S 是纯负债。

### 3.2 无状态是"默认入口"的性质，但整个服务并没有需要编排的特性

实测确认默认入口**没有进程内可变状态**：

- 代码层面：`validator/rules.py` 模块级只有 `TAGS = frozenset(...)`、
  `AMOUNT = re.compile(...)`、`UNAVAILABLE = object()` 三个常量，
  没有被写入的全局容器、没有缓存、没有计数器、不读时间不读随机数；
  `validate()` 自述为"纯函数公开接口"（`validator/rules.py:254`）。
- 行为层面：交错误发给两个副本 30 组，**0 组**响应字节不一致；
  同一载荷重复 20 次，得到**1 个**唯一响应哈希
  （`compose/evidence/stateless-byteidentity.txt`）。

**但这恰恰说明不需要 K8S**：无状态是"容易水平扩展"的前提，
而"容易扩展"不等于"需要交一个编排系统来扩展"。当前没有需要扩展的负载。

### 3.3 没有真实的流量与 SLO 依据

本机实测（Docker Desktop / WSL2 单机，**不是**云端数字）：

- 直连单副本峰值吞吐约 **496 req/s**（并发 4）；
- 并发 ≥16 后吞吐**反而下降**到约 300 req/s，p95 飙到约 **1030 ms**；
- 2 副本相对 1 副本的吞吐增益在各并发档位都约 **1x**（0.89x~1.23x），
  即**加副本在这个环境里没有可观测收益**。

在没有真实流量、没有 SLO、且扩容收益测不出来的情况下引入 HPA，
HPA 阈值只能靠猜。**用猜出来的阈值做自动扩缩，比不扩缩更危险。**

### 3.4 可观测链路还不足以支撑 K8S 运维

- `/metrics` **不是默认入口**（默认入口 `/metrics` 实测 **404**）；
- 可观测入口的 `/metrics` **完全未鉴权**：匿名 GET **200**、
  伪造 `Authorization: Basic …` 也 **200**，且泄露 `rules_source_sha256` 与 `python_version`；
- 也就是说：**能支撑 K8S 决策的指标，目前不在默认交付路径上，且没有访问控制。**

在这样的可观测基础上上 K8S，等于"用一个看不见的仪表盘去开一辆自动驾驶的车"。

### 3.5 进程不支持优雅停机，滚动更新会丢请求

`deploy/server.py` **没有** SIGTERM 处理（无 `import signal`），
且它用的是标准库 `ThreadingHTTPServer`，其 `daemon_threads = True`。
后果：容器收到 SIGTERM 后被直接终止，**正在处理的请求被丢弃**，
连 408/500 都来不及返回。补丁见 `compose/patches/graceful-shutdown.patch`
（**只生成、未应用**，且其 base 是交付镜像内的 `server.py`，sha256 `130cb065db68…`）。

在没有优雅停机的前提下上 K8S，`maxUnavailable: 0` 只能保证"不主动下线 Pod"，
**不能**保证"在途请求不丢"。这是先决条件缺失，不是编排参数能解决的。

## 4. 什么条件下才值得上 K8S

按"从下到上"的顺序，**每一条都是上一条的前置条件**：

1. **单机已经撑不住，且确认瓶颈在应用层。**
   判据：单副本 CPU 持续 >70% 且吞吐随副本数**近线性增长**（直连实测增益 ≈ 2x）。
   ⚠️ 本仓库现状**不满足**：实测增益 ≈ 1x，说明瓶颈不在副本。
2. **进程支持优雅停机。**
   判据：`SIGTERM` 后在 `terminationGracePeriodSeconds` 内，
   在途请求全部收到正常响应，日志出现"all in-flight requests drained"。
   前置：合入 `compose/patches/graceful-shutdown.patch` 或等价实现。
3. **有可信的、带访问控制的指标链路。**
   判据：默认入口就能暴露 `/metrics`，且需要鉴权；指标能区分
   "业务负载"与"框架开销"（当前实测 90% CPU 是框架开销，
   所以纯粹看 CPU 利用率的 HPA 会误判）。
4. **有多副本的真实需求，而不是"看起来更专业"。**
   判据：能给出"单副本在 X 并发下 p95 超过 SLO 的 Y ms"这样的具体观测。
5. **有发布与回滚流程。**
   判据：镜像**已推送到仓库**且可被集群拉取（当前**从未推送**），
   有版本标签策略、有回滚演练记录。

**在这些条件满足之前**，正确的做法是：一台 UHost + 一个容器 + 一个反向代理
（或直接 `-p` 发布端口 + 安全组限制来源），成本更低、可观测更简单。
