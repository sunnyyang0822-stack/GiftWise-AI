§4 「按关系分流的产品逻辑」到底哪一段会因新值换挡
==============================================================================
  boss 与 other 的 request_json 差异字段（变体版）：
    recipient_relation: '其他'  →  '职场上司'
    recipient_relation_id: 'other'  →  'boss'
  差异字段数 = 2

  逐层核对（哪些层真的按关系分流）：
    validator/rules.py    : 不消费关系枚举（只要求 recipient_relation 是非空字符串）。
                            → 规则层无任何规则因新值生效（PM 定性：/validate 是规则门不是契约门）。
    workflow/prompts/*.md : generate.md / repair.md 无逐关系枚举，只有通用「低关系压力」措辞。
                            → 提示词不需要改动，也不会因新值自动换挡。
    web/server/intake.mjs : choice("recipient_relation", RELATIONS_FULL)。
                            → 与 Python 同形的白名单闸门；变体表里加了 boss 才放行。
    web/server/mock-model.mjs relationFlavor()：有 8 个键，没有 boss 键。
                            → 把 recipient_relation_id="boss" 渲染呈现时，
                              与 "other" 的 presentation_json 完全相同 = True
                              与 "pursuit" 是否不同 = True
                              实际贺卡文案：生日快乐！一点心意，祝一切顺利。
                              实际关系提示：['关系信息有限，保持中性表达']
                            → 结论：单独加枚举值**不会**让「职场分寸／送礼边界」分支生效；
                              它只会让 boss 从 other 的中性话术变为「有明确关系名」的中性话术。
