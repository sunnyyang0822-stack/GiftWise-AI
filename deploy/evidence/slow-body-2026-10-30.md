## 2. 改了什么（最小改动）

### 2.1 `deploy/server.py`（默认入口）

```python
READ_TIMEOUT_SECONDS = float(os.environ.get("GIFTWISE_READ_TIMEOUT", "10") or "10")
if READ_TIMEOUT_SECONDS <= 0:
    raise RuntimeError("GIFTWISE_READ_TIMEOUT must be > 0")

class Handler(BaseHTTPRequestHandler):
    timeout = READ_TIMEOUT_SECONDS          # StreamRequestHandler.setup() 会据此 settimeout()

    def _read_body(self, size):             # 带【总预算】的正文读取（不是裸 rfile.read）
        deadline = time.monotonic() + READ_TIMEOUT_SECONDS
        while remaining > 0:
            budget = deadline - time.monotonic()
            if budget <= 0: raise TimeoutError(...)
            self.connection.settimeout(min(READ_TIMEOUT_SECONDS, budget))
            chunk = self.rfile.read1(remaining)   # 对端关闭 → 返回短读
            ...
        self.connection.settimeout(READ_TIMEOUT_SECONDS)   # 读完即恢复完整额度（见下）

    def _send_request_timeout(self):        # 408 + 关闭；不回显任何已读字节
        self.close_connection = True
        self._send(HTTPStatus.REQUEST_TIMEOUT, {"error": "REQUEST_TIMEOUT"})
```

`do_POST` 里的 `self.rfile.read(size)` 换成 `self._read_body(size)`，并新增一条
`except TimeoutError: self._send_request_timeout()`（在既有 `INVALID_JSON` 分支之前）。

**为什么正文读完后要恢复额度**：读取期间 socket 超时被压到"剩余预算"，
若正文恰好在预算最后一刻读完，剩下的响应写出只有几毫秒期限，可能把**本该正常的响应**掐掉
（408 路径本来就在写之前重置了额度，成功路径没有）。这是本轮在首轮 42/42 之后补的一行，
补完后全部证据已重跑（最终一轮 `raw/slowbody-20261030-232005/`）。

**为什么单有 `timeout = 10` 不够**：socket 超时是**单次 recv** 的期限，
"每 9 秒发 1 字节"的滴流能一直续命。因此正文读取用**总预算**（10 秒内必须读完，
或对端关闭），两种拖法都被同一个上限截断（B4 断言验证）。

**为什么默认值取 10 秒**：与我在 S-5 里登记的修复方案一致，且远小于 QA 观察到的 45 秒；
≤64 KiB 的正文若 10 秒还传不完，属于异常客户端。可用 `GIFTWISE_READ_TIMEOUT` 覆盖（测试用 3 秒验证过）。

### 2.2 `deploy/observable_server.py`（可观测入口）—— 同一缺陷，一并修

`_peek_body()` 原本也是 `self.rfile.read(declared)` 且 `except Exception: return None`：
超时被吞掉后，父类的 `handle_one_request` 只会**静默关闭**（不产生响应），
或者读到缓冲区里那 5 个字节 → 错误的 400。改为：

```python
    def do_POST(self):
        try:
            body = self._peek_body()
        except TimeoutError:
            self._send_request_timeout()     # 与默认入口同一套语义：408 + 关闭
            return
    def _peek_body(self):
        try:
            return self._read_body(declared)  # 复用父类的带预算读取
        except TimeoutError:
            raise
        except Exception:
            return None
```

两个入口现在**共用同一实现**（子类只覆写钩子），因此不会再出现"一个修了、一个没修"。
408 会被 JSONL 与 `/metrics` 记录（E3/E4）。

## 4. 影响面（如实说明）

- **新增了一个状态码**：`408` + `{"error":"REQUEST_TIMEOUT"}`。此前不存在该组合；
  只在"正文读不完"时出现，正常/既有 6 类路径的行为**逐字节不变**（已用 10 用例矩阵证明）。
- **`Content-Length` 声明值 > 0 时**，服务端现在会按 `Content-Length` 读取正文（原本也是），
  但**最多等 10 秒总量**；`Content-Length` 缺失/非法/超限仍是 413（不读正文，行为不变）。
- **请求行/请求头超时**：由标准库 `handle_one_request` 的 `except socket.timeout` 处理 ——
  **静默关闭、不返回响应**（B2/B3 实测 3 s 内关闭）。这与"正文超时返回 408"不同，
  是标准库既有行为，本轮**没有**改动它（要改成 408 需要覆写 `handle_one_request`，属于更大改动）。
- **`Dockerfile` 未改**：镜像默认 `CMD` 仍是 `python -m deploy.server`（现在这条路径**已带 S-5 修复**）；
  可观测入口仍未成为默认入口。

## 5. 未做到 / 未验证

1. **并发连接数仍无上限**：`ThreadingHTTPServer` 每连接一线程，10 秒内可以建立任意多条连接
   （每条只发 5 字节）把线程数堆起来；超时只是让每条连接**有界**，不是限流。
   更彻底的做法是限制并发连接数或前置反向代理 —— **本轮未做**（超出"最小改动"范围，已登记进 `security-review.md`）。
2. **未做压测**：没有测"1 万个真实连接"或"1 万次调用"时演示机的表现（与 S-2 的未完成项同一条）。
3. **请求行/请求头的超时不返回 408**（静默关闭），未改成显式响应。
4. **未在任何云端环境验证**（无账号、无授权，按边界不采购）。
5. **`GIFTWISE_READ_TIMEOUT` 的非默认值只在本机验证**（容器内用的是默认 10 s）。

## 6. 本轮 harness 自身踩过的坑（首轮失败现场保留）

首轮（`raw/slowbody-20261030-230911/`）**失败 3 项**，原因全在验证脚本、不在被测代码，按纪律保留现场：

1. **容器就绪判定过早**：Docker 的端口代理会**先于应用**接受 TCP，`wait_port` 通过 ≠ 应用已监听 →
   改成"反复请求直到真正拿到 200"（`wait_http`）。
2. **`docker exec` 用了裸命令名**：Windows 上 `CreateProcess` 用**父进程** PATH 解析可执行文件，
   传 `env=` 里的 PATH 不生效 → 必须用 `shutil.which` 找到的**绝对路径**（或已在 Docker 目录里的可执行文件）。
3. **滴流测试串行读**：发送方要持续 40 s，若先发完再读响应就永远读不到 → 改为发送与接收**并发**。
4. **"修复前线程不回收"的采样点选错**：最初在**客户端关闭之后**采样，读立刻返回、线程已释放，
   采不到"不回收" → 必须在**客户端仍持有连接**时采样（连接后 2 s 与 12 s 各一次）。
