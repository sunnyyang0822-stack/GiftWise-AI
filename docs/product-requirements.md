# 产品需求：MVP 设计

更新时间：2026-10-30（北京时间）。状态：产品对齐完成，契约决定已记录；缺口 G-1…G-4 待补（见 `docs/pm-reviews/stage-2-acceptance-checklist-2026-10-30.md`）。Issue #1 正文已可直接访问，本文件与之一致；不把未核实内容写成事实。

## 背景、目标用户与场景优先级

GiftWise AI 面向主要青年用户，解决“不知道送什么、担心不合适、关系表达过强或过弱、预算／禁忌／准备时间冲突”等送礼决策问题。当前优先级是产品定位判断，不是已完成的频率统计：

1. 恋人送礼。
2. 追求对象送礼。此关系与恋人完全分开，不假定双方已建立恋爱关系或互有好感。
3. 朋友送礼。
4. 上司、亲戚家人、同学、老师／导师、客户／合作伙伴等其他关系。

**同事已完全移出产品场景**（2026-10-30 产品负责人决定）：产品界面、导航、演示脚本和验收案例均不出现同事；仅保留为技术回归案例（`tests/` 回归夹具与本地样例），不向产品用户暴露。公开内容只使用虚构人物和脱敏数据。

## 产品价值与 Agent 增量

普通聊天推荐通常直接给出若干想法，难以证明依据、硬约束和修改边界。GiftWise AI 必须完成：需求结构化、三个不同方案、事实／推断／未知分离、独立规则校验、最多一次自动修订、用户明确选择，以及选择后才生成的风格配色、包装、贺卡／装饰和赠送方式。模型不能覆盖用户预算、天数或明确禁忌；系统也不承诺对方一定喜欢。

## 输入体验

用户目标是约 60 秒完成初始输入，实际完成时间待测。输入分三步：

### 第一步：关系与场景

- 关系（8 个稳定 ID，与冻结契约一致）：**恋人 `partner`**、**追求对象 `pursuit`**、朋友 `friend`、家人 `family`、同学 `classmate`、老师／导师 `mentor`、客户／合作伙伴 `client_partner`、其他 `other`。恋人与追求对象是两个独立值，不得合并。
- 熟悉程度：非常熟悉、比较熟悉、了解不多、几乎不了解、不确定。
- 场合：生日、节日、感谢、纪念日、毕业／升职祝贺、其他。
- 预算：先选预设区间，再确认明确金额上限；支持自定义金额。
- 时间：先选时间区间，再确认最终可用准备天数。
- 首版只支持人民币 CNY。

预算金额包含礼物、包装、贺卡、装饰和配送等估算费用；准备天数表示可用准备时间，不是送达承诺。预算和天数不能静默补默认值。

### 第二步：兴趣与风格

兴趣标签包括设计与艺术、咖啡与美食、阅读与学习、科技与数码、运动与户外、音乐与电影、游戏与动漫、旅行与探索、家居与生活、植物与自然、时尚与配饰、体验与活动、暂时不知道。每个兴趣单独设置可信度，`interest_confidence` 只接受 `confirmed` 或 `inferred`；界面上的“未知／暂时不知道”是互斥状态，**不是机器值**，提交时表示为 `interests: []` 与 `interest_confidence: {}`。未知时不生成事实，不根据性别、年龄或职业擅自推断兴趣。

礼物风格包括有设计感、实用型、个性化定制、有趣能带来惊喜、有纪念意义、体验型、精致但不张扬、不确定。

### 第三步：排除与补充

用户填写不喜欢或不适合的类型、明确禁忌和可选短说明。明确禁忌是硬性约束；不能可靠理解的限制需要先澄清。

## 输出与阶段边界

阶段一必须输出恰好三个不同思路，包含理由、事实引用、推断、未知信息、全量估算费用、CNY 币种、准备时间和独立规则检查结果。最多自动修订一次并重新检查。用户只能选择通过检查的方案，系统不自动替选。

阶段二只围绕用户选中的方案生成，并按以下顺序呈现：

1. 风格与配色。
2. 包装材料与步骤。
3. 贺卡正文，以及花等装饰物建议。
4. 赠送时机、方式和话术。

阶段二必须复核礼物、包装、贺卡、装饰和配送的总费用、准备时间及禁忌。全局两个阶段合计最多一次自动业务修订。

恋人与追求对象必须使用不同的提示、关系风险说明、贺卡语气和赠送话术。追求对象默认采用低压力表达，避免暗示关系已经确定。

## P0 范围

1. 中文三步输入和服务端可信请求整理。
2. 恋人、追求对象、朋友及其他关系的场景适配。
3. 预算区间加明确上限确认、自定义预算、时间区间加最终天数确认。
4. 逐项兴趣可信度设置。
5. 三个不同候选及事实／推断／未知分离。
6. 独立规则检查、一次修订和重新检查。
7. 只允许用户选择通过检查的候选。
8. 选择后按既定顺序生成风格配色、包装、贺卡／装饰和赠送方式。
9. 中文加载、空状态、错误、超时、无可选方案和未选择状态。
10. 记录运行 ID、候选版本、校验结果、修订次数、调用次数和失败原因。

## P1 与边界

P1 包括视觉精修、动效、更多关系模板、性能分析和成本看板。暂不开发账号、长期记忆、支付、实时库存和未经验证的商品价格源；不虚构 Dify、云部署或实际物流状态。是否引入 FastAPI、Docker 或 UCloud 取决于真实沙箱兼容性、比赛要求、资源和实测证据。

## 默认低风险策略

没有任何兴趣信息时，优先通用生活用品、文具、低承诺体验、可替代或可自主选择的方向；避免强烈浪漫、尺寸敏感、气味敏感和明显个性化物品。该策略是设计方案，不代表用户研究结论。

## 成功标准与待验证假设

成功标准是：用户能完成明确输入；系统真实生成三个不同候选并完成规则校验；失败项不可选；选择前不生成详细赠送设计；选择后输出完整且通过增量校验的指南；跨阶段最多一次自动修订；所有状态和限制可解释。

待验证问题包括：青年是否愿意完成三步输入、60 秒目标是否可达、三个候选是否足够、事实／推断／未知分离是否提升信任、两种关系文案是否降低压力、包装和装饰是否可执行、延迟与费用是否可接受。当前没有真实用户研究、真实商品价格、库存、物流、Dify 或云部署完成结论。
