## 2. 设计提案（最小改动集）

### 2.1 取值命名建议：**只加一个 `boss`，中文「职场上司」**

| 问题 | 建议 | 理由 |
| --- | --- | --- |
| 机器值命名 | `boss` | Q5（`docs/scenarios/03-…md:126-141`）原文建议 `boss` / `supervisor`；`boss` 更短、与既有全小写蛇形风格一致 |
| 是否加同义词 | **不加**（不要 `supervisor`/`leader`/`manager`/`chief`） | ① `docs/intake-contract.md:11` 已明确「**不自动翻译、猜同义词或裁剪**」——同一语义给多个 ID 会立刻产生需要二次消歧的代码分支；② `pursuit` 先例就是**只加一个值**；③ 代码分支按 `recipient_relation_id` 判断，多值会让「给上司送礼」逻辑要写 `in (...)` 而不是 `==`，更容易漏 |
| 中文显示文本 | **`职场上司`** | 与 `AGENTS.md:11`「再次**职场上司**、亲戚家人等」逐字一致；`docs/product-requirements.md:15`／`product-flow.md:126` 同样用「职场上司」 |
| 覆盖范围 | 一个值覆盖「上司／领导／老板／上级／主管」 | 这 5 个词在中文里对应**同一种关系位置**（职务上的直接上级），不是 5 种关系；分级细化的收益（部门经理 vs CEO）不足以支撑新增 ID，且会破坏「一个语义一个值」 |
| 是否需要 `unknown` 之外的状态 | 不需要 | `boss` 是确定的已声明关系；不确定仍走既有 `unknown` → 澄清 |
| 是否加契约闸门（如 `BOSS_CONTRACT_READY`） | **不需要**（建议不加） | `pursuit` 的闸门是因为当时「界面先上、契约后落地」的**分阶段**现实（`config.mjs:9-35` 有完整记录）。本次若按第 4 节条件 3 **同批落地**，契约与代码同时生效，闸门没有存在意义，只会新增一个需要维护的开关和一条永远不会触发的分支 |

## 4. 决策材料：**不修的代价 vs 修的代价**

### 4.1 不修的代价（3 条）

1. **产品定位与代码正面冲突，且可被一分钟证伪。**
   `AGENTS.md:11` 白纸黑字把「职场上司」列为第三优先级；但任何人都能跑
   `python -c "from workflow.labels import RELATIONS; print([k for k,v in RELATIONS.items() if '上司' in v])"` → `[]`。
   这不是"功能没做"，而是"**定位声明与机器可检验的事实不一致**"——比功能缺失更难辩解。
   而且**同一优先级的兄弟关系（家人/同学/导师/客户）都有值**，只有上司没有，属**内部不一致**，不是范围取舍。

2. **关系语义在 `request_json` 里永久丢失，且恰落在最需要分寸的场景。**
   前端只能落 `other`，于是 `recipient_relation_id="other"` 一路传到底：报告显示"其他"、贺卡与赠送话术用中性模板、关系提示是"关系信息有限，保持中性表达"。
   **给上司送礼是合规与得体高度敏感的场景**（预算、场合、是否私人化、是否在办公场合交接），恰恰最需要关系分流；而系统此时**无法把"给上司送礼"与"给邻居送礼"区分开**。

3. **Q5 已在案且评级不低，不改就是"发现了但没闭环"。**
   `docs/scenarios/03-…md:16` 把它列为 🟠 **中高**，并且在同一份质疑清单里**排位靠前**（第 2 条，仅次于 Q8）。
   早间评审如果翻这份文档，"发现了、评级中高、但至今没有处置记录"是一个很容易被追问的状态。

### 4.4 我的建议：**有条件修**

**推荐 `有条件修`。条件三条，缺一不可：**

**条件 1（口径前提，必须 PM 先裁决）——这是能否修的前提。**
