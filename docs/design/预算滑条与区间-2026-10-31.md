## 1. 滑动条取值域

### 1.1 结论

| 子问题 | 结论 |
| --- | --- |
| 0 / 1000 是端点还是档位边界？ | **端点值（闭区间 [0, 1000]）**，与「档位边界」二义性无关 |
| 拖动是连续还是吸附？ | **吸附，步长 50 元** |
| 档位数 | 1000 / 50 + 1 = **21 档**：0, 50, 100, …, 1000 |
| 单滑块还是双滑块？ | **双滑块（区间）**，因为用户给的是**区间范围**不是确定值 |
| 吸附取整规则 | **四舍五入到最近档；恰在中点向上取（round-half-up）**。例：124→100，125→150，137→150 |

### 1.2 理由【推断】

1. **为什么是端点值**：现行 `checker.mjs:20` 的 `AMOUNT_RE = /^(?:0|[1-9][0-9]*)(?:\.[0-9]{1,2})?$/`
   与 `validator/rules.py:128` 的 `_amount` **都能表示 0 和 1000.00**，格式层没有障碍。
   把 0 或 1000 定义成"档位边界"（即"小于 50 都算 0"）会让界面上"我明明选了 0"与后端收到的值不一致，
   直接违反 `docs/intake-contract.md:70`「**前端不得静默填预算**」。
2. **为什么步长 50 而不是 10 / 1**：
   - 21 个档位在 320–390px 宽的移动端轨道上，每档约 15px（轨道 ~300px），
     而触控拇指（thumb）视觉直径约 20px —— **相邻档位可分辨**。步长 10（101 档）每档 ~3px，
     用户无法精确停在某一档，拖动必然抖动。
   - 现行 `web/server/config.mjs:121–125` 的 5 个 chip 边界 **0 / 100 / 200 / 500 / 1000 全是 50 的整数倍**
     ⇒ 旧档位可以无损降级为滑条上的档位，`server.mjs:163` 导出的 `ranges.budget` **不必立刻删除**，
     可在一个迭代内平滑迁移。
   - 本项目**所有**价格都是模型估算，固定携带 `business_data_verification=not_verified`
     （`tests/test_validator.py:114` 断言、`docs/demo` 归档亦如此）⇒ **50 元精度已经超过数据可信度**，
     更细的档位是"虚假精度"。
3. **为什么必须吸附不能连续**：连续拖动会产生 `137.4826` 这类值，而契约要求
   「有限、非负、最多两位小数」（`checker.mjs:109`、`rules.py` 的 `_amount`）。
   若浮点值被静默截断成两位，就再次违反「前端不得静默填预算」；若不截断就必然报
   `INVALID_AMOUNT`。**吸附是唯一能同时满足"可表示"与"不静默改值"的方案。**
4. **为什么双滑块**：用户原话是「用户给的是**区间范围**，不是确定值」。单滑块只能给一个点，
   必须靠"附加选项"补区间，交互会更绕。双滑块直接产生 `[min, max]`。

### 1.3 ⚠️ 命名冲突（实测发现，必须先解决）

`web/public/app.js:50` **已经**有一个叫 `budget_range` 的前端 state 字段：

```js
// web/public/app.js:50（实测）
budget_range: null,          // 存的是 chip 的 id 字符串，如 "r1"（见 :287, :303）
```

它存的是**字符串 id**（`cfg.ranges.budget.find((r) => r.id === f.budget_range)`，`:287`），
**不是** `{min, max}` 对象。若契约方案 a 也叫 `budget_range` 并且是对象，
实现者极易把两者混用。

**【推断】建议**：契约键用 `budget_range: {min, max}`（与新语义一致），
前端 state 里那个旧的字符串字段**重命名**为 `budget_preset_id`（或直接删除，
因为滑条不再需要 chip id）。这一条必须写进实现任务单，否则会出真 bug。

## 2. 「附加选项」：文案、行为、落契约

### 2.1 结论：4 个互斥选项 + 1 个默认态

沿用现行 chip 交互（`web/public/app.js:299–307`，`chip--radio`，单选）。

| # | 文案（面向用户，简体中文） | 行为 | 落到契约的值 |
| --- | --- | --- | --- |
| A | **「0–1000 元（拖动选择）」** —— **默认态** | 激活双滑块；两端吸附 50；区间实时回显在滑条下方 | `budget_range: {min: "<左端>", max: "<右端>"}`；服务端派生 `budget_amount = max` |
| B | **「0 元 · 不花钱的心意」** | 滑条禁用并把两端钉在 0；提示改为「我们会只给 DIY / 手写 / 心意类方案」 | `budget_range: {min: "0", max: "0"}`；`budget_amount = "0"` |
| C | **「1000 元以上 / 其他金额」** ← **这是「其他」** | **唯一**解锁自由填写：滑条禁用，出现 `最小` 与 `最大` 两个输入框（0–10000，最多两位小数） | `budget_range: {min, max}` 原样透出；`budget_amount = max` |
| D | **「不确定 / 看情况」** | 滑条禁用；**不产生**任何预算值；展开三档宽区间 `0–300` / `300–600` / `600–1000` 让用户**选一个**；未选前「下一步」不可用 | **不可提交**（见下）；选中宽档后按 A 的规则落值 |
| — | （可选第 5 个）**「越省越好，不超过我选的数」** | 等价于 A 但文案强调省钱；可推迟 | 同 A |

### 2.2 「不确定/看情况」为什么**不能**直接提交【推断，有原则依据】

`docs/intake-contract.md:46` 已经为兴趣/风格定下原则：

> UI 的"暂时不知道/不确定"是互斥交互状态，**不是可提交的机器值**

预算必须**同一条原则**。否则会出现一个没有 `max` 的请求，而
`validator/rules.py:199` 的 `total > context["budget"]` 直接失去比较对象 ——
要么崩、要么被迫"放行一切"，两种结果都击穿「未通过规则校验的方案不可选」这条核心主张。

**因此：D 是交互态，不是值。** 它必须收敛到 A 的具体区间后才允许提交。

### 2.3 「1000 元以上」与「其他」为什么合并成一个选项

用户给的原话是「另有附加选项；**只有用户选了「其他」才能自由填写**」——
即**自由填写只能有一个闸门**。若把「1000 元以上」和「其他」做成两个 chip，
两者都需要自由填写（因为 1000 以上的具体数只能手填），就会**出现两个闸门**，与用户规则直接冲突。

【推断】**合并为 C 一个选项**是唯一自洽的解法：它既是"1000 元以上"的出口，
也是用户所说的「其他」，机器 id 用 `other`。
文案里把两个意思都写出来：**「1000 元以上 / 其他金额」**。

### 2.4 与现行 chip 的关系【实测】

现行 `web/server/config.mjs:120–126`：

```js
export const BUDGET_RANGES = [
  { id: "r1", label: "100 元以内", min: "0", max: "100" },
  { id: "r2", label: "100–200 元", min: "100", max: "200" },
  { id: "r3", label: "200–500 元", min: "200", max: "500" },
  { id: "r4", label: "500–1000 元", min: "500", max: "1000" },
  { id: "r5", label: "1000 元以上", min: "1000", max: null },   // ← max 为 null
];
```

两点实测结论：

1. **r5 的 `max: null` 已经暴露了同一个问题**：`app.js:287–289` 对 `max` 为 null 的档位
   只能显示「该区间没有固定上限，请直接填写你确认的金额」，即**它已经是"自由填写"闸门**。
   所以现在的界面上**已经有两个**自由填写入口（r5 + 手填框）—— 用户的新规则正是在纠正这一点。
2. ⇒ **r5 必须被 C 取代**，`BUDGET_RANGES` 里的 `max: null` 这个形状在新契约下**不允许存在**
   （见 §5 判定规则 E9）。

### 3.1 方案 a（**推荐**）：新增 `budget_range: {min, max}`，`budget_amount` 降格为服务端派生的 `max`

**契约键**

```jsonc
// 前端提交（intake 层，白名单内）
"budget_mode": "slider" | "zero" | "other",        // 新增，记录用户是哪个闸门进来的
"budget_range": { "min": "0", "max": "1000" },     // 新增；min/max 均为十进制 string
"budget_amount": "1000",                            // 保留必填（兼容既有校验器与提示词）
```

服务端 intake（`web/server/intake.mjs`）**派生并覆盖**：

```
budget_amount := budget_range.max          # 单一真值，:199 只认它
```

**为什么要保留 `budget_amount`（本方案的关键）**：
`validator/rules.py:199` 只读 `context["budget"]`（来自 `:160`），而 `:160` 只读 `:128` 的标量。
只要 `budget_amount` 仍等于 `max`，**候选侧一行都不用改**，
320 个夹具里 276 个用 `budget_amount: "200.00"` 的用例（实测占比 276/320 = 86.3%）
**在结构上不可能受影响**。

## 4. 🔴 0 元裁决（本条是全文最重要的结论）

### 4.1 结论

> **0 元合法。**
> 语义 = **「本次礼物不花钱」**，即 DIY / 手写 / 心意类方案（例如手写贺卡 + 自制小物），
> **不是「没填」、不是「未知」、不是「无限」**。
> `validator/rules.py:131` 放宽为 `0 <= budget <= 10000`。

### 4.2 理由

1. **控件不能说谎**【推断】：滑条左端就是 0（用户原话）。若 0 非法，
   用户能拖到 0、能看到 0、提交后却被 `LIMIT_EXCEEDED` 拒绝 —— 界面与契约直接矛盾。
   这是**用户可见的判定不一致**，比任何实现成本都严重。
2. **与天数口径一致**【实测】：`docs/intake-contract.md:70` 已允许 `deadline_days = 0`
   （「0 表示当天可用准备时间」）。预算与天数同属"数值下限"问题，
   两者取不同的下限语义是**口径漂移**。
3. **与"未知不是机器值"原则不冲突**【实测，依据 `docs/intake-contract.md:46`】：
   那条原则说"不确定"不是值。**0 是"确定的不花钱"**，与"不确定"是两件事。
   "不确定"由 §2 的选项 D 承担，且它**不可提交**。两者分工明确，互不替代。
4. **现行禁 0 的裁决来源是"修订 VAL-001 §5"**【实测，`docs/intake-contract.md:205`】，
   而 VAL-001 §5 **原文是允许零预算的**，`docs/intake-contract.md:149` 明写
   「**修订** VAL-001 §5 原「零预算允许」」。⇒ 禁 0 本身是一次**翻转**，
   现在按用户新需求把它**翻回去**，有据可依，不是凭空放宽。

### 4.3 对 `validator/rules.py:199` 意味着什么（⚠️ 必须配套，否则产品死局）

`rules.py:199` 是 `if total is not None and total > context["budget"]`。
当 `budget = 0` 时：**任何 `total > 0` 的候选全部 `OVER_BUDGET`**。

后果【推断，逻辑必然】：用户选「0 元 · 不花钱的心意」→ 三个有价候选全部不可选 →
`all_passed = false` → 按核心主张「未通过规则校验的方案**不可选**」→ **界面没有任何可选方案**。

这不是 bug，是**正确判定**（0 元确实买不了有价礼物）。但**产品上不可接受**，
因为它把一个可理解的用户意图变成了死局。**因此 0 元合法必须配套三件事**：

| # | 配套要求 | 落点 |
| --- | --- | --- |
| 1 | 候选生成提示词在 `budget_amount == "0"` 时必须只产 `estimated_total = "0.00"` 的**心意类**方向 | 提示词/工作流线（不在本文件范围） |
| 2 | 若三候选仍全为有价 ⇒ 返回**可读解释**，不能只抛 `OVER_BUDGET` 码 | 前端 `app.js`（§8 波及面） |
| 3 | 呈现阶段复核同样只比礼物价（见 §6） | `checker.mjs:502` |
| 4 | 已有测试同步改 | 下表 |

## 5. 区间与候选校验的交互：精确判定规则

### 5.1 结论：硬上限 + 软下限

| 条件（金额**全部转分/Decimal 整数比较**） | 判定 | 是否可选 |
| --- | --- | --- |
| `total > max` | `OVER_BUDGET`，**error** @ `candidates[i].estimated_total` | ❌ **不可选**（保持现行语义） |
| `total == max` | 通过，**无提示** | ✅ 可选 |
| `min < total < max` | 通过，**无提示** | ✅ 可选 |
| `total == min` | 通过，**无提示**（相等**不算**"低于"） | ✅ 可选 |
| `total < min` | **新码 `BELOW_BUDGET_RANGE`，warning**（`rules.py:168` 的 `warnings` 数组） | ✅ **仍可选** |
| `min` 为 `null`（用户只填上限） | 不执行下限分支，**永不**产生该 warning | ✅ 可选 |

**伪代码（两支实现必须逐字等价）**

```
max = context.budget                 # = budget_range.max，且 budget_amount 已由服务端派生为它
min = context.range_min              # None 表示未设下限

if total is not None and total > max:
    error(OVER_BUDGET, "candidates[i].estimated_total", "估算总费用超过预算上限")
elif total is not None and min is not None and total < min:
    warnings.append(BELOW_BUDGET_RANGE,
                    "candidates[i].estimated_total",
                    "估算总费用低于你给的预算下限，仍可选")
# 无 else 分支：min <= total <= max 通过
```

### 5.2 为什么低于下限**只提示不拦截**（关键论证）

1. **语义不对称**：`total > max` 是"超支"，是会花钱的风险；`total < min` 是"省钱"，
   **不构成任何风险**。
2. **核心主张的原意**：「未通过规则校验的方案**不可选**」的立法目的是拦截
   **违规、不安全、超支、超期**（现行 error 码即 `OVER_BUDGET`/`PREPARATION_TOO_LONG`/
   `FORBIDDEN_TAG`/`FORBIDDEN_TERM`/`CURRENCY_MISMATCH`/`UNKNOWN_FACT_REF` 六类）。
   把"比你打算花的少"塞进这个名单，是**扩大化解释**，会让"物美价廉"的好方案被误杀 ——
   这是产品伤害，不是合规收益。
3. **不能污染 `all_passed`**【实测依据】：320 个夹具中大量断言
   `case["expected"]["all_passed"]`（`tests/test_validator.py:110`）与
   `candidate_passed`（`:111–113`）。若把软下限做成 error，`all_passed` 的语义就被改写，
   影响面从 5 个夹具扩散到所有设了下限的用例。
4. **但它必须可见**：用户既然主动给了 `[min, max]`，"没花到下限"是他的决策信息。
   现行 `rules.py:168` 的 `result["warnings"]` **本来就是为这种事准备的**，不新增结构。

### 5.3 边界含等号（明确写出，避免实现分歧）

- `total == max` **通过** —— 现行已有正面夹具：`gen-parity-fixtures.mjs:130`
  ```js
  { id: "边界-刚好等于预算", candidates: batchWith((b) => (b.candidates[0].estimated_total = request.budget_amount)) },
  ```
  以及 `gen-parity-fixtures.mjs:133` 的"超一分钱"反例。
  单测侧：`tests/test_validator.py:47` 起（`test_decimal_boundary_ignores_context_rounding`）
  明确要求"十进制比较不按浮点取整"，`"10000"` vs `"10000.00"` 通过、`"10000.01"` 失败。
  **这些在方案 a 下全部不变。**
- `total == min` **通过且不提示** —— 相等不属于"低于"。
- ⚠️ **禁止浮点**：JS 侧 `checker.mjs:49` 定义的 `amountToCents` 返回 **BigInt 分**
  （`amount()` 于 `:114` 调用它），
  比较是 `budget < 100n || budget > 1000000n`（`:171`）与 `total > context.budget`（`:296`）；
  Python 侧 `Decimal`。**新增的 `min` 比较必须沿用同一表示**，不得引入 `float`。

### 5.4 请求侧区间自身的合法性（先于候选侧）

| 条件 | 判定 |
| --- | --- |
| `min`、`max` 任一不是十进制 string | `INVALID_AMOUNT`（**格式优先于范围**，对齐 `rules.py:128–132` 与 `checker.mjs:109` 既有纪律） |
| `min > max` | **`INVALID_BUDGET_RANGE`** → 请求侧 `needs_input`；**不得静默交换**（静默交换＝静默改用户输入，违反 `docs/intake-contract.md:70`） |
| `max` 缺失或为 `null` | **`INVALID_BUDGET_RANGE`** —— 无上限则 `rules.py:199` 失去比较对象（见 §2.4 的 `r5: max: null` 必须被消灭） |
| `min` 缺失或为 `null` | **合法**，等价于"不设下限" |
| `max > 10000` | `LIMIT_EXCEEDED` → `needs_input`（现行口径不变，`rules.py:131`） |
| `min < 0` / `min > 10000` | `LIMIT_EXCEEDED`（与 `max` 同一上界） |
| `budget_mode == "slider"` 但 `max > 1000` | **拒绝 `INVALID_BUDGET_RANGE`**【推断】理由：滑条物理上到不了 1000 以上，这种组合是**前端不可能产生的输入**；接受它就等于给了一条绕过"只有「其他」才能自由填写"的后门，直接违反用户规则 |
| `budget_mode == "other"` 且 `max <= 1000` | **允许**（用户从"其他"进去却填了个小数，无害；不得反过来拒绝，否则制造"填错就卡死") |
| `budget_mode == "zero"` 但 `min != 0` 或 `max != 0` | **拒绝 `INVALID_BUDGET_RANGE`**（模式与取值必须自洽） |
