### 1.2 「四步 / 第 X / 3 页」不一致的核实结果

**核实结论：真正自相矛盾的是同一个元素内部，位置在 `#steps`。**

`#steps` 这个 `<nav>` 有两个数字来源，**它们写在同一个 DOM 元素上**：

1. **静态**：`index.html:297`
   ```html
   <nav class="steps" id="steps" aria-label="填写进度：四步"></nav>
   ```
   `aria-label` 是**写死的字符串，`app.js` 从不更新它**（`renderSteps()` 只做 `replaceChildren()` 与 `hidden`，见 `app.js:149-176`，全文没有对 `#steps` 的 `aria-label` 赋值）。

2. **动态**：`app.js:166`
   ```js
   nav.append(el("span", { class: "step-page", text: `第 ${state.step} / 3 页` }));
   ```
   屏读顺序 = 先读 `aria-label`，再读子节点文本 → 无障碍用户会听到
   **「填写进度：四步 … 第 1 / 3 页」**，在同一元素内直接冲突。

**这是唯一一处「同一元素内自相矛盾」的地方。哪一处过期了：**

- ❌ **`index.html:297` 的 `aria-label="填写进度：四步"` 是与该元素实际内容不匹配的描述。** 理由：该元素**唯一的动态内容是页数**（`app.js:166`），pill 才是主题数（`app.js:172`）。`aria-label` 描述了这个元素里**根本没有显示的那个数字**，而且它覆盖（override）了子节点语义。→ 应改为按页口径，或删掉 `aria-label` 让子节点文本自己说话。
- ✅ **`app.js:166` 的「第 X / 3 页」正确**，`state.step ∈ {1,2,3}` 已逐点核对（§1.1）。
- ⚠️ **`index.html:286` 是第三处、也是唯一"孤立"的数字**：
  ```html
  <button class="gw-button" type="button" id="cta-start-3">
    开始挑选礼物 · 填写三步需求
  ```
  同页其他四处都用「四步」：`index.html:7`（meta description「四步中文输入」）、`index.html:98`（「真要用起来，是这样四步。」）、`index.html:121`、`index.html:283`（「四步，大约 60 秒」）。**「填写三步需求」是页面上唯一说"三步"的面向用户文案。** 它虽然与"页面数=3"巧合一致，但与页面通篇词汇冲突，属**词汇不统一的过期/残留文案**。

**一句话交付**：交互上是 **3 个页面 / 4 组主题**；「第 X / 3 页」是对的；「四步」在"信息主题"口径下也是对的，但它被错贴到了 `#steps` 这个描述**页数**的元素上（`index.html:297`）；`index.html:286` 的「三步需求」是与全页冲突的孤立文案。

   ```js
   345|  const total = textOf(totalCents);
   ```
   `centsOf` / `textOf` 为 BigInt 分↔字符串互转（`mock-model.mjs:18-28`）。
2. **校验侧**（**强制**这条等式，不满足即整份呈现失败）`checker.mjs:496-501`：
   ```js
   496|  const additional = amount(presentation.additional_cost, ...);
   497|  const revisedTotal = amount(presentation.revised_estimated_total, ...);
   498|  const originalTotal = amountToCents(candidate.estimated_total);
   499|  if (additional !== null && revisedTotal !== null && originalTotal !== null && additional + originalTotal !== revisedTotal) {
   500|    error(errors, "TOTAL_MISMATCH", "presentation.revised_estimated_total", "修订后总费用必须等于原估算加新增费用，不能通过下调原价腾出预算");
   ```
   并且 `checker.mjs:502-503` 另外强制 `revisedTotal <= budget`（`OVER_BUDGET`）——即**不允许用"总价降下来"来腾预算**。
3. **前端展示侧**：直接取这三个值（`app.js:1002-1007`）。

> 补充：推荐阶段是**每个候选各自单独比预算**，不求和。`checker.mjs:296-297`：`total > context.budget → OVER_BUDGET`。

### 6.4 含不含包装？—— 声称含，但没有任何代码验证

**（a）文案声称"含"**：
- `app.js:883`（推荐页每个候选的费用行）：`「${candidate.estimated_total} ${candidate.currency}（含包装、贺卡与配送估算）」`
- `app.js:296`（预算卡说明）：`「含礼物、包装、贺卡、装饰和配送的估算总费用。」`
- `app.js:351`（预算确认勾选文案）：`「…就是本次礼物＋包装＋贺卡＋装饰＋配送的全量上限…」`
- `app.js:431`（天数确认勾选文案）：`「…（礼物＋包装＋贺卡＋配送合计）…」`
- `index.html:181`（FAQ）：`「页面上出现的所有价格都是估算（含礼物、包装、贺卡、装饰与配送）」`
- 契约 `docs/intake-contract.md:18`：`budget_amount` 是「明确的全量预算上限…含礼物、包装、贺卡、配送等」
- 模拟数据的 `unknowns` 文案也这么写（`mock-model.mjs:42`、`:54`：「估算含基础包装、贺卡和配送」）

**（b）但代码里没有任何地方单独计算包装费用**（【实测】）：
- `additional_cost` 在**默认路径恒为 `"0.00"`**。`mock-model.mjs:341-345`：
  ```js
  341|  const forced =
  342|    attempt === 1 && forceOverBudgetFirst && budgetCents !== null && originalCents !== null
  343|      ? ... : 0n;
  ```
  `forceOverBudgetFirst` **只在 `demo=presentation_over_budget` 时为 true**（`pipeline.mjs:371-374`）。
- 而包装材料（素色包装纸 / 纸质贺卡 / 棉质束带，`mock-model.mjs:333`、`350-355`）**从不参与任何金额运算**——文件中没有为材料定价的代码。
- 因此默认演示下：`新增费用 = 0.00`，`全量总费用 == 原估算`。**"含包装"在没有额外费用的前提下成立**。

**（c）校验器的能力边界**：`checker.mjs` 只能验证 `revised = original + additional` 这条**算术恒等式**，**无法验证 `estimated_total` 的构成里到底有没有包装**（`estimated_total` 只是一个金额字符串，没有分项字段；候选必填字段见 `checker.mjs:237-254` —— 11 个字段中**没有任何 cost breakdown**）。
**→ 【推断】"含包装"是声明性约定，不是被代码验证过的事实。真实价格是否含包装无法静态判定**（见 §9）。
