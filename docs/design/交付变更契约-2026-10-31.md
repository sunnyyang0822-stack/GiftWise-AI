# 11 月 1 日交付变更契约

状态：产品负责人已确认六项建议；以下是待实现的增量规范，不是已运行能力。实施前旧版契约仍描述旧系统，开发不得宣称新能力完成。新功能统一标记 contract_version=`giftwise-20261031-v2`；旧格式按下述兼容路径区分。

## 1. 六项决定与体验

1. 预算采用 0–1000 元双端滑条。PM 采用 50 元步长作为本次最小实现选择；这不是用户研究结果。附加选项为“不花钱的心意”“其他金额”“不确定”；只有“其他金额”展开自由填写，最大 10000 元。不确定不得直接提交。滑条初始值即使可见也不表示用户确认，需用户操作或明确确认区间。
2. 0 元合法，表示礼物本身不新增支出；不能将新购材料说成免费。生成方向优先已有材料、手写或陪伴；可行性未知如实说明。
3. AI 识别“不喜欢的东西”并说明依据；独立代码最终拦截，无法可靠识别要澄清。保留可选类别标签；删除手工填写字面词与未解析禁忌两个旧框。无需用户重填模型已识别的字面词，采用同页勾选确认；未确认项不能直接成为约束，也不能静默忽略用户原话。
4. 六档时间：明天/3–5 天/一周以内/一月以内/一季度以内/一年以内，映射 1/5/7/30/90/365 个可用准备天数。标签旁明确显示“按 N 天上限检查”，不推断绝对送达日期。底层继续接受 0–365 的整数，产品 UI 无自由填天数。
5. 账单列所选礼物及估价、包装风格与色调、贺卡、赠送方式、备注和校验状态。“礼物合计”只计所选礼物，不把三个候选相加；包装、贺卡、装饰、配送不计入该预算，也不报价；不等于免费。只给包装风格/色调，不新增购物清单或复杂制作教程。
6. 本轮改动纳入 11 月 1 日交付。上线/云部署/实付资源不在本授权内。所有“已完成”仍须经开发自测、独立验收、PM 复核。

保持三页三步：关系/场合/预算/时间 → 兴趣/风格 → 不喜欢/可选类别/补充说明。最后一页在必要时内嵌识别结果确认，不新增长表单。生成时有显式加载视图；不能跳过三方案选择直接生成最终账单。追求对象低压力表达；全任务最多一次自动业务修订；全界面中文。

## 2. 预算与请求

新版 intake 示例（其余既有字段保持）：

```json
{"contract_version":"giftwise-20261031-v2","budget_mode":"slider","budget_range":{"min":"100","max":"300"},"currency":"CNY","deadline_days":5,"dislikes":"不要香水","hard_exclusions":{"tags":[],"terms":[],"unresolved":[]},"additional_context":"希望表达感谢"}
```

- budget_mode 仅 slider/zero/other。区间两端必须为旧金额格式的非负十进制字符串（最多两位小数；不接受前导零、正号、空白、指数、NaN）。min/max 都必填，不接受 null；0≤min≤max≤10000。
- slider：两端≤1000，均为 50 元的整数倍；zero：两端数值均为 0；other：允许两位小数，仍须有序和在范围内。模式、区间、contract_version 缺失或未知均须明确拒绝，不静默修正。
- 服务端从 max 派生 budget_amount。新版浏览器不必提交 budget_amount；如同时提供，必须金额数值相等，否则 BUDGET_RANGE_MISMATCH，不能静默覆盖不一致输入。
- 规则请求保留 budget_amount 标量，新增可选 budget_range。带区间时校验两端格式/范围/顺序以及 max 与 budget_amount 一致；规则层不能只信任适配层。规则请求不需要 budget_mode（它是输入交互约束）。旧版无区间的标量请求仍可用，不假造用户提供过下限。旧 0、0.99 等预算按本轮用户决定放宽；其他旧非法输入继续拒绝。
- 候选 estimated_total 在新版只表示礼物本身估价。超过 max 报 OVER_BUDGET；低于 min 产生 BELOW_BUDGET_RANGE warning，仍可选择；等于任一端点通过。Python Decimal、JS 整数分比较，不能用浮点金额比较。
- 新增码固定：INVALID_BUDGET_RANGE（结构/缺端点/端点倒置/模式不符），BUDGET_RANGE_MISMATCH（标量与 max 不一致），BELOW_BUDGET_RANGE（警告）。金额类型/格式使用既有码 INVALID_TYPE/INVALID_AMOUNT，金额范围使用 LIMIT_EXCEEDED。同一路径只报最前一项：结构→类型/格式→范围→顺序→模式→标量一致性；多路径错误按 min、max、整体顺序收集。适配层路径 intake.*，规则路径 request.*，两端实现一致。
- 新版 dislikes 可省略为 ""，不可 null；最多 1000 Unicode 码点。只作为数据传入、不能覆盖 budget/deadline/facts/repair_count；原始明确类别仍按既有规则映射。
- deadline_days 继续为整数，不新增日期解析、时区换算或物流承诺。配置返回六档和明确 numeric 值，UI 不再维护第二份映射。

## 3. 排除项识别与确认（推荐前完成）

```text
填“不喜欢” → 填补充说明 → 点击生成 → 校验基本输入
→ 非空 dislikes：识别 → 校验模型输出 → 同页用户确认/澄清
→ 服务端合并已确认项、冻结请求 → 三候选 → 代码校验/最多一次修订
→ 选择合格候选 → 呈现复核 → 最终账单
```

空 dislikes 不调用识别器，不构造“AI 已识别”记录；仍保留用户手选类别。mock 与 dify 显式区分，缺真实能力必须报未配置，不能静默用 mock 代替。现在不花任何线上模型额度；真实识别及新版 Dify 端到端仍是待验证项，不能因进入交付范围而宣称完成。

识别信封（纯函数校验，示例仅虚构输入）：

```json
{"ai_exclusion_candidates":[{"id":"xc1","kind":"tag","tag":"fragrance","term":null,"source_span":"不要香水","confidence":"high","why":"原文明确提到香水","evidence":"user_text"}],"ai_unmapped_notes":[]}
```

- 信封只接受上述两键，候选最多 5 个；每项恰好包含示例八键。id 为 xc1–xc9 且唯一；kind=tag/term。tag 项从现有词表取值但不接受泛化的 other；term 项为 1–40 码点文字；与 kind 无关的 tag/term 必须为 null。
- source_span 非空、最多 1000 码点，为 dislikes 的精确连续子串。term 用 NFKC+casefold 校验是 span 子串，禁止纯标点。confidence=high/medium/low，不参与最终裁决。why 为≤200 码点纯文本，不渲染 HTML/Markdown/链接。evidence 固定 user_text。ai_unmapped_notes 最多 3 条，每项≤200 码点，不能用来自动增加约束。
- 信封严格 JSON ≤32768 UTF-8 字节；重复键、未知键（包括嵌套）、错误形状、超限、无锚定、非法标签/词任一出现，整包 needs_input，不采用其中“看起来正确”的条目。统一格式错误 AI_OUTPUT_INVALID，大小/数量/长度错误 AI_OUTPUT_LIMIT，依据错误 AI_OUTPUT_UNANCHORED；优先解析/结构→大小条数长度→依据。错误包含 code/path/message，中文 message。
- 非空 dislikes 但零候选、存在 unmapped notes、解析失败：INTAKE_CLARIFICATION_REQUIRED，阻止推荐，不静默丢掉。用户编辑原话后重分析；仅追加备注不能自动解除硬约束。
- 识别成功后逐条展示原文依据和理由，由用户确认；无默认全选。未全确认时保留 needs_input，提供修改原话/重新识别入口，不把“取消”悄悄解释成没有禁忌。确认只产生约束，不代表推荐校验通过。
- 锚定不证明语义正确；tag 也需要用户确认。不得把“已有香水”直接等同于不喜欢全部香氛，不保证识别覆盖所有表达。已知中文词子串误伤不在本轮修复。

API 增量（接入 Agent 唯一实现者）：

1. `POST /api/exclusions/analyze`：`{intake}`。返回 `{status,mode,analysis_id,candidates,errors}`；status=needs_confirmation/needs_input/error，mode=mock/dify。analysis_id 由服务端生成，不能由浏览器自拟；候选返回仅允许经校验的字段。
2. `POST /api/recommendations` 保留 `{intake,demo}`，新版有 dislikes 时另带 `exclusion_confirmation:{analysis_id,confirmed_ids}`。服务端从快照取结果，验证 ID 唯一/完整/归属/有效期，以及整个 intake 与分析时一致；输入变更须重分析。过期 10 分钟/不存在/内容不一致用 EXCLUSION_ANALYSIS_STALE，未完整确认或已无法识别用 INTAKE_CLARIFICATION_REQUIRED。TTL 清理、有界 200 条内存、重复相同确认返回同一个推荐运行，不重复生成；进程重启丢失明确提示。该快照 ID 不是身份认证，不宣称实现多用户权限系统。
3. `/api/intake/validate` 新版校验基本字段，非空 dislikes 缺确认时返回 needs_input（需识别/确认），不能把基本字段合法当作 ready-to-recommend。analyze 在服务端使用“基本字段校验”的内部路径，无循环依赖。
4. 用户选礼物仍只提交 `{recommendation_run_id,selected_candidate_id}`；demo 维持既有测试开关。禁止把排除项确认附加到这个事件，约束必须在推荐运行开始前冻结，模型不得改写。

AI 模块接口：`checkAiExclusions(aiJson, dislikes)` → `{status:"needs_confirmation"|"needs_input",candidates,errors}`，纯函数，不存状态、不联网。`recognizeExclusions({dislikes,mode,provider})` 是独立异步提供者：mock 用显式固定夹具（不能声称 AI 实测），dify 使用依赖注入 provider；未配置报能力缺失，不读密钥。纯校验与提供者分别测试。接入 Agent 负责真正调用服务与快照，工作流 Agent 只准备提供者输入输出和提示词。

## 4. 呈现与账单

- 新版 presentation 必须带 contract_version，新增 style:string；packaging 只需 color_palette:string[]（非空）。保留 card_text、giving_advice(timing/wording/relationship_cautions)、unknowns、currency、revised_estimated_preparation_days。结构规则由 checker 实现，style/palette/贺卡/话术全部参与明确禁忌扫描。
- 新版不接收 additional_cost、revised_estimated_total、packaging.materials/steps/material_tags。不要保留这些字段填 0；不要新增包装价格别名。违反新版字段规则用 PRESENTATION_INVALID。礼物估价只能来自服务端冻结候选，不能从呈现模型读一个更低价格。
- 服务端 recheck_summary 新版输出 `{contract_version,gift_estimated_total,budget_range,budget_amount,currency,available_days,revised_estimated_preparation_days,passed,business_data_verification}`。gift_estimated_total 取冻结候选 estimated_total；原无区间兼容路径 budget_range=null，不冒充用户范围。
- 礼物费用<=预算、完整准备时间<=可用天数、禁忌、必填字段全部复核。包装不计价不代表不查准备时间/文本禁忌；不虚构材质/成分已验证。旧版本仅旧分支读取或明确拒绝重新生成，不混入新版账单。
- 先三方案逐项比价/解释，用户选中后才生成/显示详细呈现及账单；每份账单只统计一个选中礼物。失败不能展示为已完成可执行账单；不擅自改选。推荐/呈现合计最多一次自动业务修订，识别/确认不消耗业务修订也不得自动重试模型。
- 推荐、识别、呈现三种等待均有中文加载状态、失败/超时恢复、禁重复提交、aria-live。不得显示无依据的百分比。浏览器实际验证窄屏、键盘、加载可见、数据保留与超时，而非静态推断。
