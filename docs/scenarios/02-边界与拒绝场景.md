# 边界与拒绝场景：4 个"最容易被答错"的用户输入

> 全部走**真实适配层 + 真实规则层**，0 次模型调用。复跑：`python scenarios/run_all.py`。
> 原始输出：`docs/scenarios/evidence/scenarios-raw.json` → `boundary`。

边界场景的价值在于：**产品能力通常不是被正常输入击穿的，而是被极端输入击穿的。**
下面 4 条都是真实用户真会说的话，不是构造出来的刁难。

---

## B01 极小预算："就意思一下，一块钱。"

**输入**：朋友、生日、预算 `1`、可用 3 天、无禁忌。

**真实输出**：

```
stage = validate
c1（手写贺卡 1.00）    passed=True
c2（便利店小零食 12.00）passed=False  OVER_BUDGET  candidates[1].estimated_total
c3（一小束鲜花 35.00）  passed=False  OVER_BUDGET  candidates[2].estimated_total
→ 可选集合 = {c1}   共 1 个
```

**结论**：**合法输入不会掉进"0 个方案"的坑**（我先前的假设不成立，据实更正）。
1 元手写卡正常通过，用户拿到 1 个可执行方案。

**但仍然是体验断层**：产品承诺"恰好 3 个方案"，这里只给 1 个，而且**不解释为什么**。
用户看到的是"只有 1 个方案"，而不是"另外 2 个超出了你 1 元的预算"。

**建议**：可选方案不足 3 个时给出**原因说明**，并考虑按剩余预算触发一次重新生成。

---

## B02 时间极紧："今天就是纪念日，我现在才想起来。"

**输入**：恋人、纪念日、预算 `300`、可用 **0** 天、确认喜欢咖啡与美食。

**真实输出**：

```
c1（亲手做的晚餐 0 天）  passed=True
c2（当日自提蛋糕 0 天）  passed=True
c3（定制纪念相册 3 天）  passed=False  PREPARATION_TOO_LONG  candidates[2].estimated_preparation_days
→ 可选集合 = {c1, c2}   共 2 个
```

**结论**：规则层对"今天就要"是**可用的** —— 只要候选里存在 0 天方案，就能给用户 2 个可执行选项。

**真正的风险在生成侧**：`available_days=0` 时能否拿到方案，**完全取决于模型是否愿意写
`estimated_preparation_days: 0`**。若模型习惯性填 1–2 天，**最急的用户会拿到 0 个方案**，
而规则层不会告诉他"把准备期改成 0 天就行"。
→ 这属于提示词/契约约束，**规则层无法补救**。建议在生成提示词里显式要求
"当 available_days=0 时，必须至少给出一个 0 天准备期方案"。

---

## B03 喜好与禁忌直接冲突："他特别喜欢咖啡，但任何吃的都别送。"

**输入**：朋友、生日、预算 `200`、可用 5 天、
`interests = ["coffee_food"]` 且 `interest_confidence = {"coffee_food":"confirmed"}`、
`hard_exclusions.tags = ["food"]`。

**真实输出**：

```
适配层：status = ready，无任何冲突提示        ← 关键：矛盾没有被指出
c1（手冲咖啡器具，tags=["other"]）      passed=True
c2（精品咖啡豆礼盒，tags=["food"]）      passed=False  FORBIDDEN_TAG  candidates[1].tags[0]
c3（咖啡风味甜点礼盒，tags=["food"]）    passed=False  FORBIDDEN_TAG  candidates[2].tags[0]
→ 可选集合 = {c1}   共 1 个
```

**结论**：**适配层不做"喜好 × 禁忌"的交叉检查**。矛盾不在输入层暴露，一路带到候选层，
被拒绝的是候选，用户拿到 1 个方案且不明白另外 2 个为什么没了。

**风险放大情形**：如果生成侧顺着"确认的兴趣"（`coffee_food` 是 **confirmed**，
这是最强的事实依据）产出三个食品类方案，用户会看到 **0 个方案**，
错误信息全是候选级的 —— **他无法判断是自己的输入矛盾，还是系统能力不足。**

**建议**：适配层增加 `INTAKE_PREFERENCE_CONFLICT`（或至少返回一条提醒），把矛盾前移到输入层，
并在前端提示"你同时说喜欢咖啡食品、又说不要任何食品，请确认"。

---

## B04 信息不足："帮我买个礼物吧。"

**输入**：关系 `unknown`、场合 `unknown`、预算 `null`、天数 `null`、无兴趣、无禁忌。

**真实输出**：

```
stage = intake
status = needs_input
候选数 = 0                 ← 不生成任何方案
模型调用 = 0               ← 不消耗额度
```

**结论**：**这是产品最值得骄傲的一条负向验证** —— 信息严重不足时，系统**追问而不是硬给方案**，
并且**在适配层就终止，不进入生成、不消耗模型调用**。
这与"禁止无依据推断"的产品原则一致：宁可少给，也不猜。

**建议**：把这条件写进演示脚本 —— 它是"独立规则校验"之外**最能体现产品克制**的证据。

---

## 四条边界场景合起来说明什么

| 边界 | 系统当前表现 | 需要补的 |
| --- | --- | --- |
| 极小预算 | 给 1 个方案（不是 0 个） | 说明原因 + 补位 |
| 0 天准备期 | 给 2 个方案 | 生成侧强制要求 0 天方案 |
| 喜好×禁忌冲突 | 给 1 个方案，矛盾不提示 | 适配层冲突检查 |
| 信息不足 | **追问，不生成（正确）** | 保持 |

**共同模式**：规则层**判得准**，但**"判完之后怎么办"没有设计** ——
方案不足 3 个时没有解释、没有补位；输入矛盾时没有前移提示。
这是从"规则正确"走到"体验正确"之间缺的那一层。
