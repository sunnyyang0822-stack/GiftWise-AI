> **目的不是挑刺**：规则层是本项目最扎实的部分，它拦得准、不连坐、可独立复跑。
> 本文件要找的是**它会误杀好方案、或漏放坏方案**的地方 —— 这些是真正会伤害用户体验的路径。
> 每条都有可复现用例与**真实规则层输出**，复跑：`python scenarios/lib/critique.py`。

> ⚠️ **本线不修改 `validator/**`** —— 发现的问题只写报告，由规则线决定是否修。

## Q8 🔴 否定式表述被误杀

**问题**：用户禁忌字面词为"酒"时，一个**明确写明"不含酒精/无酒"**的合规方案会被
`FORBIDDEN_TERM` 拒绝。规则层做的是**字面串匹配**，没有任何否定语义处理。

**复现**：`python scenarios/lib/critique.py`（Q8 段）

**真实输出**：

```
status=failed  all_passed=False
c1（无酒精饮品组合）passed=False
    FORBIDDEN_TERM  candidates[0].name
    FORBIDDEN_TERM  candidates[0].description
    FORBIDDEN_TERM  candidates[0].reason
    FORBIDDEN_TERM  candidates[0].inferences[0]
c2（通用马克杯）    passed=True
c3（中性办公摆件）  passed=True
```

**在实际场景中的触发面**：13 个场景里出现 **4 次**，全部是我按正常、负责任的写法写的方案：

| 场景 | 被误杀的方案 | 触发它的那句话 |
| --- | --- | --- |
| S01 | 单一产地挂耳咖啡礼盒（**无酒**） | 名称里的"无酒" |
| S03 | 冬季热饮粉与马克杯组合 | 描述里的"**不含酒精**" |
| S12 | 商务茶具与办公桌面摆件 | 描述里的"**不含酒类**" |
| S13 | 办公室绿植与素色陶盆 | 描述里的"**不含酒类**" |

**为什么严重**：
1. **惩罚正确行为**。模型越是主动声明"本方案不含禁忌项"，越容易被拒。
2. **后果在商务场景最刺眼**（S12）：被拒的 c1 是"最中性、最合规"的选项，
   而**明显有合规顾虑的 c3（带企业标识）却顺利通过**。
3. **它让规则对提示词变更极其脆弱**。当前真实模型走的是"完全避开该字"策略（见下），
   所以这条路径在 n=1 的真实运行里没被触发；但只要提示词要求模型
   "说明为何不含禁忌项"，**整批方案就会被拒光**。

**真实模型证据（本线未消耗任何额度获取）**：我把真实 Dify 运行
`v2-run1-demo`（真实 LLM，1514 tokens）的候选原文调出来核对 ——
三案（精品咖啡豆小礼盒 / 美食体验小份组合 / 咖啡主题实用小物）共 1309 字符，
**"巧克力"出现 0 次**（该次运行的禁忌词是"巧克力"；原文里出现的 38 次全在提示词与请求回显中）。
→ 模型的现有策略是**完全避词**，所以**没有**触发本缺陷。
**必须如实说明：这条误杀路径已经确定性复现，但是否会命中真实模型输出，本线无法证明（n=1，且那次模型恰好避词）。**

**建议修法（可组合）**：
1. 命中词前若出现 `不含 / 无 / 不要 / 忌 / 免 / 非 / 未含 / 不涉及` 等否定词，**不计命中**（最小改动）；
2. 把字面词检查**收窄到 `name` / `description`**，解释性字段改为提示而非判死（见 Q9）；
3. 明确承认字面匹配是**不完整兜底**，并在契约里写清"语义禁忌由生成侧负责，规则层只做字面兜底"。

## Q7 🔴 禁忌标签可绕过

**问题**：禁忌拦截只有两条路 —— 候选**自己声明的 `tags`**，和**字面串匹配**。两条都不做语义判断。
一个语义上属于酒精类的礼物，只要不打 `alcohol` 标签、且所有文本不出现用户给的字面词，就能通过。

**复现**：`python scenarios/lib/critique.py`（Q7 段）。

**真实输出**：

```
status=passed  all_passed=True
c1（通用马克杯）      passed=True
c2（精酿礼品组合）    passed=True   ← 语义属酒精类，标签 ["other"]，全部文本无“酒”字
c3（中性办公摆件）    passed=True
```

> 说明：本探针的上一版**被我自己污染**了（我在 `reason` 里写了"酒"字，导致它被
> `FORBIDDEN_TERM` 拒掉，看起来像是"拦住了"）。此处已把全部文本清干净后重测，
> **结论是拦不住**。这个自我更正一并留在这里，便于复核。

**为什么严重**：**用户明确说了"不要酒"，却可能被推荐并选中酒精类礼物。**
而且这条路径**不依赖任何恶意构造** —— 只要生成侧漏打一个标签，硬约束就失效。

**建议**：把类别判断与生成侧的标签**交叉验证**（例如名称/描述里出现已知酒类词表时强制要求
`alcohol` 标签，否则报"标签与文案不一致"）；或引入一次独立的语义复核。

## Q9 🟠 禁忌词扫描字段过宽

**问题**：`FORBIDDEN_TERM` 扫描 `name` / `description` / **`reason`** / **`inferences`** / **`unknowns`**。
后三个字段的职责恰恰是**解释候选为何合规、以及还有哪些未知**。结果：**候选越解释越容易被拒。**

**真实输出**：

```
status=failed
c1（通用保温杯，名称与描述完全干净）passed=False
    FORBIDDEN_TERM  candidates[0].reason      ← 仅因 reason 里为说明“本方案不涉及该类别”而提到该词
c2、c3 passed=True
```

**建议**：字面词检查收窄到 `name` / `description`；解释性字段命中时记入 `warnings` 而非直接判死
（规则层已有 `warnings` 通道）。

## Q5 🟠 关系枚举里没有"职场上司"

**问题**：产品定位把"职场上司"列为**第三优先级关系**，但 `workflow/labels.py` 的
10 个关系值里**没有任何值表示"上司"**。

**真实输出**：

```
relation_enum_count = 10
relation_enum = {friend:朋友, colleague:同事, partner:恋人, pursuit:追求对象, family:家人,
                 classmate:同学, mentor:老师/导师, client_partner:客户/合作伙伴,
                 other:其他, unknown:关系暂不确定}
含“上司/领导/老板/上级/主管”的值 = {}     ← 空
```

**为什么重要**：这不是文案问题，是**产品规则在代码里失去依据**。
前端无法提交语义正确的值，只能落到 `other`；任何按 `recipient_relation_id` 分流的产品逻辑
（优先级排序、语气、得体度约束、职场分寸）对"给上司送礼"**全部不生效**。
S13 场景完整演示了这个后果。

**需要产品负责人裁决**（二选一，属于**产品决策而非工程决策**）：
- 新增 `boss` / `supervisor` 值并同步标签表、契约、前端枚举；或
- 明确"上司"并入某个既有值的语义范围（例如 `mentor`），并在契约里写清并入理由与适用范围。

⚠️ 注意：`colleague`（同事）已被标注为**仅技术回归**、不对产品暴露，
所以**不能**用"同事"来承载上司。

## Q4 🟠 候选侧允许金额填 0，请求侧禁止 0

**问题**：请求侧 `budget_amount=0` 会被 `LIMIT_EXCEEDED` 拒绝；
但候选侧 `estimated_total="0"` **可以通过**（`0 <= budget`，不触发 `OVER_BUDGET`）。

**真实输出**：

```
status=passed   all_passed=True
c1（零元占位方案，estimated_total="0.00"）passed=True   ← 放行
c2 passed=True   c3 passed=True
```

**为什么重要**：契约要求"不把未知价格填零"，但这条约定**只靠模型自觉，规则层没有兜底**。
漏放的后果是用户可能看到一个"0 元方案"并选中它。
**建议**：候选侧对 `estimated_total=0` 明确处理 —— 要么拒绝，要么强制要求同时声明价格未估算并降级展示（不可作为可选方案）。

## Q3 🟡 喜好与禁忌冲突：适配层不提示

**问题**：用户同时勾选"喜欢咖啡与美食"和"禁止一切食品"时，适配层**不报冲突**，
request 正常产出（`status=ready`），冲突要到候选层才由 `FORBIDDEN_TAG` 逐条拒绝。

**真实输出**：

```
status=failed
c1（手冲咖啡器具）passed=True
c2（精品咖啡豆礼盒）passed=False  FORBIDDEN_TAG
c3（咖啡风味甜点礼盒）passed=False  PREPARATION_TOO_LONG + FORBIDDEN_TAG   ← 错误聚合为多条并列
```

**为什么重要**：被扣分的是候选，而错误在用户输入。
若模型顺着"确认兴趣"给出三个食品类方案，用户会看到 **0 个方案**，
且错误信息是候选级的 —— 他无法判断是自己的输入矛盾，还是系统能力不足。
**建议**：适配层增加 `INTAKE_PREFERENCE_CONFLICT`（或至少返回一条提醒），把矛盾前移到输入层。

## Q6 🟡 request 侧无字段白名单（但并非完全无检查）

**问题**：intake 侧有 11 字段白名单（未知字段报 `INTAKE_UNKNOWN_FIELD`）；
**request 侧没有白名单**，只有一层按值类型递归的扫描。

**真实输出（两种情形，此处更正我先前的假设 —— 并非"完全无检查"）**：

```
(a) 只注入字符串型未知字段（recipient_relation_id / unexpected_field / another_note）
    → status=passed   错误列表为空          ← 静默通过
(b) 注入对象型未知字段（facts）
    → status=needs_input   INVALID_TYPE request.facts
```

**为什么重要**：防护强度不对称。只要有人直接构造 `request_json`（其它服务、测试工具、
未来第二个前端），就能把未契约化的**字符串**字段带进规则层而不被察觉。
契约文档里"`recipient_relation_id` 由服务端产出"这条**没有代码层强制**。
**建议**：request 侧也加字段白名单（或至少把未知字段记入 `warnings`）。

## Q1 🟡 极小预算下可选方案退化

**问题**：预算取合法下限 1 元时，规则门把方案数从 3 压到 1。

**真实输出**：

```
status=failed
c1（手写贺卡 1.00）passed=True
c2（便利店小零食 12.00）passed=False  OVER_BUDGET
c3（一小束鲜花 35.00）passed=False  OVER_BUDGET
```

> ⚠️ **据实更正**：我先前的假设是"1 元预算 → 0 个方案（死路）"，**实测不成立** ——
> 只要候选里有 1 元方案，就还有 1 个可选。这里只报告实测结果。

**为什么仍然值得记**：产品承诺"恰好 3 个方案"。规则判断本身是对的（12 元确实超 1 元预算），
但**校验之后没有补位机制**：用户看到 1 个方案，且没有解释"为什么只有 1 个"。
**建议**：当可选方案不足 3 个时，明确告知原因（例如"其余 2 个方案超出预算"），
并考虑触发一次"按剩余预算重新生成"。

## Q2 ⚪ 0 天准备期的可用性依赖模型

**真实输出**：

```
status=failed
c1（亲手做的晚餐，0 天）passed=True
c2（当日自提蛋糕，0 天）passed=True
c3（定制纪念相册，3 天）passed=False  PREPARATION_TOO_LONG
```

**结论**：只要候选里存在 0 天方案，最急场景不会落入"无方案"。
**剩余风险不在规则层，而在生成侧**：若模型习惯性写 1–2 天准备期，
`deadline_days=0` 的用户会拿到 **0 个方案**。这属于提示词/契约约束，规则层无法补救。
**建议**：在生成侧提示词里显式要求"当 available_days=0 时，必须给出至少一个 0 天准备期的方案"。

## 六、复跑与边界说明

```bash
cd <仓库根>
python scenarios/lib/critique.py          # 打印 9 条探针的真实输出
cat docs/scenarios/evidence/critique-raw.json   # 机器可读原始输出
```

**边界说明（避免过度声称）**：
- 本文件只质疑**规则层与适配层**的表现，不评价生成质量 —— 本线 0 次模型调用。
- Q8 的误杀路径**已确定性复现**，但在真实模型输出上的触发率**未被证明**（现有真实运行 n=1 且模型避词）。
- Q7 的绕过路径**已复现**，但在真实模型输出上是否发生**未被证明**（同样 n=1）。
- 结论：这两条都应当**按"已知的确定性缺陷"处理**（因为它们一旦触发，后果是硬约束失效或正确方案被废），
  但**不应**在答辩中声称"真实模型已经踩中"。
