# 场景走查报告：13 个完整场景，从用户原话到"只放行合法方案"

> **本报告的全部判定由真实规则层 `validator/rules.py` 与真实适配层 `workflow/intake.py` 产出，
> 全流程 0 次模型调用，可离线复跑。** 复跑：`python scenarios/run_all.py`（原始输出落
> `docs/scenarios/evidence/scenarios-raw.json`）。
>
> **候选来源声明**：S02 的三案取自仓库既有产物（`workflow/examples/candidates.json`）；
> **其余 12 个场景的三案由本线按契约人工构造，不是模型产出** —— 这样做的目的是**刻意覆盖规则的每一条分支**，
> 因此本批的"拒绝率"**不代表真实模型产出的分布**（真实运行的对照见 S02 与
> `v2-run1-demo`：模型产出 0 违规）。

## 一、链路与判定口径

```
用户原话（四步）
   ↓  workflow/intake.py  adapt_intake()      ← 确定性映射，不经过模型
request_json（recipient_relation_id / budget_amount / available_days / hard_exclusions …）
   ↓  （真实产品链路此处由 Dify 生成三候选；本线用人工构造候选替代，且已声明）
candidates_json（恰好 3 个）
   ↓  validator/rules.py  validate()          ← 独立规则校验，纯函数
候选级判定：每个候选 passed = 该候选无任何错误
最终集合：只有 passed=True 的候选才进入用户可选集合
```

**规则层用的是"候选级"判定**：一个候选失败不影响其他候选；`all_passed` 只在三案全过时为真。

### S01 追求对象·刚认识·生日（不确定对方是否有好感）

**输入四步（用户原话）**
> 关系："我们是在读书会认识的，聊过几次，我还不知道她对我是什么感觉。"
> 场合："下周她生日。"
> 预算与时间："两百以内吧，就这两天。"
> 兴趣与禁忌："她好像挺喜欢看书的，也爱喝咖啡……但我不确定。**千万别送酒，也不要带酒字的。**"

> ⚠️ **追求对象场景合规性**：本场景**不假定**双方已有恋爱关系、不假定双向好感，
> 三条方案均按"低压力、可被理解为普通朋友往来"的取向设计。用户的 `recipient_relation` 是
> `pursuit`（追求对象），与 `partner`（恋人）**并列互斥**，未被合并。

**产出三案的定位差异**（不是三个同义词）

| 候选 | 定位 | 金额/准备期 |
| --- | --- | --- |
| c1 | **把选择权交给对方**（书店选购额度 + 不署名小卡） | 120 / 1 天 |
| c2 | **一个人安静使用的日常消耗品**（挂耳咖啡礼盒） | 160 / 2 天 |
| c3 | **一次轻量体验**（可自选体验券） | 180 / 1 天 |

**禁忌命中**：用户禁忌 = 类别 `alcohol` + 字面词"酒"。
**规则判定**：c1 通过、c3 通过、**c2 被拒**。

- c2 被拒的字段是 `candidates[1].name` 与 `candidates[1].description`，错误码 `FORBIDDEN_TERM`。
- c2 的名称是「单一产地挂耳咖啡礼盒（**无酒**）」——**因为它老老实实写明"无酒"而含"酒"字被拒**。
- ⚠️ **这是误杀，不是正确的拦截**。详见 `03-规则层产品级质疑.md` 的 **Q8**。

**选择后应该看到什么**：包装 / 配色 / 贺卡 / 赠送方式 —— **当前未实现**（四处全未实现）。

### S03 追求对象·几乎不了解·节日问候（含一个真禁忌命中 + 一个误杀）

**输入四步**
> 关系："朋友聚会上认识的，其实不太了解她。"
> 场合："过年。"
> 预算与时间："一百块以内，越快越好。"（1 天）
> 兴趣与禁忌："说不好她喜欢什么……**不要送酒。**"

**三案定位**：c1 居家热饮组合（通用消耗品、托人转交不刻意）／c2 桌面绿植（无香氛无食品）／
c3 节日限定红酒礼盒。

**规则判定**：只有 **c2 通过**。
- **c1 被拒 = 误杀**：说明文字写「**不含酒精**，托人转交也不会显得刻意」→ `FORBIDDEN_TERM`（description）。
  一个"明确不含酒精"的方案，因为声明自己不含酒精而被拒。
- **c3 被拒 = 正确**：`FORBIDDEN_TAG`（tags=`["alcohol"]`）+ `FORBIDDEN_TERM`（name 含"酒"、description 含"酒"）。

**这个场景最能说明问题**：用户说"不要酒"，系统**杀掉了那个声明无酒的方案，却需要标签和字面词两条同时命中才能杀掉真正含酒的方案**。
如果 c3 的生成方没有打 `alcohol` 标签、文案里也避开"酒"字，它会**顺利通过**（见 Q7 实测）。

### S13 职场上司·感谢（**枚举缺口演示**）

**输入四步**
> 关系："直属领导这一年挺照顾我。" → **前端提交时只能落到 `other`（其他）**

**这里暴露的第一个问题不是规则，而是契约**：`workflow/labels.py` 的 10 个关系值里
**没有"职场上司"**（`mentor` 是"老师/导师"，`client_partner` 是"客户/合作伙伴"）。

→ `recipient_relation_id` 只能是 `other`，于是**任何按关系分流的产品逻辑对"给上司送礼"都不生效**。

**规则判定**：c2、c3 通过；**c1 被拒 = 误杀**，`FORBIDDEN_TERM`（description 写「不含酒类与卡券」→ 含"酒"字）。

## 四、从 13 个场景里读出来的四件事

**1）独立校验确实在起作用，而且拦得很准。** 金额越界、准备期不足、币种不一致、
重复方案、自定义标签、编造事实依据 —— 六类问题各有一个场景被精确拦下，且**不连坐**（只拒违规的那一条）。
其中 `DUPLICATE_CANDIDATE_CONTENT` 与 `UNKNOWN_FACT_REF` 两条尤其有价值：
前者直接兑现"不能是三个同义词"，后者是"禁止无依据推断"的机器化。

**2）但同时存在一条稳定的误杀路径，触发面比预想的大。**
13 个场景中 **4 个（31%）**出现了误杀（S01 / S03 / S12 / S13），
4 条被拒候选里全是因为文案写了「**不含酒精 / 无酒精 / 不含酒类**」这类**否定式声明**。
→ 规则层没有否定语义处理，**惩罚的是主动声明合规的方案**。

**3）"刻意覆盖分支"的代价要说清楚。** 本批 13 个场景里有 11 个被至少拒掉一票，
只剩 1–2 个可选方案 —— 但这是**我故意种了违规**的结果，**不代表真实模型产出**。
真实证据是反过来的：官方样例三案全过；真实 Dify 运行（`v2-run1-demo`，1514 tokens）
模型产出的三案**0 违规**，且我把它的候选原文调出来核对过 —— 模型**主动避开了禁忌字面词**。
→ 所以准确的说法是：**规则门的拦截能力已被充分证明；误杀路径已经复现，但是否会在真实模型输出上触发，本线无法证明**
（n=1，且那次模型恰好走了"完全避词"策略）。这一点必须如实告诉评委。

**4）"选完之后"的四段在整条场景线里是空的。** 13 个场景全部走到"选择"为止。
产品定位要求"选择后才生成详细包装、配色、贺卡与赠送方式"——**这四段当前整体未实现**，
Web 侧仅有 mock 演示，Dify 侧未接线。这是场景完整度上**最大的缺口**，且它是产品定位的**后半段**，
不是可选项。详见 `05-发现的问题清单.md` 第 1 条。
