## 第 3 页 · 整体方案与选型理由

**标题**：整体方案：模型生成 + 独立校验 + 服务端可信状态

**页面要点**

- 三个关键设计决定：
  1. **生成与判定分离**：模型只负责"有依据的方向"；预算/币种/禁忌/必填/准备时间由**独立 Python 代码**判定。
  2. **用户选择在中间**：未选择前**不生成**任何详细包装/贺卡（避免一次性生成三份浪费且有诱导）。
  3. **状态在服务端**：浏览器只提交输入与选择，**不信任**前端传来的 `passed` 标记。
- 选型与理由（含替代方案与代价）：

| 技术 | 用途 | 选它的理由 | 代价/替代 |
| --- | --- | --- | --- |
| Python 3.12（**纯标准库**） | 确定性规则 | 零第三方依赖，评委可二次复验；规则可离线跑 | 需自己实现；已用 `re.ASCII`+NFKC 防全角绕过 |
| Dify Cloud 1.18.0 | 模型编排 + Code 节点 | 平台承担编排、节点调度与沙箱 | 沙箱能力需实测（已实测）；平台限制 = 供应商耦合 |
| Node.js（**零依赖**） | 中文页面 + 薄接入层 | 无需构建工具链，本地即可演示 | 无框架，UI 规模受限 |
| Docker | 可复现打包 | 便于交付 | **未构建**，只在赛题要求或确有需要时采用 |
| UCloud | 托管校验 API | 满足"可访问入口" | **未开通、未部署**；费用未确认 |

- 为什么**不**做：不做微服务、不上 K8s、不引数据库 —— 当前负载与状态量**没有证据**支撑这些复杂度（评分规则说"能解释取舍"，这就是取舍）。

**口播稿（约 38 秒）**

> "我们的核心判断是：模型可以给建议，但不能给自己打分。所以预算、禁忌、时间这些硬约束全部交给独立的 Python 代码，而且这份规则只有一份真源，同时喂给 Dify 的 Code 节点和本地 API。第二个决定是让用户在中途做选择，选完才生成包装和贺卡。第三个是把可信状态放在服务端。反过来，我们没有上微服务和 K8s，因为目前没有任何负载数据支持那种复杂度。"

## 第 6 页 · 工程化设计（复现、异常处理、可靠性、可观测性）

**标题**：工程化：复现、异常处理与可观测性

**页面要点 — 复现**

- **零第三方依赖**：`validator/`、`workflow/`、`deploy/` 只用 Python 标准库；`web/` 只用 Node 内置模块（`dependencies` 为空）→ 无需 `pip install` / `npm install`。
- 五条复现命令写进 `README.md`；生成物带 `sources_sha256` / `artifacts_sha256` 哈希清单，**哈希与实际文件逐一匹配**（无 STALE）。
- `/healthz` 返回规则源码哈希 → 可确认现场运行的**就是提交版本**。
- 提交材料含**版本快照/commit**（评分规则 1.4）。

**页面要点 — 异常处理**

| 异常 | 处理方式 | 状态 |
| --- | --- | --- |
| 模型输出非法 JSON | 判定为可修订 → 全局最多一次修订 → 仍失败则如实失败，**不标为通过** | **E** 离线/mock |
| 硬约束不满足（超预算/禁忌/时间） | 失败项**不可选**；可选项由 `selectable_candidate_ids` 决定 | **E** |
| 修订额度用尽 | 保留真实失败结果，提示额度已用尽 | **E** |
| 未选择就请求呈现 | `INVALID_SELECTION`，**不替用户选择** | **E** |
| 伪造/越界的候选或状态 | 服务端按运行 ID + 候选版本校验；不信任前端 `passed` | **E**（mock） |
| 工具调用失败 / 超时 | 中文提示、不重试风暴；**独立成文的异常处理说明尚未完成**（缺口 G-3） | **P** |
| Dify 草稿自动保存延迟 | 以服务端实读为准，不以界面显示为证据（WF-002 记录） | **E**（观测） |

**页面要点 — 可靠性与可观测性**

- 服务端持有：运行 ID、候选版本、两次校验输出、**全局修订计数**、错误码、调用计数。
- 成本字段缺数据记 `not_measured`，**不填 0**；模型调用次数记 `model_calls`。
- **缺口**：Dify 租户**未启用 trace 采集**（`status: not_collected`）→ **无平台级调用轨迹**；可观测性验收项尚未收编（G-2）。

**口播稿（约 38 秒）**

> "工程化上有两点值得说。第一是复现：我们整个项目没有第三方依赖，Python 只用标准库，前端只用 Node 内置模块，评委拿到的仓库直接就能跑，而且生成物带哈希清单，健康检查会返回规则源码的哈希，可以确认现场跑的就是提交的那一版。第二是异常处理：模型输出的 JSON 坏掉、超预算、禁忌、未选择就请求呈现，这些路径我们都实测过，原则是失败就是失败，不会伪装成通过。同时我也要说明一个缺口：Dify 租户没有开启 trace 采集，所以我们拿不到平台级的调用轨迹。"

## 第 7 页 · 成本、性能与取舍

**标题**：成本、性能与取舍

**页面要点 — 真实数据（有就是有，没有就是没有）**

| 项 | 实测值 | 说明 |
| --- | --- | --- |
| 模型调用次数 | **0** | 全程未调用模型（无授权，OPEN-5） |

| 端到端业务延迟 | **无实测** | 探针耗时 0.079s / 0.094s / 0.462s 为**无模型探针**抖动值，**不可当业务延迟** |
| 调用成本 | **`not_measured`** | 无计费即无费率依据，**缺数据记未知，不填 0** |
| 本地测试耗时 | 322 项 0.163s；39 项 0.126s | 固定快照、离线 |
| 云资源消耗 | **无** | 未部署、未开通、未付费 |

**页面要点 — 成本结构（估算，不等于实测）**

- 主要潜在成本 = **模型调用**（Dify 平台配额 + 供应商 token）；其次是**云主机**（若赛题强制部署）。
- 结构性省钱设计：**确定性规则不消耗 token**；未选择前**不生成**三份详细包装（省掉大部分输出 token）；全局**最多一次**修订（防止失败重试放大成本）。
- 瓶颈判断：真正的不确定性在**模型输出质量与延迟**，而不是规则层（规则层是纯本地毫秒级）。

**页面要点 — 取舍**

| 取舍 | 选择 | 理由 |
| --- | --- | --- |
| 自建编排 vs Dify | 用 Dify | 省下编排与调度工程量；代价是平台耦合与沙箱限制 |
| 微服务 vs 单体 | 单机单体 | 无负载证据支持微服务 |
| K8s vs 直接容器 | 暂不引入 | 无伸缩需求证据；赛题是否强制**待核实** |
| 实时商品数据 vs 估算 | 明确标注为估算 | **没有真实数据源**，不虚构价格/库存/物流 |

**口播稿（约 37 秒）**

> "成本这一页我尽量只讲有数据支撑的：模型调用是零次，token 是零，因为供应商还没有授权。业务延迟和调用成本我们没有实测数据，所以记成'未测量'，而不是填零。结构上我们做了省钱的设计：规则不花 token，选之前不生成三份详细方案，修订全局只有一次。真正的瓶颈会是模型质量和延迟，不是规则层。"
