## 第 3 页 · 整体方案与选型理由

**标题**：整体方案：模型生成 + 独立校验 + 服务端可信状态

**页面要点**

- 三个关键设计决定：
  1. **生成与判定分离**：模型只负责"有依据的方向"；预算/币种/禁忌/必填/准备时间由**独立 Python 代码**判定（规则层共 **19 个错误码**）。
  2. **用户选择在中间**：未选择前**不生成**任何详细包装/贺卡。
  3. **状态在服务端**：浏览器只提交输入与选择，**不信任**前端传来的 `passed` 标记。
- 选型与理由（含替代方案与代价）：

| 技术 | 用途 | 选它的理由 | 代价/替代 |
| --- | --- | --- | --- |
| Python 3.12（**纯标准库**） | 确定性规则 | 零第三方依赖，评委可二次复验；容器内**逐字节一致** | 需自己实现；已用 `re.ASCII`+NFKC 防全角绕过 |
| Dify Cloud 1.18.0 | 模型编排 + Code 节点 | 平台承担编排、节点调度与沙箱；**已发布并创建版本** | 平台耦合；**ELSE 分支无运行证据**；**trace 不可用** |
| DeepSeek 模型节点 | N2 生成 / N5 修订 | **真实调用已跑通**（累计 13 次 / 38,326 tokens） | **用户自备额度；单价未核实** |
| Node.js（**零依赖**） | 中文页面 + 薄接入层 | 无需构建工具链，本地即可演示 | 无框架；前端**已过 100 项真实浏览器验收 / 0 失败**（残余仅真实用户可用性验证）；parity 仅**样例级** |
| Docker（**本机实测 14 项**） | 可复现打包 | 178 MB／169.676 MiB；冷构建 3.662 s；**14 项通过** | **未推 registry、未上云；单机基线≠生产容量**；**镜像已于 2026-10-31 01:13:59 重建并复核通过**（`submission-20261101` = `latest`；`/healthz` 规则哈希与本机一致、半开正文 10.02 s 返 408 并关闭、40 并发日志 0 粘连、`/metrics` 默认 404） |

- 为什么**不**做：不做微服务、不上 K8s、不引数据库 —— **云部署从未发生**，当前无任何容量证据支撑这些复杂度。

**口播稿（约 38 秒）**

> "核心判断是：模型可以给建议，但不能给自己打分，所以硬约束全部交给独立 Python 代码，这份规则只有一份真源，同时喂给 Dify 的 Code 节点、本地 API 和容器。第二个决定是让用户在中途做选择。第三个是把可信状态放在服务端。容器我们只做了本机实测与可复现打包，明确没有上云、没有 K8s——本机容器数据是单机基线，不是生产容量结论。"
