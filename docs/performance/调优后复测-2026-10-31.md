## 3. 改了什么（file:line + 前后代码）

### 3.1 定位：HTTP 服务在哪里被创建

```
$ grep -n 'ThreadingHTTPServer|request_queue_size|^class |serve_forever' deploy/server.py
15:from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer
52:class Handler(BaseHTTPRequestHandler):
153:    server = ThreadingHTTPServer((host, port), Handler)      <- 改动前：直接用标准库类
156:    server.serve_forever()
```

**改动前没有任何自定义 Server 类**，`main()`（`deploy/server.py:153`）直接实例化标准库的
`http.server.ThreadingHTTPServer`，因此继承 `socketserver.TCPServer.request_queue_size` 的默认值。

### 3.2 当前值 vs 实际可用值

| 项 | 值 | 取证 |
| --- | --- | --- |
| `socketserver.TCPServer.request_queue_size` | **5** | `python -c "import socketserver; print(socketserver.TCPServer.request_queue_size)"` |
| `http.server.ThreadingHTTPServer.request_queue_size`（继承值） | **5** | 同上 |
| `deploy/server.py` 里 `main()` 实际使用的类 | `http.server.ThreadingHTTPServer` | 改动前自检 |
| 容器内 `/proc/sys/net/core/somaxconn` | **4096** | `MSYS_NO_PATHCONV=1 docker exec <c> cat /proc/sys/net/core/somaxconn` |
| 容器内 `/proc/sys/net/ipv4/tcp_max_syn_backlog` | **512** | 同上 |
| `listen()` 的真实调用点 | `TCPServer.server_activate()` → `self.socket.listen(self.request_queue_size)` | `inspect.getsource` |

→ **内核给得起 4096，进程只要 5。** 这就是主报告 §6 定位到的瓶颈。

### 3.4 为什么是 512（不拍脑袋的四条理由）

1. **实测最优值中的最大值**：性能线单变量对照只测过 **5 / 128 / 512**，512 这一档在 c=100 与 c=200 上同时最好。
   **比 512 更大的值没有任何实测支持，因此不取（不猜）。**
2. **不超过内核上限**：Linux 实际 accept 队列 = `min(request_queue_size, somaxconn)`；
   512 < 4096，所以这个值会被**完整采纳**，不会被内核静默截断。
3. **与 SYN 队列对齐**：同一容器内 `tcp_max_syn_backlog = 512`，512 让连接建立的两段队列（半连接/accept）尺寸一致。
4. **内存有界**：线程模型是一连接一线程（实测 1,000 并发 = 989 线程峰值、约 27 KB/连接）；
   512 条排队连接最坏约 **14 MiB**，远低于实测余量（1,000 条并发半开只多吃 27 MiB）。

**"那为什么不取 128 甚至更小？"** —— 因为 **128 的 p50 更好，但没有把问题真正解决**：
性能线测到 `128`（日志开）在 c=200 是 `p50 123 ms / p95 1,092 ms / 48 个错误`，
而 `512` 是 `p50 162 ms / p95 194 ms / 0 错误`。
即 **128 的 p50 反而更低（123 < 162），但错误没清零、p95 还在 1 秒以上**——
说明 512 换来的不是"p50 更好看"，而是**把尾部和错误真正清掉**（复测实测：调优后 >500 ms 样本 = 0）。
⚠️ 这两次测量之间夹着"日志开关"这个变量，**所以这是提示，不是严格单变量证明**（详见 §5.8 末）。

### 3.5 日志持锁写：**我没有动，这是有意的**

主报告 §6.5「建议 2」提出"日志不要每请求同步持锁写 stdout"。**本次保留原样**，理由：

1. **任务是条件授权**：「只有在你能证明『并发 40 请求日志 0 行粘连』仍然成立时才可以动；
   若做不到，保留原样并在报告里说明」。而 **N-4 是已经修好的旧缺陷，绝不能改回去**——
   `deploy/server.py:27-34` 的 `_LOG_LOCK` + 一次 `write()` 写完整行，正是 N-4 的修复点本身。
2. **我无法给出"保证"，只能给出"这一次没复现"**。`sys.stdout.write()` 在 `PYTHONUNBUFFERED=1` 下
   依赖 CPython 缓冲层的实现细节（单次 `write(2)` 且长度 ≤ `PIPE_BUF` 才原子），
   这是**未文档化的行为**，而这个仓库已经因为同类"应该没问题"栽过一次（N-4 本身）。
   用一个未文档化的保证去替换一个显式的锁，风险与收益不对称。
3. **本次验收仍把 N-4 当回归项逐条复测**（§4 d40/d60），并**额外把并发从 40 提到 60**（N-4 的原始复现口径）。

**代价我量化出来了**（性能线原始单变量数据，同为 backlog=128、本机直跑）：
日志开 802 无错 rps / 48 错误 ↔ 日志关 1,073 无错 rps / 4 错误。
即**在高并发下关掉每请求同步日志还能再快约 25–34%**。这是一块**仍然留在桌子上的收益**，
建议由 PM 单独派一条线用「异步日志（`logging` + `QueueHandler`）」或「反向代理记访问日志、服务端默认静音」
的方式做，并**自带一次 N-4 回归**。本次不顺手改，是因为那是**另一个改动**，不是本任务的最小改动。

### 5.5 ⚠️ 反直觉点专章：p50 从 11 ms 涨到 138 ms，**不是变慢**

**先看事实**：同一份改动，**c=100 的 p50 恶化 12.6 倍、c=200 恶化 18.5 倍**，
同时**错误从 243/978 个降到 0**。如果只报"吞吐 +36%、错误归零"，就是在**隐瞒一半事实**。

**为什么不是变慢——两件事同时发生：**

**(1) 基线是拿错误换延迟。** backlog=5 时内核 accept 队列最多排 5 条，
排不进去的连接被丢弃/重置（客户端看到 `RemoteDisconnected`）。
基线因此把 **2.02%（c=100）/ 4.08%（c=200）** 的请求**直接扔掉**：
被扔掉的请求不是"快"，是**没有结果**。

**(2) 更关键：基线让"被接纳的那批"几乎不排队。** 队列深度上限只有 5，
所以**被服务的那批请求几乎立刻被处理**，中位数就落在 ~10–15 ms。
把 backlog 提到 512 之后，多出来的连接不再被扔掉，而是**排队**，
排队时间进入延迟 → 中位数升到 138–287 ms。

**→ 所以正确的说法是：调优把「丢弃 + 超长尾」换成了「人人排队约 0.14–0.29 秒」。**

**最有力的证据是"尾部整体消失"**（不只是 p95 改善）：

| | >1,000 ms 的样本 | 占比 |
| --- | --- | --- |
| BEFORE c=100 | 849 / 12,000 | **7.08%** |
| BEFORE c=200 | 3,310 / 24,000 | **13.79%** |
| AFTER c=100 | **0** / 12,000 | 0% |
| AFTER c=200 | **0** / 24,000 | 0% |

调优后**所有档位 0 个样本超过 500 ms**（`tail.over_500ms = 0`），
而基线 c=100 有 7.08%、c=200 有 13.79% 的样本超过 1,000 ms。
**"两轮 p95 都在 1 s 以上、且 7–14% 的请求要等 1 秒以上"这句话，就是基线真实的样子。**

**公平比较（同一错误率下比吞吐）**：

- BEFORE 只有在 **c ≤ 10** 时才做到零错误 → 它的**零错误能力上限 = 354.0 无错 rps**。
- AFTER 到 **c = 200** 仍零错误 → c=50 达 **725.2 无错 rps**。
- **零错误承载能力：354 → 725 rps（+105%）**，与性能线本机直跑测得的 +107% 相互印证。

### 5.6 对主报告 §4 那条「必须点破的陷阱」的一处更正（我只报告，不改它）

主报告 §4 写：

> 基线在 c=200 拒掉了 631/12,000 个连接（**5.3%**），**被拒请求的延迟不进延迟分布**。

**核对 `bench/bench.py` 源码后，这个说法与工具实现不符**：

```python
# bench/bench.py
163|            except Exception as e:            # 失败分支
173|                errs.append(f"{k}: {msg}")
174|            finally:
180|                    conn = None
181|            lat.append((time.perf_counter() - t0) * 1000.0)   # <-- 在 try/except/finally 之外
```

`lat.append(...)`（`bench/bench.py:181`）位于 `try/except/finally` **之外**，
因此**每一次尝试（含失败）都会进入延迟样本**——被拒请求的延迟**是进分布**的。

**实测也反驳该机制**：基线 c=200 的 `>1000 ms` 样本有 **1,410（A1）/1,900（A2）** 个，
远多于错误数 **449 / 529**——说明超长尾里**大部分其实是"成功了但排了很久"的请求**，不是失败。

**但主报告那条注释的结论仍然成立**（基线的"p50 更低"不是更快，而是拿丢弃换来的）——
**只是机制写错了**：p50 的差距**不是**"把慢样本排除掉了"
（2–4% 的样本移动不了中位数，这是数学），**而是** §5.5(2)：基线让被接纳的那部分几乎不排队。
