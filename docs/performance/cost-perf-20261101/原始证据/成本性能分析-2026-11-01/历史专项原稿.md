## 1. API 调用成本

### 1.1 一次成功交互的调用次数分解

【实测·代码口径】一次**成功**的完整交互 = **4 次 LLM 调用 + 1 次生图**：
`intake_parse`（解析）→ `recommend`（推荐）→ `style_direction`（风格方向）→ `present`（呈现）共 4 次 LLM；生图 1 次，**不进 JSONL 账本**。

出处 `web/server/pipeline.mjs:638–644` 原文：

> 一次**成功**的完整交互＝recommend 1 次 + style_direction 1 次 + present 1 次（repair_count=0）＝**3 次**模型调用 + 1 次生图；首轮输出不合格触发一次修复时才是 5 次。生图**没有** JSONL 账本（recordRealCall 只在 `web/server/llm/`），它的硬证据是 media-store 新增 task+asset 与响应里的 `generation` 块。

同一文件 `:644` 另写明「解析调用同样写服务端账本（`kind=intake_parse`）」⇒ 3 + 解析 = **4 次**。⚠️ 触发一次自动修复时是 **5 次 LLM**，所以账本里同一 kind 会相邻出现多次。

### 1.2 单次端到端轨迹（时间戳互锁，可复核）

账本 `at` 字段语义是**调用完成时刻**：`web/server/llm/ledger.mjs:70` 取 `new Date().toISOString()`，其调用点在 `web/server/llm/provider.mjs:163–172`，位于 `await this.live.chat(...)` **之后**，且传入 `elapsed_ms`。

取 2026-10-31T14:26–14:27Z 这一组**唯一能与 media-store 互相咬合**的 4 条记录 + 1 个生图 task：

| 步骤 | kind | 完成时刻 (UTC) | 耗时 ms | total_tokens | prompt / completion / reasoning |
|---|---|---|---|---|---|
| ① 解析 | `intake_parse` | 14:26:28.774 | 3,237 | 3,147 | 2,749 / 398 / 284 |
| ② 推荐 | `recommend` | 14:27:12.292 | **43,495** | **10,583** | 4,041 / 6,542 / 5,577 |
| ③ 风格方向 | `style_direction` | 14:27:15.229 | 2,902 | 712 | 286 / 426 / 313 |
| ④ 呈现 | `present` | 14:27:24.125 | 7,634 | 3,346 | 2,457 / 889 / 379 |
| ⑤ 生图 | （无账本） | 14:27:24.134 → 14:27:34.985 | 10,835 | 15,552 `output_tokens` | — |
| **合计** | 4 LLM | — | **57,268** | **17,788** | — |

**互锁证据**：③→④ 间隔 1.262 s（用户在候选间做选择，说明该链路含一个人工步骤）；④ 完成后 **9 ms** 生图 task 即建立（`media-store/tasks/e7864a65b338….json` `created_at=2026-10-31T14:27:24.134Z`，而 `present` 完成于 `.125Z`）。墙钟 = 解析开始 14:26:25.537 → 图就绪 14:27:34.985 = **69.448 s**；`LLM 57.268 + 生图 10.835 = 68.103 s`，差 1.345 s 恰为三步之间的空档（0.023 + 0.035 + 1.262 + 0.009），**闭合**。

⚠️ **口径提醒**：同一份账本在 14:26:1x–14:26:3x 有若干**并发/交织**行（例：`present@14:26:35.789` 反推的开始时刻早于其上一条 `recommend@14:26:22.152` 的结束时刻，单会话串行模型下不可解释），说明当时有**多个客户端交错压测**。因此**跨行任意求和不可信**，本文只采用上表这一条自洽链。

### 1.4 失败与重试的真实代价

【实测】5 条失败记录（`.tmp/fe/ledger-feparse.jsonl` 3 条 + `.tmp/llm-calls/degradation-ledger.jsonl` 2 条），全部 `code=LLM_REQUEST_FAILED`、`attempts=3`、`elapsed_ms=767–786`、`usage=null`、`base_url_host=127.0.0.1:9`（故意指向黑洞端口）。

⇒ 失败**不产生 token 记账**；3 次尝试（`web/server/llm/transport.mjs:94–96` 默认 `maxRetries=2`、硬上限 3）在「连不上」场景只花 **≈0.77–0.79 s**，不是延迟灾难。重试仅对 `RETRYABLE_STATUS = {408,409,425,429,500,502,503,504}`（`llm/errors.mjs:43`）生效；**2xx 但结构不符不重试**（`transport.mjs:143` 注释原文「重试也只会再花一次额度」）——正确的省钱设计。

## 4. 主要瓶颈及依据

**结论：瓶颈是第 ② 步「推荐 `recommend`」，且大概率而非可能——三条独立口径同时指向它。**

1. **耗时占比**：单次互锁轨迹 43,495 / 57,268 = **75.9%**；全样本中位数口径 39,909 / 58,755 = **67.9%**。其余三步合计不足 1/3。
2. **token 占比**：中位 9,409，是解析(3,153) 的 3.0 倍、呈现(3,862) 的 2.4 倍、风格方向(893) 的 **10.5 倍**；其 prompt+completion = 116,889，占主账本总量 **51.1%**。
3. **方差最大**：21,033–66,770 ms（**3.2 倍**；风格方向 2.6 倍、呈现 1.8 倍）⇒ 推荐是「体验不可预测」的唯一主因。
4. **在关键路径上且串行**：`style_direction` 消费候选、`present` 消费用户选定候选 ⇒ 推荐不结束后续无法开始，端到端墙钟 ≈ 推荐耗时 + 余量（§1.2 已闭合验证）。
5. **钱也在这里**：其 reasoning 57,006 tokens 占全部 reasoning 的 **71.9%**，即「贵」的部分几乎全在推荐步。
6. **次瓶颈是生图**（10.8–30.5 s，`size:'2K'` 每次固定 15,552 output tokens），但它在用户选择**之后**才发生，可与人的思考时间重叠，属「**可隐藏的延迟**」。

## 5. 优化方向（可执行）

1. **解析缓存：已实现，但未取得命中实测。** `web/server/llm/intake-parse.mjs:710–712`（`CACHE_LIMIT=50`、`CACHE_TTL_MS=10 min`）、`:871–876`（命中即 `return`，**不再发模型请求**）、`:968–976`（超限淘汰最旧）。命中 ⇒ 0 token / ≈0 ms。⚠️【未测·命中】我查到的 5 份解析产物（`.tmp/ev1-parse.json`、`ev1b-parse.json`、`ev2-parse.json`、`final-case1-parse.json`、`ev-parse.json`）**全部 `parse.cache.used=false`** ⇒ **未观察到一次真实命中，故不写「实测命中 ⇒ 0 成本」**。可测方案：同一文本 10 min 内连发两次 `POST /api/intake/parse`，看第二次响应 `parse.cache.used=true` 且账本行数不增。
2. **幂等重放：已实现，同样未取得命中实测。** `web/server/pipeline.mjs:249–250`（`getRunByRecommendationKey` 命中即直接返回整份 report）⇒ 同 `recommendation key` 的重复请求 **0 次模型调用**。推荐步占 75.9% 耗时，这是**最省钱的杠杆**，建议演示前先把命中率做到可演示。
3. **库优先命中：机制已有，但当前只省采集、没省模型。** 【实测】`.tmp/ev1-rec.json`：`catalog.accounting = {candidates:3, library_hits:3, fallback_hits:0, degraded:0, scrape_calls:0, scrape_total_elapsed_ms:0}`——命中 3/3 时采集耗时为 0；**但同一响应 `call_counts.recommend = 1`，仍然调了模型**。可执行改进：当 `library_hits == candidates` 且请求指纹命中历史时，直接复用历史 `recommend` 结果（复用第 2 条机制），把「库命中」从省采集升级为**省模型**。
4. **简单步骤换便宜模型。** 解析 + 风格方向合计只占 token 的 **23.4%**（3,153+893）/ 耗时的 **13.8%**，其中风格方向 prompt 仅 286–310 tokens（中位 304）、输出中位 596 tokens，属「短进短出」，可换更小更便宜的模型。**推荐与呈现不要换**：reasoning 占比 82.0% / 61.7%，思考量本身就是质量来源。
5. **生图分辨率档位与参考图策略。** `web/server/media/seedream.mjs:129` 目前硬编码 `size:'2K'`（产物 2304×1728、660–832 KB、每次 15,552 output tokens）。实测**带参考图 19.6–30.5 s vs 不带 10.8 s** ⇒ 按需决定是否带参考图（`media/plan.mjs:15` 已限制 ≤2 张），「仅示意」场景降档，可同时省时间、省 token、省磁盘（0.76 MB/张）。
6. **并发 / 预取。** （a）解析结束即可**并行**预热商品检索（一次采集实测 5,950–9,482 ms，见 `.tmp/e2e-rec.json`、`.tmp/final-rec.json` 的 `catalog.accounting.scrape_total_elapsed_ms`），当前为串行。（b）`style_direction` 与 `present` 之间隔着**用户选择**（实测 1.262 s），可在选择期间预取该候选的包装图，把 10.8–30.5 s 的生图藏进人的操作间隙。（c）`PRESENTATION_WAIT_MS` 当前是**阻塞等图**（默认 30 s），而实测最大 30,452 ms **已越线** ⇒ 改异步 + 前端轮询（`config.mjs:395–396` 注释已把「前端补轮询」列为后续可选项），既消超时风险又降感知延迟。
7. **不要优化的地方（有实测支撑的取舍）**：失败重试只花 ≈0.78 s 且失败不计 token（§1.4）；`/api/catalog` 读侧 22 ms；确定性规则层 0 token（`docs/performance/成本模型.md:46–53`，p50 0.216 ms）⇒ 把判定下沉到规则层已是正确的工程选择。

### 5.1 新增优化：获授权电商 API＋缓存（2026-11-01，规划未接入）

**目标是改善商品身份与价格依据，减少对浏览器会话和网页解析的依赖。当前尚未取得本项目接口权限、未接入或开展对比测试，不声称更快、更便宜或已解决库存问题。**

- 商品通道优先评估京东联盟／淘宝联盟等官方授权接口，先核验GiftWise适用的应用类型、接口权限、商品池、展示用途、图片复用和缓存规则；不是注册后就能查询全站商品。先选一家实际可获批且适配礼物品类的平台，暂不指定哪家最容易。
- 服务端保管凭证和签名；统一平台商品ID、可用时的SKU、标题／图片／链接、价格条件、币种、观察时间与失效信息。区分普通价、活动价、券后／会员条件，不把API价当所有用户结算价，不凭相似标题强行绑定商品。
- 采用许可范围内缓存、限流和有上限重试；授权失效、超时或无商品时保留基本礼物建议，资料为可选增强。网络重试不重置全任务最多一次自动业务修订，用户选择前不生成最终包装图。
- OpenCLI保留作可选公开灵感／参考内容通道。它的浏览器路径需要Chrome会话与扩展，本身不等于获得平台商品数据授权；也不能据此断言换成Playwright就更稳定。API失败不自动回退到被停用的电商浏览器采集。
- 用同一组虚构场景比较商品信息覆盖、身份错绑、价格条件完整性、缓存过期比例、取数延迟和实际调用费用；模型耗时另计。没有实测前不承诺QPS、费用或加速比例，不增加全网比价、下单支付和库存／送达保证。

接入顺序：资格与用途核验 → 单平台只读查询／详情 → 数据绑定与缓存／降级 → 对比验收。当前仅完成方案与公开文档核对。本文历史采样和原始证据保留原时点，不作为新API已可用的证明。
