# 性能一页（答辩用）

> 用途：直接搬进答辩 PPT「成本、性能与工程化分析」那一页。
> 每条数字后面都跟了**评委可以现场敲的命令**，这是这一页的价值所在——
> 不是"我们很快"，而是"你可以自己量一遍"。

---

## 建议的 5 个数字（按说服力排序）

### ① 规则引擎不是瓶颈：**0.216 ms**

单次校验 p50 = **0.216 ms**，单线程 **4,394 次/秒**；

> ⚠️ **口径注**：本节是 **2,000 次迭代**基线；`docs/architecture.md` 与 `ADR-001/003` 里的 **0.166 ms** 是 **n=200、batch 100** 的另一口径 —— **两者都对，引用时不要混用、也不要并排比较**。
校验 100 万次方案约 **228 核·秒**，且消耗 **0 个 token**。

```bash
python bench/bench.py rules --iterations 2000
```

**为什么这个数字重要**：它证明架构选择是对的——把"裁决"下沉到确定性规则层，
**把判定从延迟与成本的关键路径上摘掉了**。

---

### ② 瓶颈是一个标准库默认值：**`listen backlog = 5`**

交付实现用 `ThreadingHTTPServer`，它的 `request_queue_size` 是 Python 标准库默认值 **5**；
而容器 `net.core.somaxconn` 是 **4096**——**完全没被用上**。

```bash
python -c "import http.server; print(http.server.ThreadingHTTPServer.request_queue_size)"
```

**为什么这个数字重要**：这是一个**一行改动、成倍收益**的发现，而且它是被实测定位出来的，
不是照抄最佳实践。

---

### ③ 调优前后：**566 → 1,169 rps（+107%），错误 631 → 0**

| 指标（c=100 / c=200） | 交付原样 | backlog 512 + 异步日志 |
| --- | --- | --- |
| 无错吞吐 | 566 rps | **1,169 rps（+107%）** |
| p95（c=200） | 1,039 ms | **194 ms（5.4×）** |
| 连接错误（c=200） | **631 个** | **0 个** |

```bash
# 基线
GIFTWISE_BIND=127.0.0.1 GIFTWISE_PORT=18902 python -m deploy.server &   # ⚠️ 必须先起服务，否则 connection refused
python -u bench/bench.py ramp --url http://127.0.0.1:18902 --container __none__ --levels 100,200 --requests 60
# 调优后（bench/server_variant.py，同一份 handler）
BENCH_PORT=18906 BENCH_BACKLOG=512 BENCH_NOLOG=1 python bench/server_variant.py &
python -u bench/bench.py ramp --url http://127.0.0.1:18906 --container __none__ --levels 100,200 --requests 60
```

**答辩时主动说明这个反问**（显得我们是量过而不是抄的）：
> 基线的 p50 更低（6.6 ms vs 162 ms），**但这不是它更快，而是它把 5.3% 的连接直接拒掉了**——
> 被拒请求的延迟不进延迟分布。**基线是拿错误换延迟。**

---

### ④ 并发承载上限：**1,000 条连接 / 只多吃 27 MiB / 未观察 OOM**

| 半开连接 | 建立成功 | 线程峰值 | 内存增量 | 408 时刻 |
| --- | --- | --- | --- | --- |
| 200 | 200/200 | 201 | +4.07 MiB | 10.75 s |
| 500 | 500/500 | 501 | +14.0 MiB | 11.01 s |
| **1,000** | **1,000/1,000** | **989** | **+27.0 MiB** | 10.82 s |

```bash
python bench/hold_probe.py --url http://127.0.0.1:18901 --connections 1000 --hold 16 --container gwbench
```

**为什么这个数字重要**：它填上了我们自己审计里的那句
「I-2 高并发上限：**只验到 9 条连接**，未压测 OOM 行为，不推测」——
现在是 **1,000 条**，且**未观察到 OOM**。
同时它**在 1,000 并发下再次验证了 I-2 修复**：所有半开连接都在 ~10.8 秒被 408 关闭，
即**恶意半开连接的暴露窗口有上界（10 秒）**。

---

### ⑤ 真正的成本在模型：**4.44 s vs 0.216 ms（22,000 倍）**

一次完整生成耗时 **4.91 s**，其中 LLM 节点 **4.44 s**；规则校验只占 **0.216 ms（0.004%）**。

出处：`workflow/evidence/WF-003-2026-10-30.md:1158`（4.91 s / 1,487 tokens）、`:1302`（N2 4.43872 s）。

**为什么这个数字重要**：它同时解释了**成本**和**延迟**——
两者都来自模型调用，因此**优化校验器毫无意义**，
而把判定放进规则层则同时省了钱和延迟。

## 附：如果评委追问"能不能上云"

**如实回答**（不要说"已具备"）：

> 这个服务是**无状态单进程**，同一镜像可以直接起多副本，`/healthz` 可以直接当探针，
> 冷启动 **0.668 s**——**结构上适合水平扩展**。
> 但我们**没有采购任何云资源**，所以：**没有编排、没有多副本、没有自动扩缩、没有负载均衡**，
> **多副本的一致性也没有实测过**。
> 而且 `/metrics` 目前未鉴权，**不具备公网暴露条件**，需要前置反向代理与鉴权。
> 我们能拿出的是一份**在本机 127.0.0.1 上可复现的容量边界**，不是一份云上压测报告。
