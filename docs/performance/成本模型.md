## 2. 两条路径的 token 成本

GiftWise 的判定链路刻意分成两层：

| 路径 | 判定内容 | 模型调用 | token 成本 |
| --- | --- | --- | --- |
| **确定性规则层**（`validator/rules.py`） | 越界、禁忌、预算、天数、重复、币种、ID 合法性、必需字段…（19 类错误码） | **0** | **0 tokens** |
| **模型层**（Dify `deepseek-v4-flash`） | 三个方案的生成与修订 | 1 次/生成 | 1,487 tokens（实测） |

**这条分层是成本结构上最重要的一件事：**
所有"能不能放行"的判定都在规则层完成，**不消耗任何 token**，也不受模型不确定性影响。
模型只负责**生成内容**，不负责**裁决**。因此：
- 规则层可以无限次重跑而**成本恒为 0**（46 探针 / 329 单测 / 边界 45 项的全部执行，token 成本 = 0）；
- 模型的输出即使不合规，也会被规则层拦下，**不需要靠模型自己保证合规**。

## 3. 单机计算成本（可以直接算，因为不涉及未核实的单价）

规则层的实测性能（`bench/runs/rules-median-20261031T011836.json`，**2,000 次迭代**，
样本 `mock-默认三候选`：请求 550 B + 候选 1,349 B）：

| 指标 | 值 |
| --- | --- |
| min | 0.203 ms |
| p50 | **0.216 ms** |
| mean | 0.228 ms |
| p90 | 0.257 ms |
| p95 | 0.290 ms |
| p99 | 0.390 ms |
| max | 0.869 ms |
| 单线程吞吐 | **≈ 4,394 次/秒** |

由此得到**与单价无关**的容量结论：

| 量 | 计算 | 结果 |
| --- | --- | --- |
| 校验 100 万次方案的 CPU 时间 | 1,000,000 ÷ 4,394 | **≈ 228 核·秒**（约 3.8 核·分钟） |
| 校验 100 万次方案的模型成本 | — | **0 tokens** |

对比：**一次模型生成耗时 4.91 秒**（演示真跑，`workflow/evidence/WF-003-2026-10-30.md:1158`），
其中 LLM 节点占 **4.44 秒**（`:1302`）。

> **规则引擎比模型快约 22,000 倍**（0.2 ms vs 4,440 ms）。
> 结论：**优化校验器对用户体验没有意义，时间和钱都花在模型调用上。**
> 这也解释了为什么把判定下沉到规则层是正确的工程选择——它把"裁决"从延迟与成本的关键路径上摘掉了。

## 5. 成本结构结论（可用于答辩）

1. **可变成本 100% 来自模型调用**；确定性规则层的模型成本恒为 0，且可无限次重跑。
2. **成本的可预测性来自分层**：一次生成的 token 消耗由提示词与输出结构决定，
   实测 807–4,064 区间，中心约 1,487–3,413。
3. **延迟与成本同源**：一次生成 4.91 s，其中 90% 是 LLM 节点；校验器只占 0.004%。
4. **未核实的部分照实留白**：供应商单价、云端实例单价、出口带宽费用均**未核实**，
   因此本模型**不给出"每用户成本"的单一数字**，只给出可代入的函数。
