## 4. 本次复核**不能**证明的事（口径声明）

1. **没有真实 Dify 调用**：全程 `mock` 模式，因此这次验证的是"接入层自身逻辑与模型无关的部分"，
   **不是**端到端与真实模型的联调结果。

   `workflow/intake.py`+`validator/rules.py` 在给定样例上的**语义等价**，
   不等于两者在所有输入上等价（样例外的分歧仍可能存在）。
3. **没有性能数据**：本次未测吞吐、延迟、内存；`web/` 的性能数字仍为空白。
4. **没有浏览器层面的验证**：未在真实浏览器中检查界面渲染、交互与可访问性；
   `web/public/` 的视觉正确性**未复核**。
5. **没有安全审计**：仅确认了无硬编码密钥与运行记录不含密钥；未做注入、越权、限流等专项测试。

以上 1–5 项在答辩材料中**不得**被表述为已验证。

**本报告在 2026-10-30 写的"55 组样例 / 0 处语义差异"结论本身没错，但当时漏了一句关键限定；

### 1. 该结论只覆盖"样例内"，且**结构上不可能覆盖数值范围校验**

PM 拆开 `.tmp/web-parity/fixtures.json` 实测：

| 实测事实 | 值 |
| --- | --- |
| 顶层 `request_json` | **唯一一个**，固定合法值（`budget_amount:"200.00"`、`available_days:2`） |
| `intake_cases` / `candidate_batches` / `broken_batches` | 27 / 24 / 4 条，**只变候选侧** |
| 全文件含 `budget_amount` 或 `available_days` 的节点数 | **0** |

→ **请求侧数值范围校验在 parity 里永远不可能被触发**。所以"0 处语义差异"与越界行为**毫无关系**；
它不是"这次恰好没覆盖"，而是**样例设计上的结构性盲区**。
（比对器本身没问题：`parity-check.mjs:103-111` 比对 `all_passed` / `errors` / `candidate_results`。）

### 2. 越界输入两侧**确实不一致**（同输入 A/B，15 组中 11 组不同）

| 类别 | 组数 | 现象 |
| --- | --- | --- |
| **A 类：真缺口** | 5 | `(10000,366)`、`(10000.01,365)`、`(10000.01,366)`、`(10001,365)`、`(10001,366)` —— **JS 侧完全放行（`all_passed=true`）** |
| **B 类：同一根因的另一表现** | 6 | 两侧都拒绝但层级不同：Python 走请求层（`needs_input` ＋ `LIMIT_EXCEEDED@request.*`），JS 由候选层拒绝（`OVER_BUDGET`）。**修好根因后这 6 组会一起消失，不是第二个缺陷** |

**根因**：`web/server/checker.mjs` 全文出现 `10000` **0 次**（mtime 20:52，早于规则线 23:11 的范围校验落地）。
**反向核验通过**：全网格下候选层**从未**出现 `LIMIT_EXCEEDED` → 范围**没有**下沉到与候选侧共用的
`_amount`/`_days`，**候选侧未被误伤**。
