# GiftWise AI｜分支与拉取请求（PR）规范

- 制定：PM Agent｜2026-10-30
- 起因：此前所有工作堆在**一个分支**、**一个永远挂着的草稿 PR**（#12）上，`main` 落后 7 个提交——
  等于"没有分线、没有合并决定"。
- **修订（2026-10-30 晚）**：曾一次性建 8 条 `task/*` **空分线**，经产品负责人指出后**全部删除**。
  空分支不产生任何价值，反而让仓库显得杂乱：**分支只应在该批次有真实改动时才创建**。
  现行模型改为**按批次开 PR**。

## 1. 分支模型（现行）

| 分支 | 角色 | 说明 |
| --- | --- | --- |
| `main` | **交付主干** | 评委看到的版本即此。只接受 PR 合并，不直接提交 |
| `release/2026-11-01-submission` | **集成分支** | 多 Agent 共用的工作目录所在分支，各线改动先落在这里 |
| `batch/<批次名>` | **批次分支** | **有真实改动时才创建**；一个批次 = 一个 PR = 一个合并决定 |

**不使用长期存在的空分支。**

## 3. PR 合并条件（缺一不可）

1. **交付物已提交**，且报告里给出**真实命令与原始输出**——不接受"应该可以""理论上没问题"。
2. **PM 独立复核通过**（`AGENTS.md`：测试验收独立复核，不能以开发声明代替证据），
   且回归保持绿色（本机探针、单元测试）。
3. **口径诚实**：未做到的一律写"未核实 / 未发生"，不得把设计当已实现。
4. PR 描述写清三件事：**改了什么、证据在哪、还剩什么没做到**。

**不允许"挂着不管"**：每个 PR 最终必须落到 **已合并** 或 **已关闭**（关闭必须写明原因）。

## 4. 共用工作区带来的显式让步（如实说明）

本项目的多个 Agent **共用同一个工作目录**，无法让每条线各自 `git checkout` 到自己的分支——
那会让其他 Agent 正在写的文件凭空消失。因此实际流程是：

1. 各线先把改动提交到集成分支 `release/2026-11-01-submission`；
2. PM 在该批次完成后，从集成分支的交付提交上开出 `batch/<批次名>` 分支，以 `main` 为基开 PR；
3. PM 复核后**合并**，或**关闭并写明原因**。

因为 `main` 只在合并时前进，这样开出的 PR 恰好只包含**该批次新增的改动**，评审范围清晰。
这是对"共用工作区"这一约束的**显式让步**，不是省略流程。

## 5. 给各 Agent 的强制约束（必须写进每个 Agent 的提示词）

```
⚠️ 禁止任何 git 分支操作：不要执行 git checkout / switch / branch / merge / rebase / push。
多个 Agent 共用同一个工作目录，切换分支会让其他 Agent 正在写的文件消失。
你只需把改动留在工作区；确需提交时只许 `git add <你自己的文件>` + `git commit`，
提交、开 PR、合并一律由 PM 统一处理。
```
