# GiftWise AI｜分支与拉取请求（PR）规范

- 制定：PM Agent｜2026-10-30
- 起因：此前所有工作堆在**一个分支**、**一个永远挂着的草稿 PR**（#12）上，`main` 落后 7 个提交，
  等于"没有分线、没有合并决定"。本规范修正这一点。

## 1. 分支模型

| 分支 | 角色 | 说明 |
| --- | --- | --- |
| `main` | **交付主干** | 评委看到的版本即此。只接受 PR 合并，不直接提交 |
| `release/2026-11-01-submission` | **集成分支** | 多 Agent 共用的工作目录所在分支，各线提交先落在这里 |
| `task/<线>-<主题>` | **任务分线** | 一条线一个分支，对应一个 PR 与一个 Issue |

## 3. PR 合并条件（缺一不可）

1. **交付物已提交**，且报告里给出**真实命令与原始输出**——不接受"应该可以""理论上没问题"。
2. **PM 独立复核通过**（`AGENTS.md`：测试验收独立复核，不能以开发声明代替证据），
   且回归保持绿色（本机探针、单元测试）。
3. **口径诚实**：未做到的一律写"未核实 / 未发生"，不得把设计当已实现。
4. PR 描述写清三件事：**改了什么、证据在哪、还剩什么没做到**。

**不允许"挂着不管"**：每个 PR 最终必须落到 **已合并** 或 **已关闭**（关闭必须写明原因）。

## 4. 共用工作区带来的显式让步（如实说明）

本项目的多个 Agent **共用同一个工作目录**，无法让每条线各自 `git checkout` 到自己的分支——
那会让其他 Agent 正在写的文件凭空消失。因此实际流程是：

1. 各线先把工作提交到集成分支 `release/2026-11-01-submission`；
2. PM 随即把该线的提交**指针**推成 `task/<线>` 分支，并以 `main` 为基开 PR；
3. PM 复核后**合并**，或**关闭并写明原因**。

因为 `main` 只在合并时前进，这样开出的 PR 恰好只包含**该线新增的改动**，评审范围清晰。
这是对"共用工作区"这一约束的**显式让步**，不是省略流程。
