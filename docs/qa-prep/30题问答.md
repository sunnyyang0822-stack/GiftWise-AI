## 一、数字类

### 1. 329、39、45 是什么关系？加起来是多少？

- **一句话**：四个**互不包含**的集合——329（`discover -s tests`）/ 275（stage_b）/ 39（stage_c）/ 45（boundary），合计 688 条 Python 用例；我们从不把它们相加当成一个数字宣传。
- **30 秒**：`tests/` 与 `tests/acceptance/` 及其三个子目录**刻意都不放 `__init__.py`**，所以 `python -m unittest discover -s tests` 不会递归进去。证据是我实测的：`discover -s tests -v` 的输出里 `acceptance` / `stage_b` / `stage_c` **各出现 0 次**（⚠️ **别拿 `boundary` 当判据**——会命中一条用例方法名 `test_decimal_boundary_ignores_context_rounding`，那是 `tests/test_validator.py` 里的用例，不是目录）。四个集合测四件不同的事：329 是规则层契约与 fixture（含 313–319 号新增的请求侧范围用例）；275 是阶段 B 的评审基线回归；39 是阶段 C 的端到端验收；45 是越界边界（`budget ∈ [1,10000]`、`days ≤ 365`）。
- **当场演示**：
  ```bash
  python -m unittest discover -s tests -v 2>&1 | grep -c stage_b    # → 0
  python -m unittest discover -s tests/acceptance/boundary           # → Ran 45 tests / OK
  ```

### 2. token 到底多少？为什么有两个口径？

- **一句话**：**主批次 10 次 / 34,127 tokens；累计 13 次 / 38,326 tokens**——两个数都对，差别是"哪一批"。
- **30 秒**：主批次是那条正式跑通的端到端测试链，10 次调用、34,127 tokens；累计包含为调通它额外重跑的 3 次（13−10），所以更大。我们**刻意保留双口径**：只报小的会被质疑"次数对不上"，只报大的会掩盖主批次基线。单位价格与单任务成本写**未核实**——那必须来自真实账单，未提供前不得用估算值冒充实测。
- **当场演示**：`docs/acceptance-criteria.md` 第 13 节第 3 条；Dify 控制台「上次运行」。

### 3. 探针 46、接入层 40、冒烟 59、parity 74——不重不漏吗？

- **一句话**：四个数字测**四个不同层**，本来就不该相等。
- **30 秒**：层次是「纯函数 → JS 模块 → HTTP 契约 → 跨语言等价」。46 探针是**本机 Python 直接调 `validate()`** 的离线用例（含 P0–P3 优先级、零模型调用）；40 是 **JS 侧模块级**单测（路径在 `web/tests/access-layer.test.mjs`，**不在 `tests/` 下**）；59 是**真的起 HTTP 服务**打状态码矩阵与 413/408 边界；74 是**同一输入喂 Python 与 JS 再比对**。parity 是唯一的跨语言层，最贵也最有价值。
- **当场演示**：`node web/tools/parity-check.mjs`（自己会打印 74 组的构成）。

### 4. parity 74 组全一致，是不是说明 JS 和 Python 完全等价？

- **一句话**：**只能说"这 74 组样例上语义一致"**——而且我们主动指出还剩 1 条极端值分歧。
- **30 秒**：样例级等价 ≠ 全输入等价（这是归纳问题，不是偷懒）。验证指南的**独立 14 条网格**上我们抓到：`days=10**20`，Python 判 `needs_input / LIMIT_EXCEEDED`（请求层越界），JS 判 `error / INVALID_JSON`（解析/表示层）。**两侧都拒绝**，只是错误码与层级不同。这条登记为"未消解"，我们不写成"全一致"。
- **当场演示**：`python tools/verify_all.py --only js_range_parity` → `1/14` + 分歧清单。

### 5. 规则层 19 个错误码怎么来的？

- **一句话**：19 个是从 `validator/rules.py` 逐一清点得到的（18 个原有 + 1 个新增），对外材料已从 18 更新为 19。
- **30 秒**：分族——请求侧（结构/类型/范围/格式）、候选侧（预算/数量/重复/引用）、契约开关（`PURSUIT_CONTRACT_NOT_READY`）等。规则层是**唯一真值来源**，前端 JS 只是复刻它的判定（74 组 parity 钉住）。
- **当场演示**：`grep -oE '"[A-Z_]{4,}"' validator/rules.py | sort -u | wc -l`
- ⚠️ 本线**未逐一清点**，只核对了"18→19"这处对外声明的变更；评委深挖清单时现场跑上面这条命令。

### 6. 178 MB、169.36 MiB 还是 169.676 MiB？为什么有三个数？

- **一句话**：`docker images` 的 **178 MB** 是十进制（10⁶）；换算成二进制（2²⁰）后，**构建时基线 = 169.36 MiB**、**交付镜像（2026-10-31 01:13:59 重建版）= 169.676 MiB**——**口径是旧的，数字也是旧的**。
- **30 秒**：`docker inspect` 的真值：构建时基线 **177,582,258 B ＝ 169.36 MiB**（2026-10-30）；交付镜像 **177,918,474 B ＝ 169.676 MiB**（`submission-20261101` = `latest` = `d9a4a35763ee`，Created **2026-10-31 01:13:59**）。所以 **169.36 MiB 是重建前的值**，台上若只说它，和 `docker inspect` 当场对不上。同页还有：**冷构建有两个合法值**——10-30 基线 **1.720 s**、01:13:59 重建版 **3,662 ms**（`docker build --no-cache`）；启动到 `/healthz` 200 用 0.750–0.939 s、常驻内存 14.45–17.08 MiB。
- **⚠️ 必须主动说的限定**：两次冷构建**是否同口径未确认**，所以**不得**宣称"变慢了"，只并列两个时点值。
- **当场演示**：`docker inspect giftwise-validator:submission-20261101 --format '{{.Id}} {{.Created}} {{.Size}}'`
- **必答限定**：这些是**单机本机构建基线**，**不是生产容量结论**。

## 三、技术选型类

### 13. 为什么规则层不用模型？

- **一句话**：**"能不能送"是可判定的，不该交给概率模型**；模型负责"想出好方案"，规则层负责"守住红线"。
- **30 秒**：禁忌词/标签、预算上限、天数上限、恰好三方案、引用完整性（`fact_refs` 必须存在于输入）、重复检测——都有确定答案。用模型判会引入不确定性、不可复现、不可审计。我们用纯 Python（`validator/rules.py`）实现，**零第三方依赖**；并且它**同时被 JS 复刻**用于浏览器侧即时反馈，74 组 parity 保证两侧一致。
- **当场演示**：`validator/rules.py`；`node web/tools/parity-check.mjs`。

### 14. 为什么不上 K8s？云原生 15 分不要了？

- **一句话**：**15 分要，但"装了 K8s"不等于云原生**；单机容器化 + 可交付部署脚本 + 自证接口是这条规模下的正确形态。
- **30 秒**：云原生的核心是**可构建、可交付、可观测、最小权限、可复现**——这五点我们都有实测（多阶段构建、非 root uid 10001、`/healthz` 返回规则指纹、镜像内无密钥与 `.git/tests/docs`、冷构建 1.720 s）。K8s/k3s、多副本、弹性伸缩、资源调度、分布式状态**明确登记为未做**，因为要做就得先有云主机，而边界不允许采购。**写"未做"比装一个空壳编排更诚实，也更经得起追问。**
- **当场演示**：B1 组 4 条 + `deploy/Dockerfile`。

### 15. 为什么是单进程单机？没有数据库？

- **一句话**：单进程是**刻意的形态选择**——校验是纯函数、无状态、无 IO；没有数据库是因为**不需要持久化任何东西**。
- **30 秒**：`/validate` = 输入 JSON → 输出判定。没有账号、没有会话、没有业务数据落库（隐私上这也是优点：**不收集、不存储**）。采集层是可选可观测入口，默认不暴露。
- **必须主动补**：因此**并发能力只有单机基线**（内存 14.45–17.08 MiB、40 并发日志 0 粘连是我们测过的）；**云端资源消耗与真实跨机延迟均未测量**，不能外推成生产容量结论。
- **当场演示**：`docs/qa-prep/tools/verify_delivery_claims.py`（第 3 项就是 40 并发）。

### 16. 同一套规则为什么在 Python 和 JS 里写两遍？

- **一句话**：**两侧要的东西不同**——Python 是判据真值（Agent 链路必须信它），JS 是浏览器侧**即时反馈**（不能让用户等一次往返）。
- **30 秒**：代价是"双实现会漂移"。我们**用 74 组 parity 夹具把漂移钉住**，而且**刚抓到一个真实的结构性盲区**：原夹具里 request 是**固定的合法值**，越界输入**永远触发不到请求侧校验**——我们补了 **15 组越界网格 + 2 组格式优先**，现在 74 组 0 差异；仅剩 1 条极端值（`days=10**20`）分类不同，已登记。
- **当场演示**：`node web/tools/parity-check.mjs`（会打印"请求侧越界与格式 17 条"）。
- **这一问最能体现工程能力，建议主动引出。**

### 17. 为什么用 Dify 而不是自己写编排？

- **一句话**：**编排不是我们的创新点，规则校验才是**；用平台换时间，把工程量投在"可验证"上。
- **30 秒**：Dify 提供可视编排、模型接入、版本管理（已发布并创建版本 v2）。代价也如实登记：**平台级 trace 不可用**（该租户未开 tracing），节点级输出只能从界面「上次运行」取，**没有平台侧调用链**；`N4` ELSE 分支从未触发；无自然触发的 `OVER_BUDGET` 证据。
- **当场演示**：Dify 编排页 + PPT 骨架 B2 组。

### 18. 为什么健康检查不能代表服务可用？

- **一句话**：**`/healthz` 只证明"进程活着 + 规则版本对不对"，它不碰请求路径**——我们实测过半开正文缺陷骗过健康检查。
- **30 秒**：`Content-Length: 100` 只发 5 字节时，旧镜像**25 秒零响应且不关闭**、占住工作线程，而 `/healthz` 依然 200。所以自证脚本**不看 `/healthz`，直接打半开正文并计时**（现在 10.02 s → 408 + 关闭）。
- **当场演示**：`verify_delivery_claims.py` 第 2 项。

## 四、对抗类

### 19. 这不就是个 prompt 包装吗？

- **一句话**：**不是**——prompt 之外有三层可验证工程：确定性规则层、跨语言等价、容器自证。
- **30 秒**：如果只是 prompt，就不需要 19 个错误码、329 条规则单测、275 条评审基线回归、45 条越界边界、74 组跨语言 parity、以及一个**带时钟预算的半开连接防护**——这些不是 prompt 能给的。而且我们**故意把"没做到"的 15 条列出来**：包装品不会这么写。
- **当场演示**：`python tools/verify_all.py`（一条命令跑完全部对外声明）。

### 20. 和直接问 DeepSeek / ChatGPT 有什么区别？

- **一句话**：**通用模型给你"看起来不错"的建议；我们给"不会踩雷"的建议，而且能证明为什么。**
- **30 秒**：四个差别——①**关系优先级显式建模**：恋人/追求对象最高，其次朋友，再次职场上司与亲戚家人，且**追求关系不假定已有恋爱关系或双向好感**（通用模型最容易在这里冒犯）；②**禁忌与预算的确定性校验**，不通过就不给你选；③**三方案必须全部过闸**，用户只在通过的里面选；④**规则真值可复核**：`/healthz` 返回规则指纹，你说不清跑的是哪版规则，我们能。
- **当场演示**：`validator/rules.py`（关系优先级 + 契约开关）。

### 21. 你的校验会不会误杀好方案？

- **一句话**：**这正是我们最在意的，所以我们专门做了"反向核验"**——证明修复没有误伤候选侧。
- **30 秒**：补请求侧范围校验时，我们做了**反向断言**：候选侧 `estimated_total="0"`、`preparation_days=0` **仍然通过**（"方案可以估 0 元"这类合理情形不被误杀）。逻辑上两者语义不同、不共用判定分支：**请求侧范围校验的是用户填的预算/天数**（1–10000 / ≤365），**候选侧校验的是方案自身报价/工期**（可为 0）。45 条越界边界套件里就有这条反向用例。
- **当场演示**：`python -m unittest discover -s tests/acceptance/boundary` → 45 条 OK。

### 22. 如果模型给的三个方案都很差呢？

- **一句话**：**会被闸拦下来，用户看不到**——三方案必须**全部**通过校验才呈现；并规定全局**最多一次自动业务修订**。
- **30 秒**：闸门检查完备性（恰好三个）、预算上限、天数上限、禁忌词与标签、引用完整性、重复检测；任一不过不进入选择环节。修订是"改一次再校验"，超出即返回明确错误码而不是无限重试。
- **诚实补一句**：修订路径**修复之后的真实运行时证据我们没拿到**（B2 组第 8 条），属"明确未完成"。

### 23. 用户乱填 / 恶意输入怎么办？`days=10**20` 呢？

- **一句话**：**请求侧有范围校验 + 体积上限 + 严格 JSON 解析**；`10**20` 这种极端值两侧**都会拒绝**。
- **30 秒**：`budget_amount ∈ [1,10000]`、`available_days ≤ 365`；正文 32 KB 上限（32768 通过 / 32769 拒绝）、文本 1000/1001 字符、列表 20/21 项、重复键、`NaN`/`Infinity`、单引号、尾随垃圾——探针里有大量这类用例。`days=10**20`：Python 判 `needs_input / LIMIT_EXCEEDED`（请求层越界），JS 判 `error / INVALID_JSON`（解析/表示层）——**都拒绝，只是分类不同**，如实登记为未消解。
- **当场演示**：`python tools/verify_all.py --only js_range_parity`；`tests/acceptance/boundary`。

### 24. 只给一次自动修订，够吗？

- **一句话**：**是刻意的**——一次修订是"防止无限烧额度"的工程约束，不是能力上限。
- **30 秒**：①模型额度是稀缺资源（累计只用 13 次 / 38,326 tokens，要给现场留量）；②无限重试会让延迟不可控（实测 N5 约 3 s、端到端 5.2–8.9 s）；③**给用户明确的失败原因比默默重试 5 次更好**。超出一次修订时返回明确错误码，不假装成功。
- **当场演示**：`validator/rules.py` 的修订计数与错误码。
