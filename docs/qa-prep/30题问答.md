## 一、产品与选择

### 1. GiftWise 到底帮用户做什么？

**短答：帮助用户挑选礼物：送什么、为什么适合、如何比较和选择。**

展开：把已知关系与偏好整理清楚，给出三个不同方向及理由，再结合预算、禁忌和准备时间比较。用户决定选哪个，选定后才补赠送建议。核心产出是有依据的选择，不是自动修订的展示。

依据：Issue #1 产品主张补充；讲稿 S1/S3。

### 2. 为什么优先面向青年？

**短答：这是产品的目标人群判断，尚不是已验证的需求频率统计。**

展开：我们优先考虑青年在关系分寸和礼物选择上的困惑，先服务恋人、追求对象，再服务朋友。没有真实用户研究就不说这类人“最高频使用”或已经愿意付费。

依据：Issue #1 用户与动机；真实用户验证待核实。

### 3. 你们最重要的场景是什么？

**短答：恋人和追求对象并列最高优先级，朋友其次。**

展开：恋人可以结合共同经历；追求对象要避免关系假设；朋友更重视具体兴趣和日常使用。本轮不新增虚构用户或市场数据，既有示例不当作用户访谈。同事生日只作技术回归，不在产品主展示中出现。

依据：Issue #1；虚构场景文档。

### 4. 追求对象和恋人有什么不同？

**短答：追求对象不代表已有恋爱关系或双向好感。**

展开：适配理由、关系提醒和贺卡不能暗示对方心意，不能承诺关系进展。低压力表达是要求，不等于已证明礼物会降低压力。仍需当前版本输出与用户验证支持。

依据：Issue #1；QA 待验证关系文案。

### 5. 为什么是三个方案？

**短答：让用户有可比较的不同方向，同时限制需要阅读的内容。**

展开：候选要有可解释的差异，不能只是同一种礼物换名字。三个是当前产品选择，没有对比试验就不称为最优数量。用户仍可能都不喜欢，可以补充信息重新考虑。

依据：Issue #1 核心体验；真实体验收益待验证。

### 6. 用户具体怎么比较？

**短答：看理由是否贴合已知信息，再比较估价、准备时间、关系表达和未知风险。**

展开：比较实际候选的适配理由、关系表达、估价、时间与未知，不编造候选名称、价格或工期。PM 审核 QA 报告后，才按获准范围用实际输出说明。

依据：产品比较维度；候选证据待 PM 审核 QA。

### 7. 和搜礼物清单相比有什么增量？

**短答：产品要帮助用户理解候选为什么适合、怎样取舍。**

展开：搜索可以提供线索；GiftWise 的设计是将同一组约束、事实和未知放到每个候选旁边，方便比较。没有搜索对照实测，不能说已经更快或更准。

依据：产品设计对比；未作竞品效果试验。

### 8. 和直接聊天问模型有什么差别？

**短答：把需求、理由、约束检查和明确选择串成固定流程。**

展开：模型给建议，独立规则检查确定约束；用户保留选择权。这个设计不能证明通用模型一定做不到，也不能证明我们的推荐质量更高；新版实际闭环仍待 QA。

依据：Issue #1；交付变更契约。

### 9. 推荐理由怎么避免编造？

**短答：要求区分用户事实、模型推断和未知，并核对引用。**

展开：有原文或事实引用还不等于语义正确。“喜欢阅读”不能被扩写成“肯定喜欢某本书”。规则能检查引用存在，理由是否合理仍需输出审阅，不能保证彻底消除幻觉。

依据：事实/推断/未知契约；新版输出待 QA。

### 10. 用户不了解对方，还能推荐吗？

**短答：保留未知，避免把年龄、职业或关系当成个人偏好。**

展开：可以提出需要进一步了解的地方，或克制表达、保留选择空间的方向。模糊预算或无法理解的限制必须先澄清，不能为了出结果而默默补值。

依据：Issue #1；输入与排除项确认契约。

### 11. 三个都不喜欢怎么办？

**短答：通过约束检查不等于用户喜欢；让用户补充偏好或结束选择。**

展开：不能回答“三个不好就会被规则自动拦住”，因为主观不合心意未必违反确定约束。用户主动再发起任务不属于系统可无限自动修订的理由；具体交互以交付验收为准。

依据：产品边界；不新增未实现的“换一批”能力声明。

### 12. 系统会自动选最优吗？

**短答：不会擅自替用户选。**

展开：要求用户明确选择一个通过检查的候选。不把估价最高、最低、浪漫程度或模型推荐顺序等同于最优。可信选择保护的新版验收尚待回填。

依据：Issue #1；契约选择事件。

### 13. 为什么选择后才讲包装、贺卡？

**短答：先解决送什么，再围绕选中的礼物提供增强服务。**

展开：三候选先配商品图辅助比较，用户明确选择合格礼物后才生成包装效果图和赠送建议，避免为未选方案出图。底图由图像服务生成，中文箭头与说明由前端叠加，便于修改、窄屏阅读和文字等价；PM 已做一次 Seedream 纯文字接口调用，产品接线、参考图能力和费用仍待验证。包装不报价，减少无用生成与等待只是动机，节省比例/成本未实测。

依据：Issue #1 增量决定；呈现契约。

### 14. 预算包含哪些钱？

**短答：新版礼物预算只统计选中的礼物本身，三个候选不相加。**

展开：包装、贺卡、装饰和配送不计入该预算且不报价，不意味着免费；估价未核实，不能当作真实购买账单。新版区间滑条和选后账单正在联调，待独立验收。

依据：增量契约预算与账单章节；不沿用旧全量费用说法。

### 15. 零元礼物是什么意思？

**短答：礼物本身不新增支出，不把新买材料说成免费。**

展开：已有材料、手写内容或陪伴可以是设计方向，但仍需确认可执行性和准备时间。零元合法是新版需求，不能用旧候选估价为零的测试证明新版输入已支持。

依据：Issue #1；新版零元输入/候选/账单贯通待 QA。

### 16. 语义识别会不会替用户决定禁忌？

**短答：识别只提出有依据的候选约束，需要用户确认。**

展开：展示原文依据，用户同页确认，服务端固定约束后由规则拦截。无法理解或未完整确认时先澄清，不能静默忽略。原文锚定不证明语义正确；真实识别与模型路径尚未验证。

依据：增量契约排除项识别与确认；新版 QA 待核实。

### 17. 准备时间是不是保证送达？

**短答：不是；准备时间是估算检查，不能证明物流。**

展开：新版六档分别按 1、5、7、30、90、365 天上限检查，需显示映射；这些值是契约要求，不是运行数字。真实交付时间还受商品与物流影响，均未核实。

依据：交付变更契约 §1；UI 映射验收待 QA。

### 18. 有真实用户证明这个产品有价值吗？

**短答：还没有真实用户效果验证。**

展开：不能把测试数量或虚构场景当作用户收益证据。后续可测试用户能否解释所选理由、是否理解未知项、完成比较的时间和放弃原因；这只是研究计划，不是已完成实验。

依据：待核实清单“用户验证”。

## 二、链路、工程与交付范围

### 19. 独立规则为什么重要？

**短答：让确定约束的判定不依赖模型自评。**

展开：预算、准备时间、禁忌词/标签与必要字段可按固定规则检查。规则不等于语义理解全覆盖，也不能替收礼人判断喜好。新版验证应看对应版本报告，不报旧错误码总数充当质量。

依据：规则契约与新版验收入口，结果待 QA。

### 20. 自动修订是你们的核心能力吗？

**短答：不是，核心是礼物方案、理由、比较与选择。**

展开：当候选不满足硬约束且有可修订路径时，全任务最多一次自动业务修订，推荐与选后增强合计计算；仍失败就报告。识别确认不消耗这次业务修订，也不能因此无限重试模型。

依据：Issue #1 产品主张补充；增量契约。

### 21. 当前新版真实端到端跑通了吗？

**短答：不能宣称通过；新版仍在联调，最终结论等 PM 审核 QA 报告。**

展开：模块自测、本地 mock 流程、真实模型识别、推荐和呈现是不同范围。只有同一交付版本的独立报告能说明其覆盖范围，不能用多个旧记录拼接。

依据：待核实清单；不能用旧 Dify 归档回答新版结论。

**短答：说明对应旧工作流曾发布或运行，不证明新版功能。**

展开：按报告标明版本和原始运行记录，历史数字保留原文。本轮不调用模型；没有新增真实模型记录就不说新版已发布、已识别或已呈现。发布状态也不能只看草稿字段推定。

依据：`workflow/evidence/WF-003-2026-10-30.md`；当前需求另看增量契约。

### 23. 为什么用这种架构？

**短答：分别说明建议生成、约束检查和选择状态的责任。**

展开：新方案由后台专用浏览器获取证据，模型解释适配理由，可信服务端绑定商品/规格/价格，独立代码检查确定约束，界面帮助比较与选择。模型不能改价过关，网页内容是数据而非系统指令。方案已确定，正在实现和验证；进程内状态失效、扩容和故障恢复仍需说明，不把架构图当运行证据。

依据：架构文档、增量契约；最终图随 QA 锁版制作。

展开：选编排平台是为了组织生成与检查步骤，同时需要承担平台耦合和可观测限制。产品增量应由三方案选择流程说明，不靠堆叠名词。旧平台限制只在对应版本归档范围内引用。

依据：新版证据待回填；旧成本报告只作历史参考。

## 技术支持追问（不占主讲）

本段服务七分钟追问，不增加主讲页数；统一状态为**方案已确定，正在实现和验证**。权威为 [#59](https://github.com/sunnyyang0822-stack/GiftWise-AI/issues/59)、[#60](https://github.com/sunnyyang0822-stack/GiftWise-AI/issues/60)，具体实现/验收边界见 [同步记录](../competition/检索与媒体方案材料变更记录-2026-10-31.md)。

**为什么在后台检索？用户需要装扩展吗？**

目标是用户只用网站，由后台 OpenCLI 与专用浏览器读取商品信息，不接触用户个人浏览器、Cookie 或登录会话。这样能把来源读取与网站交互分开管理；代价是后台浏览器、连接与任务队列的运维。服务器未部署，普通用户无需扩展的真实同版全链路仍待 QA。

**为什么选择 OpenCLI，官方 API 不好吗？**

它是浏览器页面观察的候选实现路径，目的是取得具体规格和价格条件的证据，而不是让模型猜价。不宣称普遍优于官方 API；若有获准稳定 API，要比较覆盖、授权、结构与维护成本。浏览器需运行环境，网站访问限制、登录过期、验证码、超时、页面变化都会影响可靠性；遇限制停止，不能把绕过平台限制当优势。安装成功只证明 CLI 可启动。PR #61 的练习站读取使用包内 CDPBridge，不能说 CLI browser 命令或真实商品检索已完成。

**如何防止模型把价格改小来过预算？**

目标是可信服务端按商品 ID 绑定规格、数量、币种、来源、读取时间、价格条件与证据，候选引用绑定记录，模型只解释适配理由；未知/过期/错任务 ID 拒绝。独立代码用绑定金额检查，不能接受模型随手改价。网页文字是数据，不执行网页中的系统指令，也不开放任意 shell/eval。模块受控自测不等于已与生成模型同版跑通。

**四种价格来源有何区别？价格未知怎么办？**

页面观察价是当时该规格/条件的页面记录；用户报价是用户提供但未独立核实；种子参考价是带日期的非实时参考；模型估价只是推测，不是商品证据。#60 sidecar 当前无 model_estimate 枚举，按契约使用 unknown 并在说明层披露，不擅改接口。未知金额为 null，不填 0。条件价资格不明、区间跨预算均不能称预算已核实；区间按上端点筛选。0 元礼物预算合法不意味着所有未知商品免费，页面观察价也不保证结算价、库存或送达。

**为什么先选礼物再出包装图？为什么底图与标注分开？**

三候选各有对应商品图供比较，选定合格礼物后才生成包装图，减少无用生成与等待；尚无实测节省比例。底图由图像服务生成，前端叠加中文箭头和简短说明，可修改、窄屏放大并提供文字等价。参考图支持、外观一致性、坐标缩放与无障碍仍需验证；PM 首次纯文字请求已返回图片，但边缘裁切、比例不理想、无箭头，不能当产品视觉通过；后续调用仍按授权执行。

**AI 图会不会误导用户？图片有授权吗？**

来源图须对应 SKU/规格并有使用依据，公开可见不代表可任意转载；准确性优先于白底风格。通用样例标示例，AI 图标“AI效果示意，非商品实拍”，不能伪装商品照片。任何图都不能证明材质、成分、过敏安全或价格真实，不能声称图像校验消除风险。当前真实商品图来源与授权仍缺。

**检索或图片失败、商品不足怎么办？如何隔离后台？**

明确 unavailable/partial/failed，条件价不清先澄清，真实有据商品不足不凑数。允许显著标识的参考数据或保留文字结果，不能伪造实时成功。目标采用单 worker 串行、有界队列、超时取消和清理，任务/用户状态隔离；浏览器端口只在本机或受控私网，公网只开放业务 API，密钥只在服务端。重复选择不应重复创建付费任务；幂等、安全下载与隔离需独立 QA，不宣称生产安全已验证。

**目前到底完成哪一步？最新 QA 证明了什么？**

本轮 release 尚无 #59/#60 同版独立结论；PR #61 有后台模块、接口与受控自测，以及公开练习页读取，练习站随机 GBP 标价不是真实 CNY 商品报价。文末新补证已有固定 Apple 中国详情 CNY 页面观察价，但目录搜索失败、两种规格不能凑三方案。PR 已增加模型价格引用门禁，仍未同版真实联调；通用搜索/三种不同商品、授权商品图、产品包装服务接线与服务器部署仍未完成或受阻；PM 另有一次 Seedream 纯文字返回记录，视觉未通过，不改变该结论。最新 PR #51 独立报告测试的是更早业务 SHA，HTTP mock 有通过、浏览器 E2E 受阻、真实模型跳过；不能套用到新方案，也不能用后续开发自测自动关闭旧缺陷。
