# 主动认错脚本（三条 + 一条备选）

> **为什么主动说**：评委最吃这一套——**能自己发现缺陷、说清怎么发现、讲明怎么处置**，比"我们全都没问题"可信得多。
> 而且我们的缺陷**评测方跑一条命令就能看到**（`python tools/verify_all.py` 会判 FAIL）。被挖出来是诚信问题，主动说是工程成熟度。
> 每条四段：**承认什么 → 怎么发现 → 怎么修/登记 → 口播稿（可直接照念）**。

---

## 脚本一：健康检查会掩盖半开正文缺陷

**承认什么**
> 我们的 `/healthz` 只能证明**进程活着、规则版本一致**，它**根本不碰请求路径**。一个慢速攻击者只要发一半正文，就能占住工作线程，而 `/healthz` 依然返回 200 —— 也就是说，**我们的健康检查会对这类故障撒谎**。

**怎么发现**
> 我们在给可观测入口做对抗检查时，构造了一个半开连接：`Content-Length: 100`，实际只发 5 字节。旧镜像的表现是**零响应且不关闭连接**——QA 的**原始观测是 45 秒**，镜像审计的 **26 秒**观察窗内也**始终零响应**（投影页写的「25 秒」即观察窗口径，不是上限），线程被占住 —— 而同一时刻 `/healthz` 是 200。这一条被我们自己的复核工具抓了出来。

**怎么修 / 怎么登记**
> 我们给正文读取加了**时钟预算**：现在 **10.02 秒返回 `HTTP/1.0 408 Request Timeout` 并主动关闭连接**。
> 更重要的是**我们改了自证方式**：新增的自证脚本**不看 `/healthz`**，而是**直接打半开正文并计时**——把"健康检查会撒谎"这件事变成一条可复跑的命令。
> 我们还如实登记了它的边界：线程占用是**持续到客户端放弃或进程重启**为止（客户端关闭后约 2.5 s 回落），不是"永久泄漏"。

**口播稿（约 35 秒，可直接念）**
> "第三条我想主动说一个我们自己的缺陷：**健康检查不等于服务可用**。
> 我们发现 `/healthz` 会掩盖半开正文攻击——发一半正文就能占住线程，而健康检查照样 200。
> 修完之后是 10 秒返回 408 并关闭连接。但我们真正的修法不是改健康检查，而是**改我们的自证方式**：
> 我们新写了一条命令，它不看健康检查，直接打半开正文并计时。**一个会撒谎的指标，不如一条会说真话的命令。**"

**当场演示**：`verify_delivery_claims.py` 第 2 项。

## 脚本二：parity 的样例集有**结构性盲区**

**承认什么**
> 我们的"JS 与 Python 规则一致"这条声明，曾经是**假绿**。不是数字造假，而是**夹具本身有结构性缺陷**：当时的夹具只有 **55 组**样例（**原记 55 组；补完越界网格后现为 74 组**），这些样例里 **request 字段一直是一个固定的合法值**（`budget_amount: "200.00"`、`available_days: 2`）—— 整个夹具文件里把这两个字段当作对象字段出现的节点数是 **0**。
> 结果就是：**"请求侧数值范围校验"这条代码路径在 parity 里永远不可能被触发。** 那句"55 组 0 差异"是真的（**原记 55 组；现为 74 组**），但它**没有测到该测的东西**。

**怎么发现**
> 我们两个方向各查了一次，然后对上了：
> ① 独立复核工具做跨层对照，14 条网格里**当时有 6 条分歧**（归档 `docs/verification/runs/20261031T00*/js_range_parity.out`）；**现已收敛到 1 条**（`days=10**20`，两侧都拒绝、仅分类不同）（`budget=0 / 10000.01 / 10001`、`days=366` 等）——Python 拒绝、JS 放行；
> ② 但 parity 偏偏报 0 差异。
> **"两边不一致"和"parity 说一致"同时成立，只可能说明是夹具没测到。** 顺着查就确认了上面的结构性缺陷。

**怎么修 / 怎么登记**
> 让 **request 也变化**：新增 **15 组越界网格**（预算 `{0, 1, 10000, 10000.01, 10001}` × 天数 `{0, 365, 366}`）+ **2 组格式优先**用例，并加**反向断言**证明候选侧没被误伤（候选侧 `estimated_total="0"`、`preparation_days=0` 仍然通过）。
> 现在 parity 是 **74 组 / 0 处语义差异**（intake 27 + 候选批次 26 + 请求侧越界与格式 17 + 损坏样例 4）。
> **还剩 1 条如实登记为未消解**：`days=10**20` —— Python 判 `needs_input / LIMIT_EXCEEDED`，JS 判 `error / INVALID_JSON`。**两侧都拒绝，只是错误码和层级不同。**⚠️ **它不在 parity 74 组网格内**（网格天数只到 366，该值超网格），**不要说成"74 组里有 1 项分歧"**。

**口播稿（约 40 秒，可直接念）**
> "我要主动说一个**假绿**：我们有一项声明叫『JS 和 Python 规则样例级一致，**55 组 0 差异**』——**55 组是 2026-10-30 的旧口径，补完越界网格后现在是 74 组**。
> 那句"0 差异"是真的，但它**没测到该测的东西**——因为夹具里 request 一直是个固定的合法值，越界输入**永远触发不到请求侧校验**。
> 我们是怎么发现的？两个方向对上了：复核工具说 14 条网格里有 6 条两侧不一致，可 parity 偏偏说 0 差异。**矛盾本身就说明夹具漏了。**
> 修法是让 request 也变化：补了 15 组越界网格加 2 组格式优先，并且加了反向断言，证明候选侧没被误伤。现在是 74 组 0 差异。
> 还剩一条极端值我们没消解，两侧都拒绝但错误码不同，**我们把它登记为未消解，不写成全一致。**"

**当场演示**：`node web/tools/parity-check.mjs`；`python tools/verify_all.py --only js_range_parity`（1/14 与分歧清单）。

## 脚本三：我们自己的阶段 B 评审基线测试**曾经是红的**

**承认什么**
> `tests/acceptance/stage_b` 有 275 条用例，其中 3 条是**哈希断言**——它们钉死了一份**具日期的历史评审记录**里被评审文件的 sha256。
> 规则层和测试文件改过之后，这 3 条就 FAIL 了：`Ran 275 tests / FAILED (failures=3)`。
> **一份"钉死历史哈希"的测试，会随着代码演进必然变红** —— 这是我们测试设计上的一个真实缺陷。

**怎么发现**
> 直接跑就能看到：`python -m unittest discover -s tests/acceptance/stage_b`。
> 值得说的是，**我们最大的那套单测（`discover -s tests`，329 条）是绿的**，因为 `tests/acceptance/` 下刻意没有 `__init__.py`，它不会被递归进去 —— 所以这套红**很容易被"总量全绿"掩盖掉**。是我们主动分开跑才发现的。

**怎么修 / 怎么登记**
> 关键选择是：**不改写历史**。
> 我们没有去改那份 10-29 的历史记录（改了就毁掉了审计链），而是**新增了一份 `val-001-rereview` 记录**，用 `superseded_review` / `superseded_sha256` 两个字段**把全部旧哈希原样保留**；测试改为断言**新基线**的同时**校验旧值仍可追溯**。
> 同时 `cases.json` **加了 313 行用例**（是**加**，不是删断言）。
> 现在：`Ran 275 tests / OK`，并且"当前可验证"和"历史可追溯"两个目标同时成立。

**口播稿（约 40 秒，可直接念）**
> "第三条是我们自己测试设计的缺陷。我们有一套 275 条的评审基线回归，其中 3 条钉死了历史评审记录里的文件哈希。
> 代码一演进，它必然变红。而我们**最大的那套 329 条单测是绿的**——因为目录结构的缘故，这套红**很容易被『总量全绿』掩盖**。
> 我们的修法**不是改那份历史记录**。改哈希最简单，但会毁掉审计链。我们新增了一份 re-review 记录，用 `superseded` 字段**把旧哈希完整保留**，测试改成同时断言新基线、校验旧值可追溯。
> 另外用例是**加了 313 行**，不是删断言。**当前可验证、历史可追溯，这两件事我们都不放弃。**"

**当场演示**：
```bash
python -m unittest discover -s tests/acceptance/stage_b   # → Ran 275 tests / OK
git show --stat 89d6624 -- tests/acceptance/stage_b   # → 5 files changed；cases.json +313 行（旧写法现已输出为空：改动已提交）
```

## 备选（第四条，****已闭环**（材料、镜像、本机三方一致）**）：材料自身声明的规则哈希已过期

**承认什么**
> `docs/competition/材料清单与自查.md` **（本条已闭环，不要讲成未修项）** `:97` 现在声明 `1f389dad4c2589fb…`，与本机 `validator/rules.py`、交付镜像 `/healthz` **三者一致**。
> 但**镜像已经重建**，`/healthz` 现在返回的是 `1f389dad…`。
> **也就是说：我们的材料自己给出的版本指纹，和我们的服务实际返回的对不上。** 评委只要 `curl` 一次就能看到。

**怎么发现**
> 我们自己的对外声明审计工具判了 FAIL，并把**具体行号**和原始输出一起落盘：
> `python tools/verify_all.py --only declared_rules_hash` → `docs/verification/runs/<时间戳>/declared_rules_hash.out`。

**怎么处置（二选一，必须写明选哪个）**
> ① 把声明**重钉**为 `1f389dad…`；或
> ② 明确"**提交基线 = 某快照**"，并且**不再声称 `/healthz` 会返回该值**。
> **不掩盖（已闭环）**：这条**已于 2026-10-31 01:5x 修好**，`python tools/verify_all.py --only declared_rules_hash` 现在判 **PASS**（归档 `docs/verification/runs/*/declared_rules_hash.out`）。

**口播稿（约 25 秒）**
> "还有一条：我们材料里写了一个规则哈希，说是 `/healthz` 会返回那个值——**曾经对不上，**现在已经一致**（三者均为 `1f389dad…`）**，因为镜像在材料之后重建过。
> 这是我们**对外声明审计工具自己判红的**，它连行号一起报给我。修法是二选一：把声明重钉到当前值，或者改成说明『提交基线是哪个快照』。
> 我不想让您去 `curl` 一次才发现这件事，所以我现在就说。"

**当场演示**：`python tools/verify_all.py --only declared_rules_hash`

## 使用建议

- **答辩时可挑 2 条讲**（脚本一 + 脚本二最稳：一条是"指标会撒谎"，一条是"假绿"），**不要四条全讲**——7 分钟问答要留时间给评委提问。
- 若评委先问到镜像/材料状态 → 用**备选第四条**，但要讲成「**我们已经自己修好的一条**」（2026-10-31 01:5x 重钉 + PASS），**不要再当成未修项**。
- 三条脚本的共同句式：**"我们发现了什么 → 我们怎么发现的 → 我们怎么处置 → 还剩什么没解决"**。**最后一段一定不能省**——省了就变成自夸。
