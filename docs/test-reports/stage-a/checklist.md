## 输入与离线执行前提

虚构完整输入见 `tests/acceptance/stage-a/baseline.json`，只有测试数据，无业务实现或 mock 通过结果。它包装 `request` 与 `candidate_batch` 方便取数，不是新增业务接口。

校验器交付后，每例深拷贝基线，按表修改；将 `request` 和 `candidate_batch` 分别严格 JSON 序列化后传给实际 `validate`。解析异常类用例直接传原始字符串，不能先被测试框架标准化。每例核对 status、all_passed、顶层/候选错误、字段路径及中文解释；预期拒绝时还需确认不崩溃、不误标通过。子例一例只改变一个条件，除非专测错误优先级。

前提 B：实际校验器及 Python 环境交付，不访问网络。前提 C：已授权的真实 Dify 环境、实际 Code 实现、可控故障测试方式和脱敏轨迹。前提 D：实际选择接口/网页、可信运行记录及包装复核实现。涉及模型调用先由 PM/操作者安排权限和资源；本清单不授权自行付费调用。

## Dify/选择阶段操作者步骤

1. 在实际 Dify Studio → 对应 GiftWise 工作流 → Test Run，确认部署/工作流版本、模型设置与托管方式，输入虚构基线。只展示脱敏运行元数据，不展示供应商配置、密钥或私有地址。
2. 查看输入、LLM、Code、条件分支、修订、报告/结束节点的真实执行记录。预期正常推荐一次生成、修订分支只一次修订并重检，已通过项保持不变；失败时先检查输入映射、Code 实际输出及分支条件，而不是只改最终文案。
3. 在实际网页/选择接口完成 T16–T21。比对可信运行编号、候选版本、原始需求与代码记录；预期选择前零呈现调用，完整正常任务两次模型调用，全局一次修订时最多三次（失败调用也逐条记账）。若异常，检查浏览器请求与可信端记录，不以浏览器 passed 字段作依据。
4. 每条保存 run ID、带时区时间、版本、原始与最终 JSON、各次校验、节点轨迹、修订计数、选择 ID、实际调用数及用量。无费率/账单依据记成本未知，不填零。任何截图与导出先脱敏。
