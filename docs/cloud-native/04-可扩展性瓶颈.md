## B1 · 90.5% 的 CPU 不在业务逻辑上 —— **已测量**（最高优先级）

**测量方法（单次 exec 内的 cgroup 自测量）**

```bash
docker exec -i -e PROBE_REQUESTS=3000 -e PROBE_CONCURRENCY=8 \
  giftwise-cloudnative-lab-validator-a-1 python - < compose/lb/incontainer_cpu_probe.py
```

**原始输出**

```
  完成请求              : 3000（HTTP 200: 3000）
  墙上时间              : 3.775 s
  吞吐                  : 794.81 req/s

  cgroup CPU 增量       : 7170362 us
  客户端(本进程)CPU     : 1787308 us
  服务端 CPU (相减)     : 5383054 us  = 5.3831 core-seconds
  平均占用核数(服务端)  : 1.426 core
  每请求服务端 CPU      : 1794.35 us

  其中 validate() 纯计算 : 170.87 us = 9.5%
  其余(HTTP/线程/socket) : 1623.48 us = 90.5%

  单核吞吐上限(按实测每请求 CPU) = 557.3 req/s/核
  单核吞吐上限(若只有 validate)  = 5852.4 req/s/核
  => 框架开销把单核上限压低约 10.5 倍
```

**已测量**：
- 每请求服务端 CPU = **1794.35 us**；
- `validate()` 纯计算 = **170.87 us**（占 9.5%）；
- 框架开销 = **1623.48 us**（占 90.5%）；
- 单核吞吐上限从 5852.4 被压低到 **557.3 req/s/核**（**10.5 倍**）。

**不是日志**（已测量排除）：`--log-driver none` 只省 **17.51 us/请求 = 1.2%**
（`compose/evidence/logdriver-vs-none.md`）。

**未分解的部分（推断，明确标注）**：
剩余约 1623 us 具体如何分摊到"每请求新建线程 / 请求行与头解析 / socket 收发 /
Python 层调度"，**本线没有拆开**。原因是拆开需要逐个换成对照实现
（例如把 `ThreadingHTTPServer` 换成线程池版、把 `BaseHTTPRequestHandler`
换成手写解析），这超出了本线的取证范围。

**可测的判据（怎样算解决）**：
1. 每请求服务端 CPU 从 1794 us 降到 **< 500 us**（若框架换成线程池 + 复用连接），
   用同一个 `incontainer_cpu_probe.py` 复测即可对比；
2. 或：单核吞吐上限从 557 req/s/核 提升到 **> 1500 req/s/核**；
3. 或：把 `validate()` 的占比从 9.5% 提升到 **> 50%**——
   这个判据最干净，因为它直接说"CPU 终于花在业务上而不是管道上"。

**为什么它排第一**：它同时解释了"为什么加副本收益不明显"的**上限**——
即使副本无限多，单核 557 req/s 的框架天花板仍然存在，
而且这个天花板与业务量无关。

## B2 · 无 keep-alive：每请求 2 次 TCP 握手 —— **已测量**

**原始输出**（`docs/cloud-native/02-本地模拟实验.md` 第 3 节）

```
纯 TCP 握手 min/median/max ms : 0.206 / 0.343 / 23.424

复用尝试：在同一 socket 上连发两个 POST /validate（模拟 keep-alive）……
  第一个响应状态行        : HTTP/1.0 200 OK
  响应头里是否显式含 close : False
  第二个请求是否被处理     : False  (第二个响应 0 字节)
```

**已测量**：
- 上下游都讲 `HTTP/1.0`，响应后即关闭连接；
- **同一 socket 上的第二个请求收到 0 字节** → 无法复用，这是行为事实不是推测；
- 纯握手中位数 **0.343 ms**（loopback）。

**为什么握手在 loopback 上看起来便宜、在云端不便宜（推断）**：
loopback 没有真实 RTT。跨主机/跨可用区时，每次握手至少要多付 1 个 RTT；
若再加 TLS，握手成本还要乘以数倍。**本线没有跨主机环境，因此这部分是推断。**
按单请求总耗时约 7 ms、握手占 ~5%（本机）估算，
云端这一比例会显著上升——但**具体升到多少，本线无法给出数字**。

**可测的判据**：
1. 在同一 socket 上连发 2 个请求，**第二个也能拿到 200**（当前是 0 字节）；
2. 或：把服务端 `protocol_version` 设为 `"HTTP/1.1"` 并正确发送 `Content-Length`，
   复跑本线第 3 节脚本，观察"第二个请求被处理 = True"；
3. 或：在**跨主机**环境下测同一批请求，比较 keep-alive 开/关的 p95 差异。

## B3 · 单机网络路径饱和 —— 现象**已测量**，归因**推断**

**原始输出**（`compose/evidence/scaling-main.json`）

```
   并发        直连 1       直连 2       增益         LB 1       LB 2       增益
    1      110.74      98.52    0.89x        78.88      77.13    0.98x
    4      496.55     609.01    1.23x       369.02     424.47    1.15x
   16      301.08     329.39    1.09x       377.02     289.97    0.77x
   48      307.53     302.90    0.98x       214.52     274.08    1.28x

  直连 1 副本 / conc=16                  thr=  301.08 req/s  p50=  12.609  p95=  26.215  max= 1038.328  ok=400/400
  直连 1 副本 / conc=48                  thr=  307.53 req/s  p50=  13.966  p95=1031.530  max= 1248.522  ok=390/400
  经 LB 1 副本 / conc=48                thr=  214.52 req/s  p50=  44.500  p95=1037.424  max= 1090.536  ok=388/400
```

**已测量（现象）**：
1. 吞吐在 **并发 4** 达峰（496~609 req/s），此后**下降**（并发 16/48 只剩约 300 req/s）；
2. **并发 ≥16 时 p95 出现约 1030 ms 的台阶**，而且这个台阶在
   **直连副本**和**经 LB**两条**互不相干**的路径上**同时**出现；
3. **直连 2 副本相对直连 1 副本的增益围绕 1x 波动**（0.89/1.23/1.09/0.98），无近线性增长；
4. 48 并发下**两条路径都开始丢请求**（直连 390/400、经 LB 388/400）。

**推断（明确标注为推断）**：
两条独立路径出现**同一个约 1 秒台阶**，最合理的解释是它们**共享的底层**
——Docker Desktop 的宿主↔WSL2 端口转发 + Windows TCP 栈——先饱和。

支撑这个推断的**旁证（已测量）**：实验 D 里连接一个已停容器时，
TCP SYN 表现为 **~1.28 s 的 blackhole** 而不是立即 RST，
量级与这里的 ~1030 ms 台阶吻合。

⚠️ **本线无法进一步定位到具体组件**（没有 WSL2 内核/hyper-v 侧的可观测手段），
也没有做"绕过端口转发"（例如用 host 网络模式）的对照实验。
**所以归因是推断，不是结论。**

**这一条对"扩容是否有用"的意义（必须讲清楚）**：
> **不要把这里的 1x 增益读成"验证器不能水平扩展"。**
> 验证器无状态、结构上可水平扩展。
> 但在这个**单机**测量环境里，**宿主机网络路径比副本先饱和**，
> 于是扩容收益被环境**掩盖**了。
> 要测出真实扩容收益，必须换到多主机环境——**本线没有该条件，故没有做。**

**可测的判据**：
1. 在多主机环境下复跑 `run-scaling-experiment.py`，
   若"直连 2 副本 / 直连 1 副本"的增益在并发 16~48 下 **→ 接近 2x**，
   则说明 B3 是单机环境假象，扩容有效；
2. 或在单机上改用 **host 网络模式** 绕过端口转发，看 ~1030 ms 台阶是否消失
   （若消失，则归因成立）；
3. 或在并发 48 下做到 0 丢包（当前直连丢 10/400、经 LB 丢 12/400）。

## B4 · 健康探测串行 + 死上游 blackhole —— **已测量**

**原始输出**（`compose/evidence/failover-main.json`）

```
 2001  200   1        validator-a:8000            5.259
 2002  200   2        validator-a:8000         1273.965
 2003  200   1        validator-a:8000            4.802
 2004  200   2        validator-a:8000         1280.862
 …
  触发失败转移(attempt>1)的请求数  : 2 / 12
  这些转移请求的额外耗时 (ms)      : [1273.965, 1280.862]

  -> 健康探测发现副本不可用用了 5.97 s（轮询 54 次，间隔 0.1s）
```

**已测量**：
1. 失败转移**不免费**：受影响请求耗时 **1273.965 / 1280.862 ms**，
   正常请求 **4.0~5.3 ms** → **约 250 倍**；
2. 健康探测发现不可用耗时 **5.97 s**（独立线程测量），
   而探测**间隔**只有 2 s → **探测本身比间隔慢 3 倍**；
3. 根因（已测量）：探测循环**串行**遍历上游，
   死上游的连接要 blackhole **约 1.3 s** 才返回，把整轮探测拖长（约 3.3 s/轮）；
4. 探测发现后不再打向死副本（12/12 attempt=1）；副本恢复后能重新纳入。

**为什么"约 1.3 s"很重要（已测量，且可推广）**：
它在 WSL2 上表现为 SYN 被静默丢弃而非 RST。
在真实云环境中，**网络分区/安全组静默丢包**会产生同类现象——
LB 必须能容忍"连接既不成功也不失败，而是要等超时"。
**但云端的实际超时值，本线没有测（推断）。**

**可测的判据**：
1. 健康探测发现不可用时间 **< 探测间隔**（当前 5.97 s > 2 s）；
2. 失败转移请求的额外耗时 **< 100 ms**（当前 ~1276 ms）；
3. 或：探测改为**并行**（`concurrent.futures`）后，
   把上游数从 2 增加到 N，观察发现时间是否**不再随 N 线性增长**
   （当前串行实现预期 O(N)，**未做 3+ 上游对照，故为推断**）。

## B5 · `/healthz` 探针语义缺陷 —— **已测量**（会掩盖故障）

**原始输出**（`compose/evidence/halfopen-main.json`）

```
  半开连接持续被挂住的期间，健康探测次数        : 27
  其中 /healthz 返回 200 的（直连）             : 27 / 27
  其中 /healthz 返回 200 的（经 LB）            : 27 / 27
  /healthz 延迟最大值（直连 / 经 LB）           : 27.829 ms / 27.762 ms
  => 健康检查是否全程全绿：True
```

半开连接读超时精确值（`compose/evidence/halfopen-timeout-precise.txt`）：

```
  trial1: 首个响应字节在 t=10.014s 到达 -> HTTP/1.0 408 Request Timeout
  trial2: 首个响应字节在 t=10.013s 到达 -> HTTP/1.0 408 Request Timeout
  trial3: 首个响应字节在 t=10.012s 到达 -> HTTP/1.0 408 Request Timeout
```

**已测量**：
- 半开正文连接占用一个 handler 线程 **10.012~10.014 s**（与
  `GIFTWISE_READ_TIMEOUT` 默认 10 s 吻合，`server.py:40`）；
- 同期探针 **27/27 全绿**，最大延迟仅 27.8 ms；
- ✅ 公平地说：`server.py:36-42,58-93` 的读超时修复**确实生效**——
  它把"永久挂住"变成了"10 秒后 408"。本实验**证实了这个修复有效**。

**这个缺陷的真实危害（推断，但方向明确）**：
单个半开连接只占 1 个线程。但 `ThreadingHTTPServer` 是**每连接一个线程、无上限**，
所以 N 个半开连接会占 N 个线程，每个最长 10 s。
在耗尽线程/内存之前，**探针一路绿灯**——
也就是说编排平台会因为"探针全绿"而**持续把流量送进一个正在退化的实例**。
⚠️ **本线没有做到"用半开连接打满线程"的压测**，所以"多少连接会打满"是**推算，未测**。

**可测的判据**：
1. 在途请求数 / 活跃线程数超过阈值时，`/healthz`（或独立的 readiness 端点）
   **返回非 200**；
2. 或：readiness 探针改用"能在预算内完成一次真实正文处理"的判据；
3. 或：把 handler 线程改为**有界线程池**，池满时立即 503 而不是无限期挂住——
   此时"池满"成为可被探针观测的信号。

## B6 · `/metrics` 非默认入口且未鉴权 —— **已测量**

**原始输出**

```
=== 默认入口的 /metrics（经 LB 转发到 deploy.server 副本）===
HTTP/1.0 404 Not Found
{"error":"NOT_FOUND"}

=== 默认入口的 /readyz ===
GET /readyz -> HTTP 404
=== 可观测入口的 /readyz ===
GET /readyz -> HTTP 200

=== /metrics（可观测入口）===
HTTP 200, 3585 bytes
giftwise_build_info{service="giftwise-validator",rules_source_sha256="1f389dad4c…",python_version="3.12.16"} 1

=== 伪造 Basic 鉴权 ===
forged Basic -> HTTP 200
```

**已测量**：
| 判据 | 默认入口 | 可观测入口 |
| --- | --- | --- |
| `GET /metrics` | **404** | **200**（3585 B） |
| `GET /readyz` | **404** | **200** |
| 匿名 `GET /metrics` | — | **200** |
| 伪造 `Authorization: Basic` | — | **200** |
| 泄露信息 | — | `rules_source_sha256`、`python_version` |

**矛盾点（这是它的核心问题）**：
- 默认入口（会被部署的那个）**没有指标** → 采集器抓不到；
- 有指标的入口**未鉴权**，且泄露规则指纹 → 不能安全暴露；
- 于是陷入"能用指标的不安全、安全的没指标"的境地。

**可测的判据**：
1. 默认入口 `GET /metrics` 返回 **200**；
2. 匿名 `GET /metrics` 返回 **401/403**（当前 200）；
3. 携带有效凭证时返回 **200**；
4. 响应中**不再出现** `rules_source_sha256`（或仅在鉴权后出现）。

## B7 · 无优雅停机 → 滚动更新丢在途请求 —— **读代码确认**（发布阻断）

**代码事实（逐条可查）**：

1. `deploy/server.py` 的 import 段（交付镜像内 `server.py:8-16`）**没有 `import signal`**，
   全文没有 `SIGTERM`/`SIGINT` 处理 → 收到 `SIGTERM` 时 Python **默认立即终止**。
2. 它使用标准库 `ThreadingHTTPServer`（`server.py:15,153`），
   而该类的 `daemon_threads = True` → 进程退出时 handler 线程被**直接掐掉**，不等待。
3. `server.shutdown()` 的语义只是"让 `serve_forever()` 退出"，
   **不等待**已在处理中的请求。
4. 对比：非默认入口 `deploy/observable_server.py:322-333` **有**完整信号处理
   → "优雅退出"能力**已实现，但不在默认交付路径上**。

**危害（推断，但机制明确）**：
滚动更新时，Pod 收到 SIGTERM → 进程立刻消失 → 正在处理 `/validate` 的请求
**收不到任何响应**（客户端看到连接被重置，而不是 408 或 503）。
`maxUnavailable: 0` **无法阻止**这件事，因为问题在进程本身。

**可测的判据**：
1. 发压的同时对容器执行 `docker stop`，**所有在途请求都收到响应**（当前预期部分收不到）；
2. 容器日志出现 `all in-flight requests drained`（补丁引入）；
3. 使用 `compose/patches/graceful-shutdown.patch` 后重跑上述测试。

⚠️ **本线没有验证补丁的运行时行为**——补丁**只生成、未应用**
（`deploy/**` 是禁区）。已验证的只有"能干净套用 + 套用后语法正确"。
详见 `docs/cloud-native/03-上云方案与未执行声明.md` 第 5.4 节。

## B8 · 可观测入口有状态 → 多副本下指标切片 —— **已测量**

**原始输出**（`compose/evidence/statefulness-main.json`）

```
--- [2] 经 LB 打 40 个请求（轮询平分给两个副本） ---
  成功 40/40
  分发到：{'validator-obs-a:8000': 20, 'validator-obs-b:8000': 20}

--- [3] 再抓一次（后值），看每个副本「自己以为」处理了多少 ---
  127.0.0.1:19101  计数 0 -> 20   增量 = 20
  127.0.0.1:19102  计数 0 -> 20   增量 = 20

  两个副本增量之和 = 40
  实际发出的请求数 = 40
  某个副本单独能看到的最大值 = 20
```

**已测量**：40 个请求，每副本各报 20，**没有副本知道总数是 40**。
代码依据：`deploy/observability.py:150-172` 的 `Metrics` 持有可变计数器。

**同时（对照）已测量**：默认入口是**真无状态**——
30 组交错请求 **0 组**响应字节不一致，同一载荷 20 次得到 **1 个**唯一哈希
（`compose/evidence/stateless-byteidentity.txt`）。

**可测的判据**：
1. 任取一个副本的 `/metrics`，累计校验数**等于**实际总请求数（需外部聚合）；
2. 或：指标里保留 `instance` 维度，且监控系统按 `instance` 聚合后总数正确；
3. 或：进程级指标（`in_flight`、`rss`、`uptime`）被明确标注为"**不可跨副本求和**"。

## B11 · GIL / 单进程解释器 —— **部分测量，且已被"证伪为主要瓶颈"**

**这一条本线要主动纠正一个常见误解。**

- **事实（读代码确认）**：`deploy/server.py:15,153` 用的是
  `ThreadingHTTPServer`，**不是**单线程 `HTTPServer`。
  也就是说，它**已经是多线程**的——它**不是**"一次只能处理一个请求"。
- **已测量**：3000 个请求 / 8 并发，服务端平均占用 **1.426 core**，
  吞吐 794.81 req/s（容器内 loopback）→ CPU 确实被并行使用了。
- **已测量**：CPU 没有被 100% 打满（1.426 core / 24 可用核），
  也就是说**不是 CPU 用尽导致的失败**，而是**每请求 CPU 成本太高**（B1）。
- **推断**：GIL 会让这些线程**不能真正并行执行 Python 字节码**，
  所以 B1 的框架开销（大量 Python 层工作）无法靠加线程摊到多核上。
  **但我没有做"多进程 vs 多线程"的对照实验**，
  所以"GIL 是当前吞吐上限的直接原因"这一句是**推断**，不是已测量结论。

**正确的表述**：
> 当前瓶颈**主要不是**"单进程/GIL"，而是"每请求 1794 us 的 CPU 成本"（B1）。
> GIL 的作用是**阻止**你通过"在同一进程里加线程"来绕过 B1。
> 要绕过 B1，需要的是"减少每请求的 Python 层工作"
> （线程池、连接复用、更轻的 HTTP 栈），而不只是"多开进程"。

**可测的判据**：
1. 对比"同一镜像开 1 个进程 4 线程"与"4 个进程各 1 线程"在相同并发下的吞吐——
   若后者显著更高，则 GIL 是直接限制因素；
2. 或：在保持并发不变的前提下，把框架换成线程池模型，
   观察每请求 CPU 是否下降（这是 B1 的判据，也顺带回答 GIL 问题）。
