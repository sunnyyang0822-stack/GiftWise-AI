### 3.1 最小可用档

```
 1. 本地构建镜像并打上不可变标签（不要只用 latest）
      docker build -t giftwise-validator:<git-sha> -f deploy/Dockerfile .
 2. 推送到镜像仓库，记录返回的 manifest digest
      docker tag  giftwise-validator:<git-sha> <registry>/giftwise-validator:<git-sha>
      docker push <registry>/giftwise-validator:<git-sha>
      docker image inspect <registry>/giftwise-validator:<git-sha> --format '{{.RepoDigests}}'
 3. 在 UCloud 控制台创建 UHost（选 Linux 镜像，装容器运行时）
 4. 绑定 EIP；配置安全组（只放行演示来源 → 服务端口；SSH 限制来源）
 5. 登录主机，登录镜像仓库并拉取 **按 digest**（不用 tag）
      docker login <registry>
      docker pull <registry>/giftwise-validator@sha256:<digest>
 6. 启动容器，只绑回环或内网，前面放一个反向代理
      docker run -d --name giftwise-validator --restart unless-stopped \
        -p 127.0.0.1:8000:8000 <registry>/giftwise-validator@sha256:<digest>
 7. 冒烟验证（从允许的来源）
      curl -fsS http://<host>:8000/healthz
      curl -fsS -X POST http://<host>:8000/validate -H 'Content-Type: application/json' \
        -d '{"request_json":"…","candidates_json":"…"}'
 8. 确认 /metrics 的行为符合预期
      curl -s -o /dev/null -w '%{http_code}\n' http://<host>:8000/metrics   # 默认入口预期 404

```

**关键设计约束（这几条来自本线实测，不是猜的）**：

- **不要**把默认入口的 `/metrics` 当作可采集端点——它**实测 404**。
  要用可观测入口，必须显式改命令为
  `python -m deploy.observable_server`（`deploy/Dockerfile:24-27` 已写明用法）。
- 一旦改用可观测入口，**必须**同时解决 `/metrics` 未鉴权
  （本线实测：匿名 200、伪造 Basic 也 200，且泄露 `rules_source_sha256`）。
- **不要**期望 liveness/readiness 用 `/healthz` 能发现"正文挂死"——
  本线实测半开正文挂满 10.0 s 期间，`/healthz` **27/27 全绿**。
- 健康检查与优雅停机的窗口必须**大于 10 s**（单连接正文读预算，
  `GIFTWISE_READ_TIMEOUT` 默认 10，见 `deploy/server.py:40`）。

## 5. 优雅停机补丁（**只生成，未应用**）

### 5.1 为什么当前设计在滚动更新时会**丢在途请求**

三条独立原因，缺一不可地导致丢请求：

**原因 1：`deploy/server.py` 完全没有信号处理。**
`server.py` 的 import 段（`server.py:8-16`）**没有** `import signal`，
全文也**没有** `SIGTERM`/`SIGINT` 的任何处理。因此容器收到 `SIGTERM` 时，
Python 采用**默认动作：立即终止进程**。正在处理的请求会连一个响应都收不到。
（对比：非默认入口 `deploy/observable_server.py:322-333` **有**信号处理——
也就是说"优雅退出"这个能力**已经写好了，但不在默认交付路径上**。）

**原因 2：它用的 `ThreadingHTTPServer` 把 handler 线程设成了 daemon。**
标准库的 `http.server.ThreadingHTTPServer` 定义等价于：

```python
class ThreadingHTTPServer(socketserver.ThreadingMixIn, HTTPServer):
    daemon_threads = True          # <-- 关键
```

daemon 线程在进程退出时被**直接掐掉**，**不会**被等待。
所以哪怕补上 `SIGTERM -> server.shutdown()`，它也只能保证"不再 accept 新连接"，
**已经在跑的那批请求照旧被丢弃**。

**原因 3：`shutdown()` 不等待 handler 线程。**
`server.shutdown()` 的语义是"让 `serve_forever()` 的循环退出"，
它**不**负责等待已在处理中的请求。必须由应用自己 drain。

> **结论**：`terminationGracePeriodSeconds` 调多大都没用——
> 因为进程在收到 SIGTERM 的瞬间就走了，根本没有"利用 grace period"的代码。

+#: 必须显式设上限：编排平台在 SIGTERM 后会等一段固定时间再 SIGKILL，
+#: 无上限的等待只会让退出时机不可控（容器会被硬杀，日志也来不及落盘）。
+SHUTDOWN_GRACE_SECONDS = float(os.environ.get("GIFTWISE_SHUTDOWN_GRACE", "20") or "20")
+if SHUTDOWN_GRACE_SECONDS < 0:
+    raise RuntimeError("GIFTWISE_SHUTDOWN_GRACE must be >= 0")

+class GracefulThreadingHTTPServer(ThreadingHTTPServer):
+    """可优雅停机的 ThreadingHTTPServer。
+
+    为什么必须换掉默认的 ThreadingHTTPServer：
+      `http.server.ThreadingHTTPServer` 把 `daemon_threads` 定为 **True**。
+      daemon 线程在进程退出时会被直接掐掉，**不会**等待 handler 跑完。
+      因此即便装上了 `SIGTERM -> server.shutdown()`，它也只能保证
+      「不再 accept 新连接」，**已经在处理中的请求仍然会被丢弃**。
+      本类做两件事：
+        1. `daemon_threads = False`：handler 线程变成可 join 的普通线程；
+        2. 自己统计在途请求数，并提供**有上限**的 `drain()`。
+    """
+
+    #: 关键：非 daemon，否则线程无法被等待（join）。
+    daemon_threads = False
+
+    def __init__(self, *args: object, **kwargs: object) -> None:
+        self._active = 0
+        self._active_lock = threading.Lock()
+        super().__init__(*args, **kwargs)
+
+    def process_request(self, request: object, client_address: object) -> None:  # type: ignore[override]
+        with self._active_lock:
+            self._active += 1
+        super().process_request(request, client_address)  # type: ignore[arg-type]
+
+    def process_request_thread(self, request: object, client_address: object) -> None:  # type: ignore[override]
+        try:
+            super().process_request_thread(request, client_address)  # type: ignore[arg-type]
+        finally:
+            # 只有这里递减才是对的：process_request() 只是「启动线程」就返回，
+            # 真正代表「这个请求处理完了」的位置是 handler 线程的退出点。
+            with self._active_lock:
+                self._active -= 1
+
+    def active_requests(self) -> int:
+        with self._active_lock:
+            return self._active
+
+    def drain(self, timeout: float) -> int:
+        """等待在途请求结束，最多等 timeout 秒；返回仍未完成的请求数。"""
+        deadline = time.monotonic() + timeout
+        while True:
+            remaining = self.active_requests()
+            if remaining <= 0:
+                return 0
+            if time.monotonic() >= deadline:
+                return remaining
+            time.sleep(0.05)
+
+

     host = os.environ.get("GIFTWISE_BIND", "0.0.0.0")
     port = int(os.environ.get("GIFTWISE_PORT", "8000"))

+    server = GracefulThreadingHTTPServer((host, port), Handler)
     _log_line(f"giftwise-validator listening on {host}:{port}; rules={RULES_HASH}")
+
+    def _request_shutdown(signum: int, _frame: object) -> None:
+        """信号处理函数里**只**请求停机，不做等待。
+
+        两点必须注意：
+          1. `server.shutdown()` 会阻塞直到 serve_forever 的循环退出；
+             若在主线程的信号处理函数里直接调用，会与 serve_forever 死锁。
+             因此放到另一个线程里调用（与 deploy/observable_server.py 的做法一致）。
+          2. 信号处理函数里不做耗时清理（会阻塞信号投递）；
+             真正的等待放在 serve_forever 返回之后的 drain()。
+        """
+        _log_line(
+            f"signal {signum} received; stop accepting new connections (grace={SHUTDOWN_GRACE_SECONDS}s)"
+        )
+        threading.Thread(target=server.shutdown, name="giftwise-shutdown", daemon=True).start()
+
+    for _sig in (signal.SIGTERM, signal.SIGINT):
+        signal.signal(_sig, _request_shutdown)
+
     try:
         server.serve_forever()
     except KeyboardInterrupt:
+        # 兜底：SIGINT 已被上面的 handler 接管；这里保留原有行为以防 handler 未装上。
         pass
     finally:
+        # serve_forever 已退出 = 不再接受新连接。此时才等待在途请求。
+        remaining = server.drain(SHUTDOWN_GRACE_SECONDS)
+        if remaining > 0:
+            _log_line(f"shutdown grace expired; {remaining} in-flight request(s) will be dropped")
+        else:
+            _log_line("all in-flight requests drained")
         server.server_close()
