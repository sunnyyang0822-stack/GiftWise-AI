## 1. 拓扑与设计选择

```
客户端 ──HTTP/1.0──> lb (python:3.12-slim, 纯标准库轮询, 宿主 18080)
                       ├──HTTP/1.0──> validator-a  (giftwise-validator:submission-20261101)
                       └──HTTP/1.0──> validator-b  (同一镜像，第二个副本)
```

设计选择及理由：

| 选择 | 理由 |
| --- | --- |
| **不用 nginx/haproxy/traefik** | 环境里没有这些二进制且装不了；引入外部依赖会让评委无法复跑。用标准库 `http.server` + `http.client` 手写。 |
| **两个副本用同一镜像** | 这样"分发"才可证伪——两副本二进制完全相同，响应差异只可能来自"谁处理的"。用 `X-GiftWise-Upstream` 响应头区分。 |
| **副本端口不发布到宿主** | 所有流量必须经过 LB，否则无法证明分发真的发生了。 |
| **LB 只绑 127.0.0.1** | 这是实验，不应对外暴露。 |
| **`Connection: close` 显式下发** | 如实反映"无法保持连接"，不做伪装。 |

文件清单：

| 文件 | 作用 |
| --- | --- |
| `compose/docker-compose.yml` | 2 副本 + LB（`metrics` profile 另起可观测入口的 2 副本 + LB） |
| `compose/docker-compose.bench.yml` | 只用于**测量**的 override：把副本端口发到宿主（19001/19002），再加一个**单副本** LB（18082），用于把"LB 自己的上限"和"副本扩容收益"分开测 |
| `compose/lb/round_robin_lb.py` | 轮询 LB：轮询分发 + 健康探测 + 诚实的失败转移 |
| `compose/lb/payload.py` | 生成合法的 `/validate` 载荷（契约来自 `validator/rules.py`） |
| `compose/run-multireplica-experiment.py` | 分发/无会话保持/并发实验 |
| `compose/run-failover-experiment.py` | 停副本后的失败转移与探测延迟 |
| `compose/run-halfopen-experiment.py` | 半开正文 × 健康检查 |
| `compose/run-statefulness-experiment.py` | 可观测入口的进程内状态取证 |

| `compose/lb/incontainer_cpu_probe.py` | 容器内单次 exec 的每请求 CPU 自测量 |

- LB 自报累计计数（`/lb-stats`）与客户端观察一致：

### 结论 ②：**会话语义不被保持** ❌ —— 这是当前设计的真实缺口

**同一 `session = sess-A` 的 60 个请求，被拆到了两个副本上。**

但这里必须**精确、不夸大**地说明它的实际影响，否则就是危言耸听：

> **当前这个校验服务是无状态的，所以"没有会话保持"在今天不会造成任何可观测错误。**
> 这不是替缺陷开脱，而是把它归位：
>
> - 本线已用代码审查 + 行为实验证明默认入口 `deploy.server` **没有进程内可变状态**
>   （`validator/rules.py` 无被写入的全局量；30 组交错请求 0 组响应字节不一致；
>   同一载荷 20 次得到 1 个唯一哈希 → `compose/evidence/stateless-byteidentity.txt`）。
> - 正因为它无状态，"同一个会话打到不同副本"与"打到同一个副本"**结果完全一样**。
>
> **所以这个缺口的准确定性是：一个"当前无害、但会阻塞未来功能"的前置约束**，
> 而不是"现在正在丢数据"。

**它会在什么时候开始伤人（推断，非实测）**：

| 未来要加的东西 | 在无会话保持下会怎样 |
| --- | --- |
| 每会话的多轮上下文（记住用户上一次给的 request） | 同一会话第二次请求落到另一副本 → 上下文丢失 |
| 幂等键 / 去重（防止重复提交生成两组候选） | 两个副本各自维护去重表 → 去重失效 |
| 每会话限流 / 配额 | 配额在两个副本各算一半 → 实际额度翻倍 |
| 会话级缓存 | 缓存命中率按副本割裂，接近失效 |
| 依据会话选的灰度/实验分流 | 同一用户在不同副本进入不同分组 → 实验结论污染 |

**注意**：本线**没有**实现上述任何一个功能，因此**无法实测**这些后果。
上表是**基于无状态性已被证伪方向的反向推断**（"一旦引入状态就会中招"），
标注为**推断**，不作为"已测量"结论。

**若要在多副本下保持会话语义，需要什么**（三选一）：
1. **LB 层会话保持**（按 Cookie / 源 IP 哈希）——最省事，但副本故障时会话仍会漂移；
2. **把会话状态外置**（Redis 等）——真正解决，但当前服务根本不需要状态，属于为假想需求付费；
3. **坚持无状态**，把任何需要的上下文**每次请求完整带上**
   （当前 `/validate` 契约本来就是"请求自带 `request_json` + `candidates_json`"，
   即**已经**是无状态的，这也是当前最合理的答案）。

## 3. 实验 B：无 keep-alive 的代价（每请求都要 TCP 握手）

### 原始输出

```
==============================================================================
B. 连接开销 · 30 个请求，每个都单独建 TCP 连接（LB 讲 HTTP/1.0，响应后关闭）
==============================================================================
做法：先测量「connect+close 但不发请求」的纯握手代价，再与完整请求耗时对比。

  i   tcp_handshake_ms
------------------------
  1              0.526
  2             23.424
  3              0.676
  4              0.304
  5              0.258
  6              0.287
  7              0.392
  8              0.281
  9              0.206
 10              0.370
... （共 30 次，下面只汇总）

纯 TCP 握手 min/median/max ms : 0.206 / 0.343 / 23.424

复用尝试：在同一 socket 上连发两个 POST /validate（模拟 keep-alive）……
  第一个响应状态行        : HTTP/1.0 200 OK
  响应头里是否显式含 close : False
  第二个请求是否被处理     : False  (第二个响应 0 字节)
  -> 结论依据取「第二个请求的字节数」，不取 close 头：
     HTTP/1.0 默认响应后关闭连接，因此复用同一 socket 的第二个请求收不到任何响应。
```

### 结论

- **纯 TCP 握手（不携带任何业务数据）中位数 0.343 ms，最小 0.206 ms**；
  偶发 23.4 ms 的尖峰（WSL2 网络栈 + Windows 调度抖动）。
- **连接无法复用**：在同一 socket 上发第二个请求，收到 **0 字节**。
  这证明"响应后关闭"是事实，而不是靠响应头声明。
- **每个请求至少 2 次 TCP 握手**（客户端→LB、LB→上游），
  因为 LB→上游的 `http.client` 也是每请求新建连接。
- 用中位数估算：握手约占单请求总耗时（约 7 ms）的 **~5%**（客户端侧）+ 上游侧同类开销。
  ⚠️ **这是单机 loopback 的数字，握手极便宜**；
  在跨主机、有真实 RTT 和 TLS 的场景下，这个比例会显著上升——**那是推断，本线没测**。

### 结论

- 但 **0.150 s / 60 请求** 这个墙上时间与 p50=26 ms 之间存在张力：
  12 并发 × 26 ms ≈ 理论 60 请求需 130 ms，与 150 ms 吻合。数字自洽。

```
--- [4] 探测发现后再发 12 个请求 ---
  （12 条全部 attempt=1、upstream=validator-a:8000、4.0~26.4 ms）

  发生失败转移(attempt>1)的请求数 : 0 / 12
  最终仍然失败的请求数           : 0 / 12

--- [5] 最终 LB 计数 ---
{
  "requests_total": 24,
  "by_upstream": { "validator-a:8000": 24, "validator-b:8000": 0 },
  "failovers_total": 2,
  "upstream_errors_total": 2,
  "all_upstreams_failed_total": 0,
  "health": { "validator-a:8000": true, "validator-b:8000": false }
}

--- [6] 恢复副本: docker start giftwise-cloudnative-lab-validator-b-1 ---
exit=0 stdout=giftwise-cloudnative-lab-validator-b-1
  -> 副本 validator-b:8000 已重新被探测为健康
```

### 结论（诚实，含失败代价）

| 判据 | 实测 |
| --- | --- |
| 停掉一个副本后，请求最终是否成功 | **是**，24/24 成功，0 个最终失败 |
| 失败转移**免费**吗 | **不免费**。2 个受影响请求耗时 **1273.965 / 1280.862 ms** |
| 正常请求耗时 | 约 **4.0~5.3 ms** |
| 失败转移的代价倍数 | **约 250 倍** |
| 健康探测发现不可用所需时间 | **5.97 s**（独立线程实测，与批次耗时无关） |
| 探测发现后是否还会打到死副本 | **不会**，12/12 全部 attempt=1 |
| 副本恢复后是否重新纳入 | **是**，健康状态回到 `true` |

**为什么失败转移要花 1.3 秒？**（这是本次最有价值的发现之一）

`docker stop` 之后，容器内不再有监听进程，但 Docker 网络的 DNS 仍然解析得到那个容器 IP。
在这个 WSL2 环境里，连向该 IP 的 TCP SYN **被静默丢弃（blackhole）而不是被拒绝（RST）**，
于是客户端要等到 TCP 自己放弃（约 1.3 s）才知道上游死了。

> 这意味着：**"健康检查 + 失败转移"并不能把副本故障对用户隐藏**。
> 在探测发现之前的窗口里，大约每 2 个请求就有 1 个要多等 1.3 秒。
> 要真正把代价压下去，需要：(a) 缩短探测间隔；(b) **并行**探测而不是串行；
> (c) 减小上游连接超时（但要小心把慢请求误杀）；(d) 用连接池 + 主动探活。
> 本线**没有**实现这些优化，如实登记为已知限制。

**探测延迟为什么是 5.97 s 而不是探测间隔 2 s？**
因为健康探测循环是**串行**遍历上游的：探测 `validator-a`（快）→ 探测 `validator-b`
（**要 blackhole 约 1.3 s**）→ 然后才 `sleep 2`。所以一轮约 3.3 s，1~2 轮后才发现。
**上游数量越多，这个串行耦合越糟（线性放大）。** 这是本 LB 的设计缺陷。

  它把"永久挂住"变成了"10 秒后 408"。本实验**证实了这个修复生效**。

## 8. 扩容到底有没有用？—— CPU 密集还是 I/O 密集

这是本线最想诚实回答的问题。**分三步测，因为只看一步会得出错误结论。**

### 8.1 第 1 步：`validate()` 本身有多贵？

```bash
docker exec giftwise-cloudnative-lab-validator-a-1 python -c "…5000 次 validate()…"
```

```
  trial1: 5000 次 -> 205.94 us/次
  trial2: 5000 次 -> 170.87 us/次
  trial3: 5000 次 -> 190.39 us/次
  trial4: 5000 次 -> 262.75 us/次
  trial5: 5000 次 -> 189.22 us/次
  trial6: 5000 次 -> 187.90 us/次
  trial7: 5000 次 -> 189.22 us/次

最佳 = 170.87 us/次
单核理论上限 = 5852.5 次/秒
```

（`compose/evidence/cpu-cost-container.txt`；宿主上也测了一遍：最佳 157.54 us/次。）

### 8.2 第 2 步：一个**完整请求**又有多贵？（这一步推翻了我的第一直觉）

**关键方法学坑**（本线踩过并修正，必须写出来）：
用「两次 `docker exec` 夹一段 sleep」测空转 CPU 是**错的**——实测每次 `docker exec`
会给目标容器 cgroup 记上约 **17~21 ms** 的 CPU
（`compose/evidence/exec-overhead.txt`：连只跑 `sleep 900` 的容器，
两次 exec 之间也被记上约 34 ms）。正确做法是把整个测量塞进**一次** exec。

```bash
docker exec -i -e PROBE_REQUESTS=3000 -e PROBE_CONCURRENCY=8 \
  giftwise-cloudnative-lab-validator-a-1 python - < compose/lb/incontainer_cpu_probe.py
```

```
  完成请求              : 3000（HTTP 200: 3000）
  墙上时间              : 3.775 s
  吞吐                  : 794.81 req/s

  cgroup CPU 增量       : 7170362 us
  客户端(本进程)CPU     : 1787308 us   <- time.process_time()，含全部客户端线程
  服务端 CPU (相减)     : 5383054 us  = 5.3831 core-seconds
  平均占用核数(服务端)  : 1.426 core
  每请求服务端 CPU      : 1794.35 us

  其中 validate() 纯计算 : 170.87 us = 9.5%
  其余(HTTP/线程/socket) : 1623.48 us = 90.5%

  单核吞吐上限(按实测每请求 CPU) = 557.3 req/s/核
  单核吞吐上限(若只有 validate)  = 5852.4 req/s/核
  => 框架开销把单核上限压低约 10.5 倍
```

**这是本次最重要的性能发现：**

> **每请求服务端 CPU ≈ 1794 us，其中 `validate()` 只占 9.5%（170.87 us）；
> 其余 90.5%（1623 us）花在 HTTP 框架、线程创建、socket 收发上。**
> 框架开销把单核吞吐上限从 **5852 req/s** 压到 **557 req/s**，**低了约 10.5 倍**。

**必须说清楚"不是什么"**：本线曾怀疑是 stdout 日志路径，并做了对照实验
（同镜像，唯一差别 `--log-driver none`）：

| 配置 | 每请求服务端 CPU |
| --- | --- |
| `--log-driver json-file`（默认） | **1463.28 us** |
| `--log-driver none`（关日志） | **1445.77 us** |
| 差值 | **17.51 us = 1.2%** |

**关掉日志只省 1.2%，所以日志不是瓶颈。**
（本实验的第一版曾得出"日志占 34.9%"的错误结论，错因是 exec 开销污染了基线；
修正过程完整保留在 `compose/evidence/logdriver-vs-none.md`。）

**那 90% 到底是什么？** 本线只能确定它**不是**日志路径。
剩余部分来自每请求新建线程、`BaseHTTPRequestHandler` 的请求行/头解析、
socket 收发、Python 层逐请求调度。**要拆开需要逐个换成对照实现，本轮没做**——
因此这部分仍是**未分解的推断**，不作为"已测量"结论。

### 8.3 第 3 步：加副本真的能提升吞吐吗？

**这一步必须同时测"直连"和"经 LB"**，否则会把 LB 自己的瓶颈误读成"扩容没用"。

```bash
docker compose -f compose/docker-compose.yml -f compose/docker-compose.bench.yml up -d
python compose/run-scaling-experiment.py --requests 400 --label main
```

```
   并发        直连 1       直连 2       增益         LB 1       LB 2       增益
    1      110.74      98.52    0.89x        78.88      77.13    0.98x
    4      496.55     609.01    1.23x       369.02     424.47    1.15x
   16      301.08     329.39    1.09x       377.02     289.97    0.77x
   48      307.53     302.90    0.98x       214.52     274.08    1.28x
```

同时记录了尾延迟：

```
  直连 1 副本 / conc=16                  thr=  301.08 req/s  p50=  12.609  p95=  26.215  max= 1038.328  ok=400/400
  直连 1 副本 / conc=48                  thr=  307.53 req/s  p50=  13.966  p95=1031.530  max= 1248.522  ok=390/400
  经 LB 1 副本 / conc=48                thr=  214.52 req/s  p50=  44.500  p95=1037.424  max= 1090.536  ok=388/400
```

**诚实的结论（分四层）**：

1. **验证器是 CPU 密集的——但密集在框架开销上，不在业务逻辑上。**
   依据（**已测量**）：每请求服务端 CPU 1794 us，`validate()` 只占 170.87 us（9.5%）。
   所以"它是 CPU 密集"这个判断成立，但**归因必须落在框架**，不能落在 `validate()`。

2. **加副本在本机环境里没有可观测收益。**
   依据（**已测量**）：直连 1→2 副本的吞吐增益在各并发档位是
   **0.89x / 1.23x / 1.09x / 0.98x**，即**围绕 1x 波动**，没有近线性增长。
   如果副本真是瓶颈，应该看到接近 2x。**没看到，说明瓶颈不在副本。**

3. **瓶颈在"共享的单机网络路径"上（推断，但有强证据）。**
   依据（**已测量**）：并发 ≥16 时，**直连和经 LB 两条路径**的 p95 都同时飙升到约
   **1030 ms**，且吞吐**反而下降**（496 → 301 req/s）。
   两条**互不相干**的路径同时出现同一个约 1 秒的台阶，
   指向的是两者共同的底层——Docker Desktop 的 宿主↔WSL2 端口转发 + Windows TCP 栈。
   这个 1 秒台阶与实验 D 里观察到的 ~1.28 s blackhole 又高度吻合。
   ⚠️ **本线没有能力进一步定位到具体的内核/转发组件**，所以归因是**推断**。

4. **"扩容有用吗"的正确回答是：在当前环境里测不出收益，且原因不在副本。**
   也就是说：**不要把这次的 1x 增益理解为"验证器不能水平扩展"**——
   验证器无状态、可水平扩展（结构性上支持）；
   但在**这个单机测量环境**里，宿主机网络路径先饱和了，
   所以**扩容收益被环境掩盖了**。要测出真实扩容收益，必须换到多主机环境——
   **本线没有这个条件，故没有做。**

### 8.4 本线对"扩容收益"的立场

- **已测量**：单机环境下 2 副本相对 1 副本 ≈ 1x；峰值吞吐约 496~609 req/s（直连）。
- **已测量**：每请求服务端 CPU 1794 us，其中框架占 90.5%。
- **推断**：单机瓶颈在宿主↔容器网络路径，不在验证器。
- **未测量**：真实多主机/云端的扩容收益；真实跨主机 RTT 下的 keep-alive 代价。
- **因此本线不主张任何云端容量数字。**

## 9. 本 LB 的已知限制（自己的缺陷自己登记）

| # | 限制 | 后果 | 是否实测 |
| --- | --- | --- | --- |
| L1 | **单进程单点** | LB 挂了整套服务不可用 | 结构事实 |
| L2 | **健康探测串行遍历上游** | 一个上游 blackhole 1.3 s 会拖慢对其他上游的探测；上游数越多越糟 | 已测（探测延迟 5.97 s 远超 2 s 间隔） |
| L3 | **无 keep-alive** | 每请求 2 次 TCP 握手 | 已测（第 3 节） |
| L4 | **无会话保持** | 同一会话跨副本（当前无害，未来有害） | 已测（第 2 节结论②） |
| L5 | **48 并发下丢请求** | `经 LB 1 副本 / conc=48` 实测 **388/400**，丢 12 个 | 已测（第 8.3 节原始输出） |
| L6 | **无重试预算/熔断/限流** | 每个上游最多试一次；下游被拖慢会传导 | 结构事实 |
| L7 | **上游超时 15 s > 上游读预算 10 s** | 若把上游超时调小于 10 s，会把上游的 408 语义变成 LB 的 502，掩盖真实行为 | 设计选择，未做对照实验 |
| L8 | **没有真实 RTT** | loopback 上握手仅 0.2~0.3 ms，掩盖了 keep-alive 缺失的真实代价 | 环境限制 |
| L9 | **docker stats 与 cgroup 不一致** | 本环境 `docker stats` 把用量按 24 核归一化（同一容器 cgroup 报 10.7%，docker stats 报 0.26%），容易误读 | 已测（`exec-overhead.txt`） |

## 11. 本线**没测出来**的（照实写）

1. **没有多主机实验**：全部在单机 WSL2 上完成，跨主机 RTT 与真实网络分区行为未测。
2. **没有测出真实扩容收益**：单机环境掩盖了收益（第 8.3 节）。

4. **没有测会话语义被破坏的"实际后果"**：因为服务当前无状态，
   任何"上下文丢失"的后果都**无法在当前代码上复现**，只能列为未来风险（推断）。
5. **没有做长时间稳定性/内存泄漏测试**：本线单次最长负载 20 s。
6. **没有在 TLS / 鉴权 / 真实反向代理下测试**：LB 是明文 HTTP。
7. **没有测失败转移的并行化优化**：只测量了当前串行实现的 5.97 s，未做改进对照。
8. **健康探测的"上游数量放大效应"只做了 2 个上游**：`O(N)` 增长是推断，未做 3+ 上游对照。
