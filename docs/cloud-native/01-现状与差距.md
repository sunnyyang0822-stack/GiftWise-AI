## 1. 逐项对照

### 1.1 容器化 —— **有** ✅

**现状（已实测）**
- 单容器交付：`deploy/Dockerfile`，28 行，`CMD ["python","-m","deploy.server"]`（`deploy/Dockerfile:28`）。
- 非 root 运行：`useradd --uid 10001 giftwise` + `USER giftwise`（`deploy/Dockerfile:18-20`）。
- 环境固定：`PYTHONDONTWRITEBYTECODE=1`、`PYTHONUNBUFFERED=1`、`GIFTWISE_PORT=8000`、
  `GIFTWISE_BIND=0.0.0.0`（`deploy/Dockerfile:6-9`）。
- 自带 `HEALTHCHECK`（`deploy/Dockerfile:23`）。
- 冷启动到 `/healthz` 200（本线自测，3 次）：**0.714 / 0.823 / 0.719 s**
  （`compose/evidence/coldstart-memory.txt`）。
  任务书给出的既有记录是 0.750~0.939 s，**同一量级**。另有交付镜像的独立口径 **0.668 s（均值；0.635/0.688/0.681）**，见 `deploy/evidence/container-probe.md:168` 与 `docs/acceptance-criteria.md:265`。**本线 0.714~0.823 s 只作本线自测口径，不作为现行值。**
- 常驻内存（本线自测）：cgroup `memory.current` **19.03~20.89 MiB**；
  `docker stats` 报 **15.27~17.02 MiB**
  （两者口径不同：cgroup 含页缓存，`docker stats` 不含；任务书既有记录 14.45~17.08 MiB 与后者接近）。

**差距**
- 镜像里**打进了不该进镜像的文档与脚本**：`/app/deploy` 下含
  `README.md`(34 KB)、`observability-collection.md`(15 KB)、`preprod-plan.md`(15 KB)、
  `security-review.md`(18 KB)、`publish-to-uhost.ps1`(4.5 KB)（本线 `ls -la /app/deploy` 实测）。
  这些是给人看的文档，占 `/app` 188 KB 中的绝大部分。
- 只有一个 tag 别名追随 `latest`，**没有语义化版本标签**，也没有不可变引用。

**若上云需要什么**
- 用 `COPY --chown` 显式控制属主，或把文档排除在构建上下文外（`.dockerignore` 已排除
  `deploy/evidence`、`__pycache__`，但未排除 `deploy/*.md`）。
- 推送到镜像仓库并获得**真正的 manifest digest**（当前没有），滚更/回滚都依赖它。
- 多架构构建（若目标节点是 arm64）。

### 1.2 编排 —— **无** ❌

**现状（已实测/读代码确认）**
- **没有 K8S**：本机无 kubeconfig、无控制面、无节点；`compose/k8s/` 下的 YAML
  **从未被 `kubectl apply`**（见 `compose/k8s/README.md` 的未执行声明）。
- **没有多副本**：默认部署就是**一个容器**。
- **没有自动扩缩、没有服务发现、没有分布式状态**。
- 本线为了取数，**临时**用 Docker Compose 在单机上模拟了"2 副本 + 负载均衡"
  （`compose/docker-compose.yml`）。⚠️ 这**只是实验编排**，
  **不是**交付物，也**不代表**任何云端拓扑。

**差距**
- 缺少整套控制面能力：调度、自愈、滚动更新、副本管理、声明式配置。
- 缺少部署环境分层（dev/staging/prod）、缺少配额与资源隔离策略。

**若上云需要什么**
- 一个托管 K8S（如 UCloud UK8S）或"单机 + 容器运行时"的折中方案。
- **但见 `compose/k8s/README.md`**：本线结论是**当前阶段上 K8S 属于过度设计**，
  并给出了 5 条"什么条件下才值得上"的判据。

### 1.3 多副本与无状态化 —— **无副本，但"无状态"是分入口的** ⚠️

这一项任务要求"读代码确认当前是否真有进程内状态，不要猜"。**读代码 + 实测的结论分两层：**

#### 1.3.1 默认入口 `deploy.server`：**确实没有进程内可变状态** ✅（已实测）

**读代码确认**（依据交付镜像内的 `server.py`，sha256 `130cb065db68…`）：
- 模块级只有三个常量：`MAX_BODY_BYTES = 64 * 1024`（`server.py:21`）、
  `READ_TIMEOUT_SECONDS`（`server.py:40`）、`RULES_HASH`（`server.py:43-45`）。
  `RULES_HASH` 在导入时算一次，之后只读。
- 唯一的模块级可变对象是 `_LOG_LOCK = threading.Lock()`（`server.py:27`）——
  它是**互斥锁**，不承载业务状态。
- `validator/rules.py`（sha256 `1f389dad4c25…`，与 `/healthz` 自报指纹一致）
  模块级只有 `TAGS = frozenset({...})`、`AMOUNT = re.compile(...)`、`UNAVAILABLE = object()`，
  **没有被写入的全局容器、没有缓存、没有计数器、不读时间、不读随机数**。
- `validate()` 的自述就是"**纯函数**公开接口"（`validator/rules.py:254`）。

**行为实测**（`compose/evidence/stateless-byteidentity.txt`）：
- 把 30 组请求**交错**发给两个副本，比较响应字节：**0 组**不一致。
- 同一载荷重复 20 次：**1 个**唯一响应哈希。
- 附加自定义请求头不改变响应字节。

> ⚠️ 说明：上表 30 组里 seq 1~10 的哈希都相同，是因为**响应不回显输入**
> （响应体只含 `status`/`all_passed`/`errors`/`candidate_results`，见 `server.py:95-102,142`）。
> 该测试的有效性来自"同一 seq 下 A 副本 == B 副本"，不是来自"不同 seq 哈希不同"。

#### 1.3.2 非默认入口 `deploy.observable_server`：**有进程内状态** ❌（已实测）

- `deploy/observability.py:150-172` 的 `Metrics` 类持有大量**可变计数器**：
  `self.requests`（dict）、`self.errors`、`self.validate_results`、`self.error_codes`、
  `self.bytes_in_total`、`self.in_flight`、`self.metrics_scrapes`、延迟直方图等。
- 实测（`compose/evidence/statefulness-main.json`）：起 2 个可观测副本，
  经 LB 打 **40** 个请求，轮询**严格 20/20** 分发；
  两个副本各自的 `giftwise_http_requests_total{POST,/validate,200}` 增量分别是 **20 和 20**。
  **没有任何一个副本知道总数是 40。**

**差距**
- 默认入口无状态 ✅，但它**没有指标端点**（`/metrics` 默认 **404**，本线实测）。
- 有指标端点的入口**有状态** ❌，指标只能在**单副本**下才等于全局真相。
  一旦多副本，任何"读一个副本的 `/metrics`"的做法都会**少报约一半**。

**若上云需要什么**
- 二选一，且**必须先做选择**：
  - (a) 保持无状态，把指标改成**外部聚合**（Prometheus 抓所有副本后按 `instance` 聚合）；
  - (b) 把指标推到进程外（如 statsd/OTel collector），进程自身保持无状态。
- 明确哪些指标是**进程级**（`in_flight`、`rss`、`uptime`）——这些在多副本下
  **本来就不该求和**，应保留 `instance` 维度。

### 1.4 服务发现 / 负载均衡 —— **无** ❌

**现状（已实测）**
- 交付物**没有任何负载均衡器**。单容器直接 `-p` 发布端口。
- 本线手写的轮询 LB（`compose/lb/round_robin_lb.py`）**只是实验工具**，
  **不是交付物**，且它自己有一堆已知限制（见 `docs/cloud-native/02-本地模拟实验.md` 第 6 节）。
- 交付镜像内**没有** nginx/haproxy/traefik，环境里也装不了；
  所以本线刻意用**纯标准库**实现 LB，以保证评委能复跑。

**差距**
- 没有服务注册/发现；没有健康感知的流量分发；没有会话保持（本线实测确认**没有**，见第 2 节）。

**若上云需要什么**
- K8S 场景：`Service` + `EndpointSlice` + `kube-proxy`/Ingress；
- 单机场景：一个反向代理（如 nginx/Caddy）+ 上游健康检查；
- **无论哪种**，都要先解决 1.5 的探针语义问题和 `docs/cloud-native/04-可扩展性瓶颈.md`
  里的 keep-alive 缺陷，否则 LB 只是把缺陷放大到多副本。

### 1.5 健康检查 —— **有 `/healthz`，但它会掩盖半开连接缺陷** ⚠️

**现状（已实测）**
- `GET /healthz` 存在且返回 200（`server.py:105-107`），响应体为
  `{"status":"ok","service":"giftwise-validator","rules_source_sha256":"1f389dad4c25…"}`。
- 镜像自带 `HEALTHCHECK`（`deploy/Dockerfile:23`）。

**缺陷（本线亲测复现）**

任务书给出的既有记录是"健康检查窗口内 `/healthz` 延迟 0/16/0 ms 全绿"。
本线用**独立方法**复现并强化了这个结论——**关键在于分辨率的差异**：

构造一条**半开正文**连接：声明 `Content-Length: 100`，**只发 5 字节**，然后静默。
在这条连接挂着的整段时间里，持续探测 `/healthz`（直连副本 + 经 LB）。

实测结果（`compose/evidence/halfopen-main.json`）：

| 指标 | 实测值 |
| --- | --- |
| 探测次数 | 27 |
| `/healthz` 返回 200 的次数（直连） | **27 / 27** |
| `/healthz` 返回 200 的次数（经 LB） | **27 / 27** |
| `/healthz` 延迟最大值（直连 / 经 LB） | **27.829 ms / 27.762 ms** |
| 半开连接结局 | `HTTP/1.0 408 Request Timeout` |

半开连接的读超时精确值（`compose/evidence/halfopen-timeout-precise.txt`，3 次）：

```
trial1: 首个响应字节在 t=10.014s 到达 -> HTTP/1.0 408 Request Timeout
trial2: 首个响应字节在 t=10.013s 到达 -> HTTP/1.0 408 Request Timeout
trial3: 首个响应字节在 t=10.012s 到达 -> HTTP/1.0 408 Request Timeout
```

与 `GIFTWISE_READ_TIMEOUT` 默认 10 秒吻合（`server.py:40`，超时逻辑 `server.py:65,83-93`）。

> **结论**：`/healthz` 全绿**只证明进程活着**，
> **不能证明服务能在时间预算内处理正文**。
> 半开正文的连接会占满一个 handler 线程长达 **10 秒**，
> 而探针在这 10 秒里**一次都没有报警**。
>
> ⚠️ 分辨率提示：本线用的计时器是 `time.perf_counter()`（粒度 200 ns）。
> 若用 `time.monotonic()`，本宿主的粒度是 **15.625 ms**（`compose/evidence/clock-granularity.txt`），
> 毫秒级探针延迟会被量化成 0/15.6/31.2 的台阶——那正是"0/16/0 ms"这类读数更可能出现的原因。

**差距**
- 探针语义错误：把"进程存活"当成了"服务可用"。
- 缺少**就绪**与**存活**的区分（默认入口 `/readyz` 实测 **404**；只有非默认入口才有）。

**若上云需要什么**
- **不要**把 `/healthz` 直接当 readiness。至少应：
  - 增加一个能反映"handler 线程池未被占满"的就绪判据（例如在途请求数 / 线程数阈值）；
  - 或把探针指向一个**会实际消耗一次请求处理路径**的端点（但仍需谨慎，避免探针本身放大负载）；
- 配置 `terminationGracePeriodSeconds` 时，必须知道正文读预算上限是 **10 s**
  （单连接），所以优雅停机窗口必须大于它——见 `deploy/server.py` 补丁
  `compose/patches/graceful-shutdown.patch`（**只生成，未应用**）。

### 1.6 可观测 —— **有，但非默认入口，且未鉴权** ⚠️❌

**现状（本线实测）**

| 判据 | 默认入口 `deploy.server` | 可观测入口 `deploy.observable_server` |
| --- | --- | --- |
| 是否为镜像默认 `CMD` | **是** | **否** |
| `GET /metrics` | **404** | **200**（3585 字节） |
| `GET /readyz` | **404** | **200** |
| `GET /healthz` | 200（内容相同） | 200（内容相同） |
| 匿名 `GET /metrics` | — | **200** |
| 伪造 `Authorization: Basic Zm9vOmJhcg==` | — | **200** |
| 泄露内容 | — | `rules_source_sha256`、`python_version` |

- 可观测入口**确实随镜像交付**（`/app/deploy/observable_server.py`，15511 B），
  但 `deploy/Dockerfile:24-27` 的注释明确说明它**不是默认入口**，理由是
  `/metrics` 未鉴权。**这个风险判断本身是正确的、也是诚实的。**
- 但后果是：**默认交付路径上没有任何指标**。

**差距**
- `/metrics` **完全未鉴权**：匿名 200、伪造 Basic 也 200，且泄露版本与规则指纹
  （`rules_source_sha256` 与 `rules.py` 内容指纹一致，构成"规则指纹"信息暴露）。
- 没有追踪（trace）、没有结构化访问日志落到默认入口、没有告警规则。
- 指标与"是否有状态"耦合（见 1.3.2）。

**若上云需要什么**
- `/metrics` 加鉴权（或只绑内网/只允许采集器网段访问）；
- **默认入口**就要能暴露指标（否则云端采集器抓不到）；
- 接入 Prometheus + Grafana（或 UCloud 的托管监控），配置 SLO 与告警；
- 日志采集（当前默认入口只向 stdout 打一行 `log_message`，见 `server.py:144-147`）。

### 1.7 配置与密钥 —— **容器内没有任何密钥** ✅（读代码确认）

任务要求"读代码确认 API key 现在怎么放"。**逐处确认结果：**

**默认入口读取的全部环境变量（穷举，`grep -n "os.environ" server.py`）：**

```
40:READ_TIMEOUT_SECONDS = float(os.environ.get("GIFTWISE_READ_TIMEOUT", "10") or "10")
151:    host = os.environ.get("GIFTWISE_BIND", "0.0.0.0")
152:    port = int(os.environ.get("GIFTWISE_PORT", "8000"))
```

**只有三个环境变量，全部是网络/超时参数，没有一个是凭证。**

**可观测入口额外读取**（`deploy/observable_server.py:307-309`）：

```
GIFTWISE_BIND / GIFTWISE_PORT / GIFTWISE_HIDE_PY_VERSION
```

**可观测库额外读取**（`deploy/observability.py:420-422`）：

```
GIFTWISE_ACCESS_LOG / GIFTWISE_ACCESS_STDOUT / GIFTWISE_ACCESS_LOG_BACKUP_DAYS
```

**容器内实际环境变量（本线实测，筛 GIFTWISE/KEY/TOKEN/SECRET/PASS/API）：**

```
GIFTWISE_BIND=0.0.0.0
GIFTWISE_PORT=8000
GPG_KEY=7169605F62C751356D054A26A821E680E5FA6300
```

> `GPG_KEY` 来自 `python:3.12-slim` 基础镜像（Python 官方的构建签名密钥），
> **不是本项目引入的凭证**，也不构成安全风险。

**`.env.example` 的实际情况：**
```
MODEL_API_KEY=replace_me
DIFY_API_KEY=replace_me
```
但该文件**首行自己就写明**："仅示意变量名，**目前没有程序读取本文件**；后续以实际实现为准。
模型供应商凭证在 Dify 设置中保管，不放提示词或前端。"

**结论**：**模型 API Key 存放在 Dify 平台的设置中，不在这个容器里。**
校验服务是**确定性规则校验**，不调用模型、不访问外部网络
（`deploy/server.py:1-4` 的模块 docstring 明确声明）。因此：

- ✅ **这个容器是无凭证的**——它被攻破不会泄露模型密钥。
- ⚠️ 但 Dify 侧的密钥保管、轮换、最小权限**不在本线可验证范围内**，
  本线**没有**审计 Dify 的密钥管理（没有该平台的访问权限，也不允许消耗 Dify 额度）。

**若上云需要什么**
- 引入 Secret 机制（K8S Secret / UCloud 密钥管理）——**当前不需要**，因为无凭证；
- 一旦未来接入模型或数据库，**必须**改为从 Secret 注入，而不是环境变量明文；
- `GIFTWISE_READ_TIMEOUT` 与（补丁引入的）`GIFTWISE_SHUTDOWN_GRACE` 应进 ConfigMap。

     `docker rm -f` + `docker run -d … -p 0.0.0.0:${ServicePort}:8000`（`:57-61`）。
- **从未执行过**。既有取证记录 `deploy/evidence/raw/ps1-static-20261031-011731/ps1-dryrun-without-bypass.txt`
  显示：在某次"dry run"尝试中，该脚本**连加载都失败**了：
  ```
  File …\deploy\publish-to-uhost.ps1 cannot be loaded. The file … is not digitally signed.
  You cannot run this script on the current system. … UnauthorizedAccess
  ```
  也就是说，在当前 ExecutionPolicy 下，脚本**无法直接运行**；
  既有记录只能用 AST 静态解析去检查它（`ps1-static-check.json`：`PARSE_OK errors=0 tokens=392`）。
- **没有 CI/CD 平台**：没有 GitHub Actions / Jenkins / GitLab CI 配置，
  没有自动化测试门禁、没有自动构建、没有自动发布。

**差距**
- 没有自动化：构建、测试、扫描、推送、部署、回滚全靠手工。
- 发布方式是"把源码 scp 到目标机上**重新构建**"，而不是"构建一次、各处部署同一不可变镜像"。
  这直接导致**同一份源码在不同机器上可能产出不同镜像**，
  也就永远拿不到可复现的 manifest digest。
- 上传清单是**硬编码的 5 个文件**——如果新增模块（例如补丁引入的新文件），
  必须手工同步这个清单，否则远端构建会静默缺文件。
  （这个坑已经踩过一次：脚本注释 `:47-50` 记录 N-1 修复时补上了两个可观测模块。）

**若上云需要什么**
- 先改为"**构建一次、推送仓库、按 digest 部署**"，消除"在目标机构建"；
- 引入最小 CI：语法/静态检查 → 单元与验收测试 → 构建镜像 → 推送 → 部署 → 冒烟检查；
- 加上镜像扫描（漏洞/SBOM）；
- 保留 `-DryRun` 这种"不接触云资源就能检查参数组合"的能力——**这是原脚本的优点，应保留**。

## 3. 本线**没做到**的（照实写）

1. **从未在 UCloud 或任何公有云上执行过**；主机/EIP 采购与部署均未发生。
2. **没有审计 Dify 侧的密钥管理**——没有该平台权限，也不允许消耗额度。
3. **没有测试过 `deploy/publish-to-uhost.ps1` 的真实执行路径**（它需要一台可达的 SSH 主机；
   且当前 ExecutionPolicy 下它连加载都失败）。本线只做了静态阅读。
4. **没有在真实 K8S 集群上验证 `compose/k8s/` 的 YAML**（本机无集群）。
5. **没有做安全渗透测试**；`/metrics` 未鉴权是"用 curl 直接看到 200"这一事实，不是完整的风险评估。
6. **没有做多机/跨主机实验**——所有测量都在**单机 Docker Desktop (WSL2)** 上完成，
   因此**所有吞吐/延迟数字都不能外推到云端**（见 `docs/cloud-native/04-可扩展性瓶颈.md` 的说明）。
7. **`server.py` 在本线作业期间被其他工作流改动过**：本线开工时读到的是交付镜像内的
   `130cb065db68…`（164 行），作业期间工作区版本变为 `e8b40f9fd685…`（203 行，
   新增了 `Server` 子类把 `request_queue_size` 提到 512）。
   本线**所有测量针对的是交付镜像**（`d9a4a35763ee`），不是工作区当前版本。
   详见 `docs/cloud-native/04-可扩展性瓶颈.md` 第 5 节与 `docs/cloud-native/03-…` 的补丁基线说明。
