## 6. ⚠️ 如实登记：镜像内的 `deploy/server.py` 比工作区旧一处

```text
$ MSYS_NO_PATHCONV=1 docker run --rm --entrypoint sha256sum giftwise-validator:submission-20261101 /app/deploy/server.py
130cb065db6868c897308cbb79ef5cce16fcd323c94d958524aaf3e960c71076  /app/deploy/server.py
$ MSYS_NO_PATHCONV=1 docker run --rm --entrypoint wc giftwise-validator:submission-20261101 -l /app/deploy/server.py
164 /app/deploy/server.py

$ sha256sum deploy/server.py && wc -l deploy/server.py
e8b40f9fd685150510fe3af87611c635c1e5b23b4dd4628a5e399d1b907c42df *deploy/server.py
203 deploy/server.py
```

**性质**：调优线在交付镜像构建时刻（01:13:59）**之后**，给 `deploy/server.py` 加了一个 `Server(ThreadingHTTPServer)` 子类把 `request_queue_size` 由 `5` 提到 `512`，构建了**独立 tag** `giftwise-validator:perf-tuning-20261031`（`abe05f29df50`，11/11 重新验收 + 9/9 一致性通过），**未移动交付 tag**。

**所以**：镜像 = 工作区的**旧一处**（"镜像早于代码"），**不是**"镜像内容不明"。
**现场口径（一句话）**：
> 「交付镜像构建于 01:13:59；此后一条调优线在**独立 tag** 上实测把 `request_queue_size` 由 5 提到 512 可让**连接错误归零、p95 改善 2.7–6.3×、>1s 长尾消失**；因为该调优在容器化环境下 c=200 的无错吞吐增益只有 +4.6%（不稳健）且 p50 会从 ms 级升到百 ms 级（基线是用**丢请求**换来的低延迟），我们**没有在截止前替换交付镜像**——这是成本/风险控制。改动、证据与回滚手段都在仓库里。」

**可复跑判据**：上面两条 `sha256sum` + `wc -l` 命令本身就是判据。
**回滚/替换一条命令**（若决定改用调优镜像）：


## 7. 一条重要的工程事实（调优线发现，PM 登记）

`deploy/Dockerfile:16` 是 `COPY deploy /app/deploy`，**会把 `deploy/` 目录下的非代码文件一并烤进镜像**（`README.md`、`preprod-plan.md`、`security-review.md`、`observability-collection.md`、`publish-to-uhost.ps1`）。

实测后果：`giftwise-validator:perf-tuning-20261031` 与交付镜像的 5 个差异文件里，**只有 `server.py` 是调优线的改动**，另外 4 个是**别的线在 01:13:59 之后改的文档**被顺带带进去的。

**含义**：**只要 `deploy/` 下有非代码文件在被编辑，任何一次 `docker build` 都会静默改变镜像内容，而 tag 不变**——镜像因此**不可归因**。这既是我们决定「不在截止前零散重建」的技术理由，也说明 `publish-to-uhost.ps1`（一个**从未执行**的发布脚本）**确实存在于运行镜像内**（已知限制，见 `docs/competition/材料清单与自查.md`）。

**行为影响**：无（`/app/validator/**` 与 `deploy/*.py` 哈希未因这些文档而变化；`*.md`/`*.ps1` 不被 import）。
