## 0. 怎么用

### 0.0 复跑卫生（重要）

> **复跑卫生（重要）**：不要直接依赖默认的 `http://127.0.0.1:8787`——本机可能有**其它工作区**的服务占用该端口，且它可能**在复跑过程中被换掉**。权威复跑请**用自有端口**：
> ```bash
> cd web && GW_PORT=18789 node server/server.mjs &
> export GW_BASE=http://127.0.0.1:18789
> node web/tools/browser-check.mjs      # 100 项 / 0 失败
> node web/tools/smoke-http.mjs         # 59 项 / 0 失败
> node web/tools/page-probe.mjs         # 首帧正常、pageExceptions 0
> ```
> 三个脚本在开工前会**自动做服务身份自检**：比对服务返回的 `/landing.css`、`/` 字节数与本地 `web/public/**` 磁盘字节数，不一致就**以退出码 3 失败**并给出占用端口的真实 PID 与处置命令（`taskkill //F //PID <pid>`）。**看到 rc=3 说明你连的不是本工作区，不要采信任何数字。**

- **已实测到的隐患（2026-10-31）**：`browser-check.mjs` / `smoke-http.mjs` / `page-probe.mjs` 默认连 `127.0.0.1:8787`，而本次会话内 8787 的监听 PID **变了三次**（`41244 → 38692 → 28436`）——说明**别的工作区会反复重启该端口上的服务**。服务身份自检**能检出"测错工作区"，但检不出"服务跑到一半被换掉"**：一次跑到第 78 项会崩在"找不到 chip「生日」"，**这不是代码坏了，是服务在替换的瞬间被重启**。
- 因此：**凡引用 `browser-check` / `smoke-http` / `page-probe` 的数字，都必须连同"自有端口 + rc=0"一起给出**；rc=3 的跑批一律作废。

### 0.1 入口命令（四条）

```bash
# ① 快速档（默认，无需 Docker）：17 项，本机实测 32 秒（其中 9 秒是三项 FAIL 各重试一次的等待）
python tools/verify_all.py

# ② 完整档（含 Docker：镜像构建 / 容器内检查 / I-2 探针 / latest 现状）：21 项，本机实测 59 秒
python tools/verify_all.py --full

# ③ 单跑某一项（可重复，也可逗号分隔）：例如只看"19 个错误码"这一条声明
python tools/verify_all.py --only contract
python tools/verify_all.py --only i2_local --only range_contract
python tools/verify_all.py --only unit,parity,http_smoke

# 辅助
python tools/verify_all.py --list        # 列出全部检查名与归属档位
python tools/verify_all.py --no-retry    # 关闭"失败自动重试一次"（并发环境约定）

# ④ 指南自身也要能被验证：核对本指南 §0.4 结果表与归档 results.json 是否逐项一致
python tools/verify_guide_selfcheck.py
```

**退出码**：`0` = 无 FAIL（允许有 SKIP）；`非 0` = 存在 FAIL。
`FAIL` 表示**对外声明里有未达标项**，不是本工具故障；`SKIP` **绝不等于通过**。

### 0.2 结果表怎么读

每项一行，五列固定：**项目 / 结果 / 耗时 / 命令（截断） / 原始输出路径**。
- 命令在表里会被截断，**完整命令**在同一个归档目录的 `commands.txt` 里。
- 结果只有 `PASS` / `FAIL` / `SKIP` 三种；`SKIP` 在表下方单独列出**原因**。
- 失败项的原始输出**完整落盘**（stdout+stderr 合并），可直接打开；重试过的还会保留 `attempt1` / `attempt2` 两份。

### 0.3 归档（绝不覆盖历史）

每次运行新建 `docs/verification/runs/<时间戳>/`（同秒撞名自动加 `-2`、`-3`，**独占创建**）：

| 文件 | 内容 |
| --- | --- |
| `<检查名>.out` | 该检查**最终判定**那次尝试的完整原始输出（文件头写明最终判定与全部尝试记录） |
| `<检查名>.attempt1.out` / `.attempt2.out` | 每一次尝试的独立原始输出（重试时两份都在，**不改名、不覆盖**） |
| `results.json` | 结构化结果：每项的状态、耗时、完整命令、原始输出相对路径、备注、相关文件 mtime |
| `commands.txt` | 本次实际执行的**完整命令**清单（未截断） |
| `environment.json` | 时间、平台、Python/Node/Docker 版本、git HEAD、端口占用、关键文件 sha256 |

## 2. 逐条详解

每条给出：**声明原文（出处）→ 一条命令 → 预期输出 → 本次实测 → 这条命令不能证明什么**。
"不能证明什么"是刻意写的：避免把局部证据读成端到端结论。

## 5. 归档与复现

### 5.1 归档结构（append-only）

```
docs/verification/runs/<YYYYMMDDTHHMMSS+0800>/
├── <检查名>.out              # 最终判定那次的完整原始输出（含判定与尝试记录头）
├── <检查名>.attempt1.out     # 第 1 次尝试（重试时保留）
├── <检查名>.attempt2.out     # 第 2 次尝试（若有）
├── results.json              # 结构化结果（状态/耗时/命令/原始输出路径/备注/mtime）
├── commands.txt              # 未截断的完整命令
└── environment.json          # 环境、git HEAD、端口占用、关键文件 sha256
```

- **绝不覆盖**：目录名独占创建，进行中的运行不会写进别人的目录。
- 本次全量：`docs/verification/runs/20261031T005152+0800/`（21 项：PASS 15 / FAIL 5 / SKIP 1）。
- 另有几份**中间态**归档保留在同一目录下，可对照工具与工作区的演进：
  `20261031T004530+0800`（2 项，探针自测）、`20261031T004602+0800`（13 项快速档）、
  `20261031T004647+0800`（17 项，完整档首次跑）、`20261031T005437+0800`（17 项快速档，用于量快速档耗时）。

### 5.2 并发环境约定（8 条线共用同一工作目录）

- 某项 FAIL 时，工具会**先打印相关文件/目录的 mtime**（判断是不是别线正在写），**隔 3 秒重试一次**，两次的原始输出**都保留**；仍红才判 FAIL。
- 本次全量中 `browser_check`、`js_range_parity`、`stage_b` 三项都走了重试，**两次均红**→ 判为真实缺陷。
- 用例数会随各线新增而变化（实测：`boundary` 套件在 5 分钟内由 25 例变 45 例）。因此**判据一律是退出码 + 关键输出，不写死用例数**；指南里出现的数字都注明取证时刻。

### 5.3 复用既有服务（不重复拉起）

工具会检测端口：若 `127.0.0.1:8787`（接入层）或 `127.0.0.1:9333`（Chrome CDP）**已在监听**，就**复用**并在结果里明写"**复用既有进程（非本工具启动）**"；端口空着才自己拉起，并在结束时**清理**临时进程。

### 5.4 环境与依赖

- Python **3.12.12**（`D:\msys64\mingw64\bin\python`，**无 pip、无第三方包**）→ 这是本工具**只用标准库**的原因。
- Node **v24.21.0**；Docker **29.9.2**（client=server）。`docker.exe` **不在** bash 默认 PATH，工具会自行解析 `C:\Program Files\Docker\Docker\resources\bin\docker.exe`。
- 完整档会用 Docker，**但不动 `latest` 标签**（构建 tag：`giftwise-validator:verify-guide`）。

## 7. 维护约定（后续新增检查怎么接入）

1. **新检查进 `tools/verify_all.py` 的 `build_checks()`**：给出 `name`（`--only` 用）、档位（`FAST`/`FULL`）、说明、执行函数、以及**事先写死的判据**。
2. **判据必须来自对外声明**，不能来自"这项大概会过"。可选判据构造器：`exit_zero`、`exit_zero_and_contains(...)`、`contains_only(...)`（用于**退出码恒为 0** 的既有脚本）、`regex_only(pattern, expect)`。
3. **不要写死用例数**（各线随时加用例）；用退出码或关键结论行。
4. **FAIL 必须能被追到原始输出**：所有输出写进本次归档目录，失败项在结果表下方给出路径。
5. **SKIP 必须写原因**（"未跑 ≠ 通过"）；**不许**因为"预期会红/会绿"而跳过或改判。
6. 需要模型、Dify 控制台或外部网络的检查，一律 **SKIP + 原因**，不在本工具里重跑。
7. 发现**别人的**命令/文档有问题 → 写 `docs/verification/发现的问题.md`，**不代修**。
8. **本指南自身的一致性也要可验证**：改完指南后跑 `python tools/verify_guide_selfcheck.py`
   （核对 §0.4 结果表与归档 `results.json` 逐项一致、FAIL 都已登记、SKIP 都写了原因、原始输出都在）。
   它默认取最新归档，也可 `--run docs/verification/runs/<时间戳>` 指定。
