## 0. 一句话结论

**11-01 前：拿不到。11-01 后：有一条官方认可的路，但它的前提是"先把 GiftWise 做成导购站"。**

**为什么 11-01 前拿不到**：官方开放平台要么把个人挡在电商能力之外（抖音官方原文：个人身份只能建小程序/小游戏/小玩法），要么要求企业资质且审核周期本身就跨过 11-01（淘宝类目：企业实名 + 营业执照 + 5–10 个工作日）；第三方聚合里，唯一自助可买的"商品比价"接口**标注"维护中"且已从站内搜索与分类下架**，另一家真有全网比价 API 的（慢慢买）是**需商务对接的付费 B 端合同**；自建抓取在 2025-10-15 施行的《反不正当竞争法》"数据专条"下已有明确的民事（判赔 500 万）与刑事（有期徒刑 9 个月–1 年 2 个月）判例。

**但是——调研的最后阶段推翻了我原本"全部拿不到"的结论，也同时否掉了"那就接淘宝客"这个看似显然的答案。** 先说结论的两半：

**（一）确实有一条对个人开放、免调用费的官方接口**：淘宝联盟的 `taobao.tbk.*`。淘宝联盟 API 官方文档（TOP 文档中心，**2023/02/01**）原文写"**淘宝联盟API 面向所有淘宝客开发者**"，其准入条款中**通篇没有"企业资质"**，只有"阿里妈妈会员 + **网站/APP 备案审核通过** + **正确部署淘点金组件** + 权限包审核"，且"**默认开通的可自助申请，高级权限为邀约制**"。另有 2020/07/09 官方 FAQ、**四份阿里妈妈官方规范正文**与五篇 2025–2026 年第三方资料印证（详见 §2.3）。

**（二）但它对 GiftWise 的形态并不成立，"个人免费拿淘宝价格"是技术上不假、产品上不成立**：准入条款里的"**正确部署淘点金组件**"意味着**你得先把自己的站点做成淘宝客的导购站**；而阿里妈妈《工具服务商业务简介》把"拿数据做工具给别人用"这一档定义为**基础要求指向《如何换绑企业支付宝》**，并规定**原始数据明细未经书面授权不得向任何第三方披露**——**把商品价格/链接展示给用户，正落在这条的射程内**。此外还有**清退规则第 4 条**（API 权限用于非申请时提供的渠道 → 可直接关停）与 QPS ≤1 的额度限制。

**（三）并且在 11-01 前它一定来不及**：流程含**网站/APP 备案审核 + 权限包审核**，第三方给出的"审核 1-3 天"只是其中一步——**即便乐观估计也已跨过 11-01**。

**（四）附带更正一条我原先偏严的判断**：阿里妈妈《规范淘宝客引导过度比价行为的管理规范》治理的是"**消费者在推广者场景外已明确了购物需求、再来找券返利**"的**比价订单**，手段是**调低那一单的佣金**，而官方 FAQ 明确"**原则上推广者导购型推广行为不受影响（如达人卖货、导购推荐等行为）**"。**所以"比价"本身不是禁区，禁区是"不做导购、只想白拿数据"。**

**结论**：淘宝客是一条**真实存在、有官方文档支撑、但要求产品形态随之改变**的路——**它 11-01 前不能用，11-01 后能不能用取决于 GiftWise 愿不愿意做成导购产品**（见 §12 第 4 句）。它给的是**券后价/推广价**、**没有库存**。

**11-01 前建议采纳的降级方案：④ 用户自己填预算区间（首选）+ 可选粘贴商品链接/价格 ＋ ⑤ 内置种子价目表（冷启动兜底）**，价格一律携带 `source` / `source_url` / `fetched_at` / `confidence` / `is_verified`，估算值保持 `not_verified`（详见 §7.2）。

代价：**0 元 + 约 1–2 人日**，11-01 前完全可行。代价的另一面是产品能力受限——不能承诺"实时价格"，只能承诺"帮你把价格记清楚、把预算算明白"。

**数据契约结论**：`business_data_verification: not_verified`（理由见 §7.6）。这不是"暂时凑合"的值，而是当下**唯一诚实、且能被证据支持**的值——我们已核验的是**来源与时间戳**，不是**价格本身**。

**关键约束**：本环境 `web_fetch` 对本批站点报 `URL hostname resolves to a non-public IP address`（本机 DNS 被劫持），不可用；`curl` 不认系统代理（全部返回 `000`）。因此所有一手抓取都由一个自写的只读 `urllib` 脚本完成，每条记录含 `requested_url / fetched_at / user_agent / status / final_url / content_type / bytes / sha256 / charset / title / raw_text`。

### 1.2 证据分级（本文件全程遵守）

- **【官方原文】**：平台/政府/法院官网或平台自家静态页的一手文本，标 URL + sha256 + 字节数。
- **【平台一手】**：平台自己的帮助页/协议页，但可能年代久远，标注年份。
- **【第三方未核实】**：社区文章、聚合站二手转述，**不得作为决策依据**，只作线索。
- **【未核实】**：明确写出"没查到"，不猜。

### 1.3 一个必须写在最前面的失败

**淘宝 / 京东联盟 / 拼多多 / 抖店 / 得物 这五家的官方开放平台文档正文，本次没有全部拿到。** `open.taobao.com/doc.htm`、`union.jd.com/*`、`open.pinduoduo.com/*`、`op.jinritemai.com/*`、`open.dewu.com/*` 都是**客户端渲染单页**：HTTP 200，但 HTML 里没有正文。例如 `op.jinritemai.com/docs/guide-docs/1305/4043` 返回 18774 字节，正文关键词（营业执照/资质/个人开发者/企业/认证/审核）出现次数为 **0**。

唯一具备 JS 渲染能力的 `agent-reach` web 渠道当天被限流，所以这条路的正文只能靠"绕开正文"补齐——见 §2，最终从**服务端渲染的协议页与准入规则页**拿到了决定性原文。

**① "比价"这件事的官方态度，和第三方说的不一样——这是个好消息。**

- **数脉**：分类页 `https://www.shumaiapi.com/product` 的品类为：身份核实、运营商类、银行卡类、企业管理、OCR识别、交通地理、生活服务、AI应用——**无电商/商品比价分类**。最接近的《条形码查询》原文写"● 接口提供价格查询服务，帮助了解商品**参考价格**信息"，但同时写"**限企业实名用户使用**"——**个人用不了**。
- **APISpace**：`https://www.apispace.com/sitemap.xml`（53965 B）实测 **78 个 API** slug，无任何商品价格类；站内博客搜"比价"为 0 条。其"全部接口"页是 Next.js 单页（静态正文为"全部 (0)""正在载入..."），**因此结论的范围仅限 sitemap 收录的 78 个接口，不能 100% 排除站内存在未收录接口**。

### 3.4 慢慢买：唯一"真的有"，但它是 B 端商务生意

URL：`https://manmanbuy.com/a_148336.aspx`（《搜索比价API》，页面标注 **2019/7/4**）｜ 48378 B ｜ sha256 `a1b8e2df85d35b19…`

> 一、搜索API（灵活，适用于搜索、排序、筛选等功能）
> 这是核心 API，能满足以下2种使用场景：
> 场景一、**政府、企业采购方**想要在线上采买办公用品、工业用品。想要整合全网报价进行比价，选择低价渠道，节约资金。
> 场景二、**企业**想要做商品比价功能服务，类似于做一个"比一比价"这样的购物搜索系统。
> 二、报价读取API（传进来绑定的多个ID，读取最新价格）
> 这是个辅助API，配合搜索API的场景一使用，前端显示产品时，通过这个API获取最新的价格。

**但**：页面**没有单价、没有免费次数、没有实名要求说明、没有自助注册入口**。另据子代理用 Wayback 存档页（`data.manmanbuy.com` 现网 SSL 握手失败）取得的原文，它是"申请试用"→"工作人员会在 **1-3 个工作日**联系您"的**商务对接**流程。

→ 结论：慢慢买**确实有**可用的全网比价/价格监测 API，但它是**付费的 B 端合同生意**，不在"零费用"约束内；且它自己的数据来源表述是"公开商品信息"采集，**合规责任会传导到我们**。**不作为候选。**

### 3.5 Q2 小结

Q2 这条路**在"零费用 + 11-01 前"下不成立**：

1. 唯一具备该品类的聚合数据，两个接口都"维护中"，且已从搜索与分类中消失；
2. 极速数据、数脉、APISpace **根本没有这个品类**；
3. 数脉那个"含价格"的接口**限企业实名**，个人用不了；
4. 慢慢买**确实有**，但是需要商务对接与付费的 B 端合同，且数据来源自述为采集；
5. 即便有，也还要过"实名认证 + 应用场景审核"，且真实性依赖一句**我们无法自行核验**的"官方直连"自述——**我们不会把一个自己都无法核验的数据源接进产品**。

### 5.5 Q4 结论

把三件事分开看：

1. **技术上做得到吗？** 做得到——什么值得买首页（公开、无登录、无查询串，`https://www.smzdm.com/`，1257878 B，sha256 `2c6fccdbdc9e0849…`）实测含 **83 行带价格的文本**，例如：
   `102.8元`、`4799元`、`1450元`、`2149.8元`、`120元`、`279元`、`189元`、`323.33元返760积分后`。
   **但请注意这些"价格"的真实语义**——同一页面里的原文长这样：
   `20.46元（需用券）`、`16.14元（需买2件，需用券）`、`17.92元（折0.74一包，需买3件，需用券）`、`61.23元返60积分后`、`9899元（淘金币后9569.03元）`、`淘金币低至44.08元、88VIP：…`。
   也就是说：**这是"爆料价/券后价/积分后价/会员价"，而不是"商品页面上的标准售价"**。把它标成"真实价格"在语义上就是错的——它连"买一件要付多少"都不是一个确定的数。
2. **法律上干净吗？** **不干净。** 2025 年新增的数据专条把"避开或者破坏技术管理措施"直接写成不正当手段；本案域内已有 500 万元级判赔与实刑判决；而淘宝、京东的用户协议**明文禁止**爬虫抓取。
3. **产品上划算吗？** 不划算——价格是"爆料价/券后价"，语义上不等于"商品实时价"，还要承担平台封禁、协议违约与判例风险，**却只换来一个我们自己都不敢标 `verified` 的数字**。

**因此：不采用 ③ 公开页抓取作为生产价格来源。**（注意：这不等于"我们不能读网页"——人工查阅、用户主动粘贴链接均不受此约束。）

### 7.2 推荐方案（含 PM 指定的"产品侧替代设计"）

**主路径 = ④ 用户自己填/粘贴；冷启动兜底 = ⑤ 内置种子价目表（显式标注"估算·非实时价格"）。**

具体形态建议（按用户付出的努力从低到高排，**默认走第 1 条**）：

1. **用户自己填预算区间（首选，最省事）**——不问商品，只问预算：
   > "你打算花多少钱？（可以直接说区间，比如 200 左右 / 100–300）"
   拿到区间后，**用 ⑤ 的种子表**在该区间内给关系适配的品类建议，并显式标注：
   > ⚠️ **以下价格带为估算 · 非实时价格**，依据是公开礼物清单的常见档位，不代表任何商品当前售价。
   → **这条路完全不依赖任何外部数据源，今天就能上线，且不存在合规问题。** 它也最贴合真实决策：人在送礼时通常先有预算，再挑东西。
2. **用户粘贴商品链接或直接说价格**——系统**原样记录** `source_url` + `original_text` + `fetched_at`：
   > 用户：「https://item.jd.com/xxx.html 这个 299」
   > 系统：「已记录：299 元（由你提供，2026-10-31 01:12 记录）。本次按 299 元参与预算计算。」
3. **系统绝不主动做的事**（写成测试用例）：**不**去"验证"用户给的价格、**不**抓取该链接、**不**把它说成"最新价"、**不**从链接反推价格。

**为什么这仍然满足用户需求**（这是替代设计能不能成立的关键论证）：

| 用户真正要解决的问题 | 真实价格能帮上多少 | ④/⑤ 能帮上多少 |
|---|---|---|
| "该花多少钱"（预算焦虑） | 帮助有限——真实价格解决的是"这个多少钱"，不是"我该花多少" | **直接解决**：关系档位 × 预算区间就是答案 |
| "这个价位送什么得体" | 帮助有限 | **直接解决**：按关系 + 档位给品类 |
| "别买贵了" | 真实价格能帮上 | ❌ 帮不上——**必须诚实承认这一条我们不解决** |
| "有没有货" | 真实价格也不解决（库存是另一个数据） | ❌ 不解决 |

→ 结论：**礼赠决策的核心变量是"关系 × 预算 × 场合"，不是"实时价格"。** 真实价格只对"别买贵了"这一条有明显帮助——而这一条**恰恰是合规风险最高、且在当前约束下拿不到的那一条**。所以替代设计不是"退而求其次"，而是**把力气花在真正的决策变量上**；同时必须在产品里**明确告知用户"我们不替你查价"**，不能假装。

**⑤ 种子价目表的具体建议**（价格带全部来自 §6 的证据，落地时由产品线确认，此处只给可校验的起点）：

### 7.6 为什么最终选择 `business_data_verification: not_verified`

这是本报告的**最终结论**，也需要显式写进数据契约：

**理由一：没有任何一条路径能在 11-01 前产出"可核验的真实价格"。**
- 官方路线 ①a（商家 API / 值得买 / 抖店 / 拼多多）全部卡在**企业资质**上；淘宝类目审核 **5–10 个工作日**，即便今天递件也跨过 11-01。
- 官方路线 ①b（淘宝客）**是唯一对个人开放、且不要求企业资质的**，但它的准入条件是「**网站/APP 备案审核通过**」+「**正确部署淘点金组件**」——即**先把站点做成淘宝客导购站**；而"工具服务商"档**要求企业支付宝**、**禁止向第三方披露原始数据明细**。**它 11-01 前不可行（备案+审核走不完），11-01 后能否使用取决于产品形态决策。**
- 第三方聚合 ② 的两个比价接口**已"维护中"并下架**；真有 API 的慢慢买是**付费 B 端合同**。
- 抓取 ③ **技术上可行但不采用**（法条 + 5 个判例 + 协议明文禁止）。

**理由二：即便拿到，也不是"价格"，而是"券后价"。**
淘宝客返回 `zk_final_price`（折后价）与 `coupon_amount`（券面额），且明确**不提供库存**；值得买返回 `page_price` 但也带 `check_tips:"15分钟前自动检测有效"`（是**检测快照**，不是实时流）。**按 §8 的硬规则，这类数据不允许把 `is_verified` 置为 `true`。**

**理由三：把"未核实"写成"已接入"会同时毁掉两个东西——比赛的诚信底线，和我们自己的判断力。**
PM 的原话是"这是比赛的诚信底线，也是我们刻意保留的加分点"。本报告因此**刻意保留了失败**：21 个归档文件里 138 条记录中有 **15 条是失败记录**，`agent-reach` 的 `RATE_LIMITED`/`NEED_SETUP`/`UPSTREAM_BROKEN`/`TIMEOUT` 全部逐字存档。

**因此：`business_data_verification: not_verified` 不是一个"暂时凑合"的值，而是当下唯一诚实、且可以被证据支持的值。** 它的语义应当是：
- **已核验的是"来源与时间戳"，不是"价格本身"**——用户自填的价格我们记录 `source_url` + `original_text` + `fetched_at`；
- 估算值（种子表/模型）永远 `confidence = 'estimated' | 'unverified'`，**前端必须显式标注"估算 · 非实时价格"**；
- 一旦将来真的接上 ①b，**也只在满足"来源为官方开放平台 + 字段语义确为商品售价 + `fetched_at` 在时效内"三条时**，才允许把该条记录的 `business_data_verification` 提升为 `verified`。**淘宝客的券后价不满足第二条，接上了也仍然是 `not_verified`。**

## 8. `PriceProvider` 接口建议（给架构 #5 与产品 #11）

目标：**今天用 ④/⑤ 落地，明天换 ① 时不用改上层。** 上层只认这个接口，不认任何具体数据源。

```ts
/** 价格来源类型。新增来源时只加枚举，不改上层。 */
export type PriceSourceKind =
  | 'official_open_platform' // ①a 官方开放平台（淘宝商家/京东联盟/拼多多/抖店/得物/值得买）
  | 'taobaoke_affiliate'     // ①b 淘宝客 taobao.tbk.*（券后价；准入要求站点备案+部署淘点金组件，即"做成导购站"）
  | 'aggregator_api'         // ② 第三方聚合 API
  | 'public_page'            // ③ 公开页抓取（当前策略下不启用）
  | 'user_paste'             // ④ 用户手动粘贴  ← 当前主路径
  | 'seed_table'             // ⑤ 内置种子价目表  ← 当前冷启动兜底
  | 'model_estimate';        // ⑥ 纯模型估算

/** 可信度。UI 直接据此决定要不要打"估算"标记。 */
export type PriceConfidence =
  | 'verified'      // 有可核验的一手来源且未过期
  | 'user_provided' // 用户提供，原样记录
  | 'estimated'     // 区间估算（种子表）
  | 'unverified';   // 模型生成/来源不明 —— 前端必须显性标注

export interface PriceQuote {
  /** 数值。没有价格能力时返回 null，绝不返回 0 冒充。 */
  price: number | null;
  /** 价格区间（种子表/估算用）。price 为 null 时优先用区间。 */
  priceRange?: { min: number; max: number };
  currency: 'CNY';

  source: PriceSourceKind;
  /** 可点回的一手来源。user_paste 时是用户粘贴的原始链接；seed_table 时为 null。 */
  source_url: string | null;
  /** 取到该价格的时刻（ISO8601）。UI 必须展示它，或据此判断"多久之前"。 */
  fetched_at: string;

  confidence: PriceConfidence;
  /** 是否可对外当作"真实价格"声明。仅 verified 为 true。 */
  is_verified: boolean;

  /** 溯源用：用户粘贴的原文，便于人工核对。 */
  original_text?: string;
  /** 库存。当前所有来源都不可靠，默认 unknown；不得对外声明。 */
  stock?: 'in_stock' | 'out_of_stock' | 'unknown';
  /** 价格语义提醒，例如"券后价""需买2件""爆料价"。 */
  note?: string;
}

export interface PriceProvider {
  readonly kind: PriceSourceKind;
  /** 是否有能力处理这个输入；不能处理就返回 null，交给下一个 provider。 */
  resolve(input: PriceQueryInput): Promise<PriceQuote | null>;
}

export interface PriceQueryInput {
  /** 用户给的原始文本或链接。 */
  raw: string;
  /** 已知的商品标识（可选）。 */
  productId?: string;
  /** 预算档位，供种子表回退用。 */
  budgetBand?: { min: number; max: number };
}
```

**三条硬规则（建议写进代码注释与测试）**：

1. `is_verified === true` **只允许**由 `official_open_platform` / `aggregator_api` 产生，且 `fetched_at` 在约定时效内；**当前没有任何 provider 能满足，所以全站 `is_verified` 恒为 `false`。**
   ⚠️ 未来接入 ①b 淘宝客时注意：它返回的是 **`zk_final_price` 券后价**，`note` 必须写清"券后价/推广价"，且**不得**因为来源是"官方接口"就自动置 `is_verified = true`——语义对不上，`price` 就不是"这个商品卖多少钱"。
2. `price === null` 时**不得**用 `0`、`-1` 或任何哨兵值代替；用 `priceRange` 或直接说"不知道"。
3. `stock` 在当前阶段恒为 `'unknown'`，禁止渲染"有货/可购买"。**淘宝客接口不提供库存**，接入它也不会改变这一条。

## 9. 对外话术红线：接入了也不能说什么

即使**将来**接入了官方 API，以下声明依然禁止；在当前阶段更是绝对禁止：

| 不可以说的 | 原因 |
|---|---|
| "实时价格" | 即值得买的接口也带 `check_tips: "15分钟前自动检测有效"`——**它是检测快照，不是实时流**。只有 `is_verified && fetched_at 在时效内` 才可以说，且必须带时间戳。 |
| "这个商品卖 X 元"（把券后价当售价） | 淘宝客接口给的是 `zk_final_price` **折后价/推广价**（还要叠加 `coupon_amount` 券），它与商品页上的标价不是一回事。必须写成"券后价约 X 元（需用券）"，`note` 字段不许留空。 |
| "实时库存 / 有货 / 必然可购" | 库存查询依赖企业资质；且库存本身是**分地域、分渠道**的（值得买接口返回的是"各省份库存状态"，还带 `A 地区名称`）。**淘宝客接口根本不提供库存**。对个人用户的一句"有货"是不负责任的。 |
| "全网最低价 / 帮你买到最便宜的" | 我们没有任何全量比价数据源；且第三方数据自证能力为零。 |
| "价格已核实 / 保证准确" | 4.1 节开源项目的头号 issue 就是"抓取的价格与实际不符"。 |
| 把估算值当中性数字展示 | ⑤ 种子表与 ⑥ 模型估算**必须**带"估算/参考"标记，且 `confidence` 不得为 `verified`。 |
| 用爬虫拿到的价格对外展示 | 见 §5：协议明文禁止 + 判例在案。 |

**可以说的**：*"这是你提供的价格，我按它帮你算预算"* / *"这个档位通常在 X–Y 元（估算，仅供参考）"* / *"价格来自你粘贴的链接，{{fetched_at}} 记录"*。

1. **价格这件事，在 11-01 前只能做到"用户说的 + 我们估的"**，做不到"我们查到的"。请据此调整产品承诺。
2. **不要为了好看去接抓取或灰产聚合**：判例和协议都摆在那儿，代价是 500 万级的，而我们换来的只是一个自己都不敢标 `verified` 的数字。

4. **11-01 之后要申请淘宝客 API 是可以的，但请先回答一个产品问题，再决定要不要申请。** 官方规范写得很清楚：基础 API 的准入条件是「**网站/APP 备案审核通过**」+「**正确部署淘点金组件**」，也就是**你得先把自己的站点变成淘宝客的导购站**；而一旦你把商品价格/链接展示给用户，平台又会把你归入「工具服务商」档——那一档**要求企业支付宝**，并规定**原始数据明细未经书面授权不得向任何第三方披露**。

   （顺带更正一条：阿里妈妈《规范淘宝客引导过度比价行为的管理规范》治理的是"用户已决定买、只是来薅返利"的**订单**，手段是**调低该单佣金**，且官方 FAQ 明确"**导购型推广行为不受影响**"。**"比价"不是禁区，禁区是"不做导购、只想白拿数据"。**）

## 13. 本次调研自身的方法学教训（留给下一个做同类调研的人）

1. **JS 单页不等于"该平台查不到"**：淘宝的 `doc.htm`/`api.htm`/`faq.htm` 全是空的，但同一域名的 `businessDetail.htm`、`business.htm`、`solutions.htm` 是服务端渲染的，而且**恰好包含准入条件与审核周期**。遇到 SPA，先枚举同域下的静态页路径。
2. **官方协议页往往比官方文档页更好抓**：`terms.alicdn.com`（淘宝协议）、`mai.pinduoduo.com`（拼多多开发者协议）、`developer.open-douyin.com` / `partner.open-douyin.com`（抖音服务协议与入驻 FAQ）都是服务端渲染的。
3. **`robots.txt` 读不到，不等于允许也不等于禁止**——`www.jd.com/robots.txt` 会重定向到首页 HTML。此时必须回到用户协议与法律，而不是从"没读到规则"推断出"没有规则"。
4. **注意 gzip**：`jzt.jd.com` 的响应是 gzip，不解压会得到一屏二进制垃圾，并可能被误判为"抓取失败"。
5. **子代理的结论要复核一手**：Q2 子代理的每条结论本次都用同一脚本重抓验证过，其中两条（聚合数据站内搜索为 0、APISpace sitemap 78 个 API）是复核时才发现的更硬证据。
6. **别把"理论上可以"写成"可以落地"，也别把"官方开放"直接读成"我们能接"**：淘宝客路径本可以被写成"个人可以免费拿到淘宝价格"——**准入条款里确实没有企业资质，这句话字面为真**；但它的准入条件同时要求"站点备案 + 部署淘点金组件"，且展示商品数据会被归入要求企业支付宝的"工具服务商"档。**如果只读准入条款第一段就下结论，PM 会因此做出"那就接淘宝客"的错误决定。**
7. **取不到官方 JS 站的正文时，去找它的文档镜像站**。本次最关键的四份官方规范，全部来自 `api.alidayu.com/docs/doc.htm?treeId=713&articleId=…`——同一个 TOP 文档中心，`pub.alimama.com` / `open.taobao.com` 是 JS 壳，而这个镜像站是**服务端渲染**的。**同一份官方内容常有多域名镜像，攻击面（对我们来说是取证面）完全不同。**
8. **第三方说"X 是敏感词"时，要去读官方原文判断"敏感"的到底是什么**。第三方说"申请材料里'比价'是敏感词"，容易让人以为"平台禁止比价功能"；读到官方《规范淘宝客引导过度比价行为的管理规范》才发现，它治理的是"**消费者已决定买、只是来薅返利**"的**订单**，手段是**调低佣金**，且明确"**导购型推广行为不受影响**"。**二手信息会把"平台在管什么"和"平台在禁什么"混为一谈。**
