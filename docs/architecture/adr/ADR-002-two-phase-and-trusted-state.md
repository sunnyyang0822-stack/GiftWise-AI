# ADR-002：两阶段工作流 + 服务端可信快照

- 状态：**已接受**（2026-10-30）
- 关联：ARCH-001、`docs/architecture.md` §3.3／§6、`workflow/workflow-spec.md` §用户选择与呈现
- 关联成功标准：SC-5（选择前不生成呈现）、SC-7（跨阶段修订合计不超过一次且不可篡改）

## 背景与约束

1. 用户必须**自己选择**一个已通过校验的方案，系统不得替选（SC-5）。
2. 包装、配色、贺卡与赠送方式**只能在选择后**生成；选择前生成即违规。
3. 同一送礼任务跨两阶段**合计最多一次**自动业务修订，且**次数不可由前端篡改**（SC-7）。
4. **已实测约束**：Dify 单次工作流执行**不适合停下来等待网页交互**；SaaS 侧不能保存跨调用的可变状态（`trusted_repair_count` 目前只能由 Start 输入提供，WF-003 §6.5）。
5. 不能信任浏览器传来的 `passed`、价格、候选内容或 `repair_count`。

## 决策

**拆成两次按需执行**（推荐工作流 A、呈现工作流 B），并由**服务端持有可信快照**充当两阶段之间的状态载体：

1. 推荐阶段：接入层适配 → 生成 → 独立校验 → 最多一次修订 → 报告（`selected_candidate_id` 固定为 `null`）。
2. 服务端快照：以 `run_id` 为键保存不可变 `request_json`、两版候选、两次校验输出、**修订计数**、可选 ID 列表。
3. 选择事件：浏览器只提交 `{recommendation_run_id, selected_candidate_id}`。
4. 呈现阶段：服务端核对来源、候选 ID、通过状态与版本，命中才调用呈现；失败如实报告。

## 理由

- **状态放在能信任的地方**：Dify 是外部平台、浏览器是不可信输入，只有服务端同时满足"能写、能读、能校验来源"。
- **额度成为服务端状态**，前端无法重置；配合"进入修订即占用、超时与无效输出同样消耗、不回滚"（`workflow/runtime.py`），堵住"用失败换额度"的绕过路径。
- **两阶段天然对应产品语义**：选择前只做"三方案比较"，选择后才做"怎么送"；一次工作流无法表达这个等待点。

## 被否决的替代方案

| 方案 | 否决理由 |
| --- | --- |
| 单次 Dify 工作流内含等待/人工节点 | 平台不适合长时间等待交互；无法保证网页实时返回；额度与状态仍无处可信保存 |
| 让浏览器持有并回传候选与 `repair_count` | 直接违反 SC-7；已验证前端提交派生字段会被拒（`INTAKE_UNKNOWN_FIELD`） |
| 只重检前端回传的候选 | 重检只能证明"约束满足"，**不能证明来源与修订次数**（`workflow-spec.md` 明确禁止） |
| 引入数据库即持久化 | 方向正确但当前**未实现**；MVP 阶段先用进程内存，并把限制写清楚 |

## 后果

**正面**：可信边界清晰；SC-5／SC-7 有可断言的观测点（`selected_candidate_id` 必为 null、`call_counts.presentation` 在选择前必须为 0、`repair_count` 不由请求参数决定）。

**负面／风险（均已披露，未假装解决）**：
- 快照是**进程内存**：重启丢失、TTL 6 小时、上限 200 条；**多副本不可用**，无法声称生产级防篡改。
- 跨调用额度持久化**未实现**。
- 呈现阶段产品侧**未实现**；接入层仅有 mock 呈现。
- 无可信快照时只允许"受控操作员带入真实记录并重检"，且**必须标记为演示步骤**，不得声称网页闭环完成。

## 重新评估条件

- 接入层需要多副本或需要跨重启恢复（→ 引入共享存储，并保持同一 `run_id` 契约）。
- 呈现阶段上线（→ 补齐 P1–P4 与选择事件接口）。
- Dify 平台提供可持久、可校验的状态能力（→ 可考虑合并阶段，但额度仍应留在服务端）。
