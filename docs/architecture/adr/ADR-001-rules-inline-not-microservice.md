# ADR-001：确定性规则内联执行，而非独立微服务

- 状态：**已接受**（2026-10-30）
- 关联：ARCH-001、`docs/architecture.md` §3.1／§4.1／§4.2、成本性能清单 §6
- 关联成功标准：SC-3（规则校验独立于模型）、SC-9（失败不伪装完成）

## 背景与约束

1. 模型输出不可信，三个候选必须经**独立于模型**的代码校验（SC-3）；模型不得覆盖预算、天数与禁忌。
2. 同一套规则需要被三处使用：本地测试与回归、Dify 编排中的 Code 节点、以及（条件性）独立 HTTP API。
3. **已实测约束**：Dify Code 节点**无法 `import` 仓库模块**（WF-003 §3.2 实证），只能接收自包含源码。
4. 交付窗口约 35 小时，且多 Agent 并行开发，必须避免"同一语义多处漂移"。

## 决策

**规则以 `validator/rules.py`（Python 纯函数）为唯一语义权威；不把规则拆成独立微服务，而是内联到执行点。**

三处复用方式（同一语义）：

| 执行点 | 复用方式 | 实测证据 |
| --- | --- | --- |
| 本地测试/回归 | 直接 `import` 纯函数 | 46 探针 / 322 单测 / 39 阶段 C 全绿 |
| Dify Code 节点 | `workflow/build_code_node.py` 打包成**自包含单文件**（28,682–28,951 字符） | 7 个 Code 节点在 Dify Cloud 1.18.0 同时在线、保存并执行成功（WF-003） |
| 独立 HTTP API | `deploy/server.py` 直接 `import` 同一纯函数 | `/validate` 响应与本地 `validate()` **逐字段一致**（本次实测） |
| Node 接入层 | `web/server/checker.mjs` **JS 镜像** + parity 比对 | 55 组样例 **0 处语义差异**（本次实测） |

## 理由

- **实测性能差距决定取舍**：规则纯函数 p50 **0.166 ms**；而本机 HTTP 往返 p50 **12.545 ms**（约 75 倍）。把 0.166 ms 的计算放到网络边界之外，是明确收益。
- **"独立"不等于"独立部署"**：SC-3 要求的是**校验逻辑独立于模型**（不同执行者、不可被模型改写），而不是独立进程。Code 节点内联执行完全满足这一语义要求，还能顺带满足"不消耗模型用量"（实测纯 Code 工作流 0 Tokens）。
- **少一个部署面就少一类故障**：网络超时、鉴权、TLS、服务发现、并发治理都不再进入关键路径。

## 被否决的替代方案

| 方案 | 否决理由 |
| --- | --- |
| 规则只作为独立 HTTP 服务 | 增加网络与运维面；**已实测** HTTP 往返比计算慢两个数量级；且 MVP 无需独立伸缩 |
| 规则只用 JS 重写一份 | 会形成两套"权威"，且 Python 侧已有 322+39 项测试资产；JS 仅作为接入层镜像并以 parity 约束 |
| 规则交给模型自检 | 直接违反 SC-3 与"不得信任 LLM 自称通过" |

## 后果

**正面**：规则层可被信任为确定性、可测试、可哈希锚定；云端与本地语义可比对（哈希归一化后一致）。

**负面／风险**：
- 目前**存在两套实现**（Python 权威 + JS 镜像），一致性靠 parity 用例而非编译期保证——见 `docs/architecture.md` §9 A-4。
- 打包产物是"复制"而非"引用"，规则更新后必须**重新构建并重新导入**，否则云端与本地版本漂移（`manifest.json` 哈希即为此而设）。

## 重新评估条件

- 规则体积增长到 Code 节点上限（当前 28.9 KB 级，实测可保存执行，上限未知）。
- 接入层需要与 Python 侧严格同源（届时改为调用独立 API 或复用打包产物）。
- 出现需要跨语言、独立伸缩的第三方调用方。
