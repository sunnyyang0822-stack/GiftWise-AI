## 2. 测量方法（怎么做，含已踩过的坑）

### 2.1 时钟与分辨率（真实失败案例，务必沿用结论）

**首次**用 `time.monotonic()` 逐次计时，2000 次测量得到 min／p50／p95 **全部为 0.000 ms**——Windows 上该时钟有效分辨率不足（约 15.6 ms 粒度），亚毫秒调用被记成 0。

**修正后的标准做法**：
1. 用 `time.perf_counter()`（实测最小非零间隔 ≈0.1 µs）；
2. **批量计时**：每批 N 次整体计时，取 `(t1-t0)/N` 作为"每次调用"样本；本文件规则层用 N=100，链路用 N=50；
3. 报告 min／p50／p95／max／mean 与样本数，不只报平均；
4. 先预热再采样（HTTP 测量预热 10 次）。

### 2.2 分类测量口径

| 类别 | 口径 | 必须注明 |
| --- | --- | --- |
| 规则计算 | 纯函数调用，同进程 | 无网络、无并发、批量大小 |
| 接入层链路 | 进程内函数串联（适配→校验→报告） | 无 HTTP、无模型 |
| HTTP 传输 | 客户端 → 规则 API → 响应 | 是否复用连接、并发度、回环/跨机 |
| Dify 编排 | 服务端 `elapsed_time`（SSE / `workflow_finished`） | **是否含模型**、节点数、token |
| 模型调用 | 首 token 延迟与总时长需分别测；token 取 `workflow_finished.total_tokens` | 供应商、模型版本、上下文长度、输入/输出长度 |
| 端到端业务 | 用户点击 → 三方案可用 | 是否 mock、是否含模型、是否含呈现阶段 |

### 2.3 统计与异常处理（对齐评分规则对"测试次数、统计方式、异常结果处理"的要求）

- **样本量**：延迟类至少 30 次有效样本；报告 P50/P95 与最大值，禁止只报最好一次。
- **异常值**：记录并单独说明（如首次冷启动、GC、控制台 I/O 抖动），**不得静默剔除**；剔除必须写明规则与条数。
- **失败样本**：失败请求必须计入失败率，不得从延迟样本中删除。
- **环境绑定**：每条结果绑定机器、Python/Node 版本、Dify 版本、规则哈希（`rules_source_sha256`）。

## 6. 瓶颈判断与优化方向（**基于实测的推断，未验证**）

| 观察（已实测） | 推断 | 优化方向（未验证，需实测收益） |
| --- | --- | --- |
| HTTP 往返 p50 12.5 ms ≫ 纯函数 0.166 ms | 瓶颈在**连接建立与线程模型**，不在规则计算 | 连接复用（keep-alive）／线程池或异步服务器／必要时在进程内调用规则而非跨进程 |
| `ThreadingHTTPServer` 每连接起线程、无并发上限 | 高并发下会先耗尽线程而非 CPU | 设并发上限与超时；生产化时换 ASGI/WSGI 服务器 |
| Dify 工作流 0.587–0.888 s（7 个 Code 节点、无模型） | 多 Code 节点串联自身有固定开销 | 合并节点、减少 JSON 字符串反复序列化 |
| 确定性检查不消耗模型用量（注入轮 0 Tokens，纯 Code） | 规则层不是成本来源 | 保持规则在 Code 内执行，不要把确定性校验挪到模型 |
| 真实模型轮 **主批次 34,127 tokens（累计 38,326）**、N2 **4.5–6.0 s**、端到端 **5.2–8.9 s**，而规则层 p50 **0.166 ms** | **成本与延迟瓶颈在模型生成段，不在规则层** | 提示词质量直接影响成本：第 3 批修正提示词后首次即通过，token 从 3,811 降到 **1,614**（省掉一次修订）；控制输出长度、避免不必要修订 |
| 成本完全未知 | 无法做成本预算结论 | 模型授权后先测 10 次真实调用的 token 分布，再外推（并标注外推假设） |
