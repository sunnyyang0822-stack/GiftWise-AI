## 0. 结论（先行）

1. **只做了一件事**：把用户输入的自然语言解析成**仓库现有**的 intake 字段。字段清单、枚举取值、取值范围**全部由代码固定**（`web/server/intake.mjs:INTAKE_FIELDS` + `web/server/labels.mjs` 的标签表）；模型只能"把用户的话对应到这些字段上"，**不能新增字段、不能新增取值**，越界的一律丢弃并如实记账（`parse.dropped`）。
2. **不做多轮自由对话**：一次调用、一个严格 JSON、没有会话状态。
3. **用户没提到的字段不填**：模型输出里"没出现的键"＝用户没提到 ⇒ 保持表单原值或空/默认，并给出可核对的 `parse.untouched_fields`。**不用"常见值"补齐**。
4. **推断如实标记**：兴趣用契约里**已有**的 `interest_confidence: "inferred"`；契约里没有推断标记的字段，用一个**不进入 intake 对象**的 `parse.inferred_fields` 如实登记（最小改动，不改字段清单）。
5. **失败一律回落**：解析失败/超时/输出非法 ⇒ 用**用户原样提交的表单字段**继续跑，`status="degraded"` + `reason_code` + 中文说明，账本照记（含失败）。⛔ 不用猜测值顶替。
6. **不是后门**：解析结果仍是普通 intake 对象，必须再过 `adaptIntakeObject()` 与 `checker.mjs` 的同一套硬校验。实测：解析出的禁忌字面词照样能拦住候选；把关系解析成 `pursuit` 也照样触发「不得假定既有恋爱关系」的既有判定。
7. 四条产品裁定（文本优先 / 确定值±带宽且显示原值 / 喜好原文是硬约束 / 体验类问城市）**全部落地**，见第 3 节；每条都有可复现的测试用例。
8. 本次一并修掉了 6 个缺陷（必修 1–4、B1、B2），其中 **2 个是我在真实调用中自己踩出来的产品级故障**（第 3.2 节）：±1 天被错误实现成"准备时间必须≈N 天"，把 3 个候选全部判失败、用户一个方案都选不了。已修并补了回归用例。

**状态语义（前端按这 5 种分别处理，不要只看 HTTP 码）**

| status | 含义 | 前端应做 |
| --- | --- | --- |
| `ready` | 解析成功，且合并后的 intake 通过现有校验 | 把 `intake` 回填表单 → 用户确认 → 提交 `/api/recommendations` |
| `needs_input` | 解析出了字段，但现有校验判定缺必填项 | 按 `intake_validation.errors[].message`（中文）追问 |
| `empty` | **没识别出任何可落地字段**（含糊/无关） | 提示"没读懂，请补一句关系/场合/预算/时间"，**不要**显示任何猜测值 |
| `degraded` | 解析失败，已回落 | 直接用用户提交的表单继续；把 `notices` 里那句降级说明展示出来 |
| `disabled` | 服务端关闭了解析，或本次没有自由文本 | 完全按老流程走（不发模型调用） |

**错误码（`reason_code`，稳定机器码；中文说明见 `notices`/`llm.code`）**

| 码 | 触发 | 前端表现 |
| --- | --- | --- |
| `LLM_NOT_CONFIGURED` | 服务端没有模型凭证 | 降级；`llm.attempted=false`、`calls=0`（**一次调用都没发**） |
| `LLM_TIMEOUT` | 超时（不是业务失败） | 降级，可提示"稍后重试或先按表单继续" |
| `LLM_REQUEST_FAILED` | 网络/服务不可用 | 降级 |
| `LLM_HTTP` / `LLM_BAD_RESPONSE` / `LLM_OUTPUT_INVALID` | 上游非 2xx / 响应不合约定 / 输出不是严格 JSON | 降级 |
| `LLM_OUTPUT_TRUNCATED` | `finish_reason=length` **且还有残缺正文**（输出上限偏小） | 降级；提示可调大 `LLM_MAX_TOKENS` |
| `LLM_OUTPUT_REASONING_EXHAUSTED` | `finish_reason=length` **且正文为空**（推理 token 吃光额度） | 降级；与"接口坏"区分开 |
| `LLM_PARSE_EMPTY` | 解析成功但没识别出字段（`status="empty"`） | 追问，不显示猜测 |
| `LLM_PARSE_DISABLED` | 解析关闭 / 无自由文本 | 走老流程 |

**前端必须照做的 4 条交互（对应四条产品裁定）**

1. **显示用户输入的原值**：金额显示 `parse.echo.budget_amount`、时间显示 `parse.echo.deadline_days`。⛔ 不要显示 `"0–×××"` 区间（`constraints.*_band` 是服务端约束用的，不是给用户看的数字）。
2. **文本优先**：`parse.overridden_from_form` 非空时，说明"你在聊天框里写的**覆盖**了下面的选项"，并让用户看到覆盖后的值。
3. **必答追问**：`parse.required_followups` 里 `required: true` 的项必须先问（体验类问城市 `city`；期限矛盾问 `deadline_confirm`；不喜欢内容走既有的 `POST /api/exclusions/analyze`）。
4. **原文不得被预设类目替代**：`parse.literal_preferences` 要在界面上原样可见（它同时被写进 `additional_context` 并作为硬约束发给推荐模型）。

### 2.2 两种接法（都支持，任选其一）

- **接法 A（推荐，省一次调用）**：先 `POST /api/intake/parse` 拿到 `intake` 给用户确认，再 `POST /api/recommendations` 只传 `{ "intake": … }`。
- **接法 B（一步到位）**：`POST /api/recommendations` 传 `{ "natural_language": "<用户原话>", "intake": <当前表单> }`；服务端先解析再走原流程，响应里多一个 `nl_parse` 审计块（内容与 2.1 的 `parse` 同源）。
  - 解析结果不过校验时，`/api/recommendations` 返回 **400** + 现有校验错误 + `nl_parse`（不进入生成）。
  - 解析失败时 **照常继续**（用表单字段），`nl_parse.degraded=true`，通知里说明降级。
- 两种接法共用同一份结果缓存：键 = `sha256(schema|catalogue|model|text|form)`，TTL 10 分钟，并发同键只发一次真实调用。**注意**：`form` 不同就是不同的键（换一份表单会重新调用一次）。

## 3. 四条裁定的实现与测试用例

> 这一节是产品负责人 2026-10-31 四条裁定的**逐条落地位置 + 可复现用例**。测试文件：`web/tests/intake-parse.test.mjs`（27 条，全部通过）。

### 3.1 裁定 1：同时输入文本又选选项 ⇒ **以用户输入为主**

**实现**：模型**只看到用户原话**（`buildIntakeParseMessages` 的 user 消息里只有 `user_text` + 今天日期 + 代码生成的字段清单，**根本不含表单选项**）。合并顺序固定为「文本 > 表单」（`mergeIntake`），每处冲突写进 `parse.overridden_from_form`，并注明依据的裁定。表单里文本没说到的字段**原样保留**。

**测试用例**

- `文本优先于选项（裁定 1）：文本说到关系与预算就覆盖表单选项，并逐条记账` —— 表单 `friend/birthday/200-500`，文本说"对象，预算300" ⇒ 关系变 `pursuit`、`budget_range.max=350`、`overridden_from_form` 含 `recipient_relation` 与 `budget_range`；文本没提到的 `interests/occasion` **仍是表单里的值**。
- `口语化输入：字段映射正确，未提到的字段保持空/默认，推断项如实标记`。

**真实调用证据**（案例①，`31d45f639495c01c`）：故意把表单写成 `recipient_relation=friend / occasion=graduation / budget 200-500 / deadline 60 / interests=[tech_digital]`，用户原话是"我女朋友30天后生日…预算大概600吧…也很爱喝咖啡" ⇒ 7 条覆盖全部如实记录：

```
overrides: recipient_relation friend→partner, occasion graduation→birthday,
           budget_mode slider→other, budget_range {200,500}→{550,650},
           deadline_days 60→30, interests [tech_digital]→[coffee_food],
           interest_confidence {tech_digital:confirmed}→{coffee_food:confirmed}
```

### 3.2 裁定 2：确定金额/时间 ⇒ 显示**用户输入的那个值**；价格约束 ±50、天数约束 ±1 天

**实现**

- `parse.echo.budget_amount` / `echo.deadline_days`：**逐字回显用户给的值**（连说法片段 `budget_phrase`/`deadline_phrase` 一起回显），界面就显示这个值，⛔ 不显示 `0–×××`。
- 价格约束：`constraints.budget_band = [值−50, 值+50]`（贴边钳在契约的 0–10000 内）。**候选侧硬门**在 `pipeline.mjs:applyInputParseGates`，超出即 `PRICE_OUT_OF_BAND` 且 `passed=false`；上界同时被既有 `OVER_BUDGET` 兜住，因此实际生效区间是 `[值−50, 值]`（**更严，不会更松**）。
- 天数约束：`constraints.days_band = [N−1, N+1]`。**口径见下面的实测修正**：N 天是"期限"，±1 天只是容差；候选侧只对"总时长 > N+1"给 `DELIVERY_BEYOND_DAYS_TOLERANCE` 警示，硬门槛仍是既有到达规则 `准备+预售/发货+运输 ≤ 可用天数`。

**⚠ 实测踩出的产品级故障（已修，值得产品负责人知道）**

第一次真实全链（`code_revision 4ede7474ddbfac55`）时，我把 ±1 天实现成"候选准备时间必须落在 [29,31]"——因为用户说"下个月"(=30 天)，而候选的准备时间是 2/3/7 天，于是**3 个候选全部被判失败、`selectable=[]`、用户一个方案都选不了**。原始证据（`validation.input_parse_gates.findings`）：


**另一件事（模型不稳定，已加代码级交叉校验）**：同一句「下个月」，模型一次算出 30 天、一次算出 **1 天**（原始响应：`.tmp/ev-parse.json`，`deadline_phrase="下个月"`、`deadline_days=1`）。1 天的期限会把用户直接卡死。现在的处理是：**不静默改写模型给的值**（改写等于替用户猜），而是给出 `parse.deadline_check.ok=false` + 必答追问 `deadline_confirm`（含 `current_value` / `suggested_value`）。用例：`相对时间的代码级交叉校验：模型把「下个月」算成 1 天时必须要求确认（实测回归）`。

### 3.3 裁定 3：喜好填了文本 ⇒ **直接抓原文，不与预设选项匹配**

**实现**

- `parse.literal_preferences`：**逐字保留**用户原话（≤200 码点/条、≤20 条），不做任何"映射到预设类目"的动作。
- 原文落到**现有字段** `additional_context`（不新增字段）：`用户原话（硬约束，不得用预设类目替代）：…`，因此它会随 `request_json.notes` 一路带到第 2 步。
- 同时作为硬约束进推荐提示词：`pipeline → llmProvider.requestCandidates({inputParse}) → buildRecommendEnvelope` 里多一个 `input_constraints.literal_preferences`，提示词明确写"不许用预设类目替代"。
- 候选侧：候选文案里找不到原文落点 ⇒ `LITERAL_PREFERENCE_NOT_REFLECTED`。**默认是警示（不阻止选择）**，`GIFTWISE_LITERAL_PREFERENCE_GATE=1` 才升为硬 gate。理由：纯子串硬 gate 可能把 3 个候选全拦掉、把用户卡死（我在 3.2 已经真实踩过一次"用户一个都选不了"）。
- 禁忌的分工严格按契约：用户原话进 `hard_exclusions.terms`（**按字面拦**，实测能触发 `FORBIDDEN_TERM`）；模型提出的**类别**只作为 `parse.proposed_tags`（`needs_user_confirmation: true`）返回，**不写进 intake**（契约："类别不自动生成字面词，词不自动推断类别"）。

**测试用例**

- `裁定 3：喜好原文是硬约束 —— 原样保留、写进现有字段、并随推荐请求发给模型`（断言 `input_constraints.literal_preferences` 真的进了提示词文本）
- `裁定 3：原文里的话必须真的落进 additional_context（含表单备注时是合并而不是覆盖）`
- `gate：候选没体现用户原文 ⇒ 默认警示（不把用户卡死），可用环境变量升为硬 gate`
- `不是后门：解析出来的内容照样过现有硬校验（禁忌字面词能拦住候选）`

**真实调用证据**：`literal: ["她特别喜欢黑白色系的东西","也很爱喝咖啡"]`；`intake.additional_context` 末行 = `用户原话（硬约束，不得用预设类目替代）：她特别喜欢黑白色系的东西 / 也很爱喝咖啡`；三个候选里有 3/3 都真的体现了"黑白"（`gates.findings=[]`）。

### 3.4 裁定 4：「体验类」必须问所在城市；挑选时考虑地域价格

**实现**

- 命中体验类（`experiential_mentioned=true`，或兴趣含 `experiences_activities`、或风格含 `experiential`）且**用户没说城市** ⇒ `required_followups` 里加一条 **必答** 的 `city` 追问（含中文问句与理由）。
- 用户说了城市 ⇒ 写进 `additional_context`（`所在城市：杭州`），`parse.region_price` 给出档位（`tier1` / `new_tier1` / `other`），并**如实标注** `is_estimate: true`。
- **诚实的边界**：本地真实库 `products` 表**没有买家城市维度**（只有卖家所在地/发货地文本），所以**无法**按城市过滤或比价，也**没有**任何真实城市价格数据。因此地域价格只能做到：① 进提示词作为硬约束（`input_constraints.region_price`）；② 响应里明确标注 `is_estimate` 与"缺少买家城市维度"；并且**说明了**：`enforced_by: "提示词硬约束 + 响应标注；本地库没有买家城市维度，无法按城市过滤或比价"`。
- 城市档位表：一线（北京/上海/广州/深圳）+ 新一线 15 城（`REGION_PRICE_CONFIG`），**仅用于分档提示，不代表任何真实价差**。

**测试用例**

- `裁定 4：体验类必须问城市；给了城市就按城市分档且不再追问`（两条：无城市 ⇒ `required_followups[0].id=="city"`；有城市 ⇒ 不再追问 + `tier` 正确）

## 7. 账本口径更正（产品负责人 2026-10-31 的更正 + 本次实测）

1. **"一次成功的完整交互是 3 次大模型调用"这句话，在第 1 步接入之后要改成 4 次**：
   `intake_parse`（第 1 步解析）+ `recommend` + `style_direction` + `present`，且 `repair_count=0`，外加 **1 次生图**（生图不计入大模型账本，见下）。

## 9. 我没做什么 / 已知限制

### 9.1 没做

- ⛔ **没改前端**（`web/public/**` 一行未动）：接入契约写在第 2 节，需要前端负责人实现"原值回显 + 覆盖提示 + 必答追问 + 原文可见"这 4 处交互。
- ⛔ **没改 `checker.mjs`**（因此也没改 `validator/rules.py`）：天数 +1 天容差目前只是警示，见 3.2 待裁决项。
- ⛔ 没做多轮自由对话、没有会话状态、没有让模型直接生成最终 intake（始终是"模型给候选对应关系 ⇒ 代码校验合并"）。
- ⛔ 没有按城市过滤/比价：库里没有买家城市维度（只有卖家所在地/发货地文本）。地域价格只是**提示词硬约束 + 标注**，**没有任何真实城市价差数据**。
- ⛔ 没有动 `8903` 服务、没有 commit/push、没有跑 `e2e-live.sh`。
- 没有为解析加"自动重试整轮"或全局修复计数（输出格式最多重试 1 次，且截断不重试）。

### 9.2 已知限制

1. **模型对相对时间不稳定**（实测「下个月」= 30 天 / 1 天）：已加代码级交叉校验 + 必答确认，但**最终仍需用户点一下确认**。
2. **原文落点是子串启发式**（2-gram + ASCII 词，去通用词）：可能误判（例如用户原文"黑白"恰好出现在候选的无关描述里）。默认只做警示，就是为了不误伤。
3. **解析结果缓存键含 `form`**：换了表单就会重新调用一次（每次约 2–4 秒、约 3k tokens）。若前端"每次改动都调一次解析"，成本会上去——建议只在用户点"解读我的输入"时调用。
4. **体验类的地域价**：见 9.1 最后一条，属于"标注 + 提示"，不是真实数据。
5. **`empty` 不等于"用户没说需求"**：只是"这一段文本里没有可落地字段"；用户仍可继续手填表单。
6. **（观察，未查清、也非本次改动引入）共享真实库的 mtime 会被"以读写方式打开"触碰**：收尾时看到 `C:/Users/lenovo/Desktop/gw-opencli-db/.local-db/giftwise.sqlite` 的 mtime 变成 `21:56` 并出现 `-shm`/`-wal`文件，但**内容没有变**（只读复核：`products` 仍是 15 行、`collection_runs` 最新一条仍是 `run_mvwg7tn2_c2klt0 / 13:40:27Z`，`stats.total=15`）。`buildCatalog()` 用的 `openDb()` 是 `new DatabaseSync(file)`（默认读写模式），WAL 库在建/断开连接时可能做一次 checkpoint，从而只更新 mtime。
   - 我**没有**写库的代码路径（第 1 步解析只读库、只写内存 store），但**我不能百分百排除**"我的某次读打开触碰了 mtime"。
   - 建议后续单独做一件事：把**读**路径改成 `openDb(dbPath, { readOnly: true })`（本次没做：`openDb` 同时承担建表/迁移职责，改成只读会影响"旧库自动补列"的既有行为，属于超出本任务范围的风险）。

### 9.3 「已验证」vs「推测」

- **已验证（有原始输出）**：契约字段/枚举/范围不可越界；四条裁定；失败回落（真实网络失败）；截断拆码；账本隔离与逐字节不变；库路径单一来源与三种覆盖；全量测试 237/230/6；JS↔Python 校验器一致；一次真实全链（4 次大模型调用 + 1 次生图）。
- **推测/未验证**：
  - 地域价格的实际价差（无数据）；
  - 真实用户对"期限确认"这类追问的接受度（没有真实用户测试）；
  - 前端按契约接入后的实际体验（前端未改，未做端到端浏览器验证）；
  - `LLM_MAX_TOKENS=16384` 是否对所有模型都足够（只在 `deepseek-v4.1-flash-1017` 上实测：截断问题未再复现，最长一次 completion 4924 tokens）。
