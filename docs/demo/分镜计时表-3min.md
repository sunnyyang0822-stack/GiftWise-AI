# 3 分钟 Demo 分镜与计时表（对齐重写后的脚本）

> 本表按 PM 指定的四段时间轴组织：**0:00–0:30 开场与问题 / 0:30–1:30 四步输入 / 1:30–2:20 三方案＋规则门＋选择 / 2:20–3:00 选后四段呈现与收束**。
> 每一段都给出三样东西：**讲什么**、**屏幕应出现什么**、**时间上限**（超了就必须进入下一段，不允许靠压缩后面的内容找补）。
>
> 段落编号 `S1`–`S4`；每段末尾标注**该段是否依赖真实额度**（`额度依赖` 字段），供 PM 决定正式演示前要不要真跑。

## 0. 这份表替代了什么、没有替代什么

| 项 | 说明 |
|---|---|
| ✅ 本表做 | 给出**四段**时间轴、每段的讲稿要点、屏幕检查点、硬时间上限、以及离线兜底路径 |
| ✅ 本表做 | 明确标出**哪几段必须有真实模型**、哪几段可以纯离线演完 |
| ❌ 本表不做 | 不改 `docs/demo-script.md`（该文件由发布线重写，我只读） |
| ❌ 本表不做 | 不承诺「已联调成功」「价格/库存已核实」这类没有证据的事 |
| ⚠️ 与 `timeline-3min.md` 的关系 | 那份是 **15 秒粒度**的细表；本表是 PM 指定的**四段骨架**。两份并存，以本表的四段为口径，细表作为 S1–S4 的下钻 |

**术语**（后面反复用，先统一）：

| 名称 | 含义 | 现场怎么演 |
|---|---|---|
| **模式 A** | 在线主路径：真的打 Dify 已发布版本 #2 | 需要网络 + 额度 |
| **模式 B** | 混合：用**归档的真实链路**（`docs/demo/snapshot/demo-snapshot.json` 的 `archived_real_model` 块） | 不需要额度，但**必须口播**「本次没有发起新的模型调用」 |
| **模式 C** | 全离线：`docs/demo/replay/offline-replay.html`（`file://` 打开，零外部依赖）＋本机 mock 接入层 | 不需要网络、不需要额度、不需要 Dify |

**三条红线**（任何一段都不能破）：
1. 不把**模拟数据**说成模型真实输出。
2. 不把**未核实**的价格/库存/物流/外部可访问性说成已核实。
3. 不把**归档的历史运行**说成本次现场新跑。

## S1 · 0:00–0:30 开场与问题

**时间上限：30 秒**（含开场问候；超过 30 秒直接进 S2，不要再补产品背景）

### 讲什么（约 4 句，逐句控时）

| 秒 | 话术要点 | 备注 |
|---|---|---|
| 0–8 | 「送礼最难的不是买不到，而是**不确定**：不确定关系分寸、不确定预算、不确定会不会踩到雷。」 | 只讲问题，不讲技术 |
| 8–16 | 「GiftWise 只做一件事：**先给三个方案，由你选**，选完才生成包装、配色、贺卡和赠送方式。」 | 这句是产品形态，必须出现 |
| 16–24 | 「我们把**硬约束**从模型手里拿走，交给独立代码校验，模型不能绕过。」 | 这是与普通 Demo 的差异点 |
| 24–30 | 「三分钟，我走一遍真实路径。」 | 收口，准备切屏 |

### 屏幕应出现什么（检查点）

- [ ] 首屏可见，**品牌名 GiftWise AI** 在顶部
- [ ] 顶部**模拟标识可见**：文字为「模拟数据 · 未接真实模型」（amber 底色）
- [ ] 页面标题/定位文案完整，**无白屏、无布局错位**
- [ ] 浏览器缩放已按投影调好（建议 125%–150%，原因见 §5）

> ⚠️ **必须提前说明**（否则后面每一句都被质疑）：首屏那条 amber 标识是**页面级**提示，指的是「候选方案与四段呈现用的是模拟数据」；**不代表**输入表单是假的。S2 的表单和校验是仓库里的真实代码。

### 额度依赖

❌ **无**。这一屏是静态渲染，零模型调用。

### 离线兜底

模式 C：`docs/demo/replay/offline-replay.html` 顶部「开场与问题」区；或直接开 `docs/demo/shots/RES-1920x1080.png`（首屏截图）。

## S2 · 0:30–1:30 四步输入

**时间上限：60 秒**（这是四段里最长的一段，也是**最容易超时**的一段）

### ⚠️ 先解决一个口径冲突：「四步」还是「三步」

PM 指令写「四步输入」。**实测界面是三步**，证据：

- `web/public/app.js:148`：`const titles = ["第一步 · 关系与硬约束", "第二步 · 兴趣与风格", "第三步 · 排除与补充"];`
- 真实浏览器实测（本轮）：步骤条 `.step-pill` 返回 **3** 项，`state.step` 取值 `1/2/3`
- 截图：`docs/demo/shots/INPUT-23b-input-step3-filled.png` —— 屏幕上**只有三个步骤条**

**所以现场不能说「第四步」**。两种安全说法，二选一：

| 说法 | 适用 | 原话 |
|---|---|---|
| **A（推荐）** | 想保留「四步」的说法 | 「输入分**四个动作**：选关系场合 → **确认真实预算上限** → 选兴趣风格 → 排除不能送的。」屏幕上仍是三个步骤条 |
| **B** | 想完全不冒险 | 「输入分**三步**。」 |

> 建议用 **A**：既对上 PM 的「四步」，又不会和屏幕打架——因为「确认真实预算上限」是嵌在第一步里的一个**独立确认动作**，不是第四个步骤条。

### 讲什么（四个动作，逐动作控时）

| 秒 | 动作 | 话术要点 |
|---|---|---|
| 30–42 | **动作1 · 关系与场合** | 「选追求对象。注意这里写的是『不代表对方已接受』——我们不假定双向好感。」 |
| 42–56 | **动作2 · 确认真实预算上限** | 「区间只是快捷方式。真正提交的是我确认的明确上限，**系统不会替我补默认值**。」（**这是全段最重要的一句**） |
| 56–74 | **动作3 · 兴趣与风格** | 「可以跳过，跳过就按『未知』处理，系统不会替 TA 编喜好。」 |
| 74–90 | **动作4 · 排除与补充** | 「不能送什么，按类别选。这些类别会被**独立代码**检查，模型绕不过去。」 |

### 屏幕应出现什么（检查点）

- [ ] 三个步骤条可见，当前步高亮
- [ ] 第一步：选完关系后出现「**已选「追求对象」**」回显 + 关系契约说明
- [ ] 第一步：选完预算区间后，**金额输入框才动态出现**（`data-field="budget_amount"`）
- [ ] 第一步：金额框下方出现**显式确认复选框**，原文：
      「我确认「200.00 元」就是本次礼物＋包装＋贺卡＋装饰＋配送的全量上限（不再改由模型决定）。」
- [ ] 第一步：选完时间区间后出现天数框（`data-field="deadline_days"`）+ 第二个确认框，原文：
      「我确认可用的完整准备时间是 2 天（礼物＋包装＋贺卡＋配送合计），不是模糊期限。」
- [ ] 第一、二步切换后步骤条打勾（`第一步 · 关系与硬约束 ✓`）
- [ ] 第三步底部按钮为「**生成三个方案**」
- [ ] 顶部 amber 模拟标识**始终可见**（它 sticky，滚动也在）

> **两个显式确认是这段的"证据核心"**——它们证明「预算上限和时间不是模型决定的」，这是产品承诺，也是最容易被评委追问的点。

### 额度依赖

❌ **无**。输入与校验全部在本机完成（`/api/intake/validate`），零模型调用。

### 离线兜底

模式 C，两级：
1. **截图序列**（6 张，按顺序翻）：`docs/demo/shots/INPUT-20-input-step1.png` → `INPUT-21-…filled` → `INPUT-22-…step2` → `INPUT-22b-…filled` → `INPUT-23-…step3` → `INPUT-23b-…filled`
2. **真实校验结果**：`docs/demo/snapshot/demo-snapshot.json` 的 `local_real_rules` → **I-02** 块（真实拒绝路径，可现场读）

> 本轮已修掉一个**离线覆盖缺口**：原先快照**没有**输入阶段任何内容，`file://` 回放页无法演完 S2。现新增 **I-01**（三步表单 + 两个显式确认 + 6 张截图）与 **I-02**（真实校验拒绝），快照块数 19 → **21**。

## S3 · 1:30–2:20 三方案 + 规则门 + 选择

**时间上限：50 秒**

### 讲什么

| 秒 | 内容 | 话术要点 |
|---|---|---|
| 90–104 | 三个方案 | 「三个候选，各自给理由、事实引用和**不确定项**。」 |
| 104–122 | **规则门** | 「现在我把预算改成 250——**超了**。校验器直接判 `failed`，代码是 `OVER_BUDGET`。」 |
| 122–134 | 字面词与类别 | 「再加一个禁词『巧克力』→ `FORBIDDEN_TERM`；给候选打上 `alcohol` 标签 → `FORBIDDEN_TAG`。」 |
| 134–140 | 选择 | 「三个方案都合规，我选第一个。」 |

### 屏幕应出现什么（检查点）

- [ ] 三张候选卡片：**简洁杯具与杯垫 138.00 / 单品咖啡豆礼盒 118.00 / 无标识香氛蜡烛 128.00**（模式 A/B 的 mock 与真实运行的候选名不同，见下方⚠️）
- [ ] 校验器输出可见：`passed` / `failed` + 错误码
- [ ] 规则门演示时出错码**逐字**是 `OVER_BUDGET` / `FORBIDDEN_TERM` / `FORBIDDEN_TAG`
- [ ] 界面上「业务数据未核实」声明可见（`business_data_verification: not_verified`）

> ⚠️ **模式 A 与模式 C 的候选名不一样**：模式 C（mock）是上面那三个；模式 B（归档真实运行）是 **精品咖啡豆小礼盒 168.00 / 小型美食体验礼盒 188.00 / 咖啡主题实用小物组合 150.00**。**现场只能用一套**，翻到哪套就说哪套，不要混。

### 额度依赖

⚠️ **部分依赖**：
- **模式 A**：跑 `/api/recommendations` 需要**真实额度**（Dify N2 一次模型调用）。
- **模式 B/C**：零额度。规则门部分（`OVER_BUDGET` 等）**本身就是本机代码**，零额度。

### 离线兜底

模式 B/C。规则门直接看快照 **L-01** 块（本机真实校验器结果，含 `rules_source_sha256`）。

## S4 · 2:20–3:00 选后四段呈现与收束

**时间上限：40 秒**

### 讲什么

| 秒 | 内容 | 话术要点 |
|---|---|---|
| 140–160 | 四段呈现 | 「选完才生成：**包装 → 配色 → 贺卡 → 赠送方式**。」 |
| 160–172 | 关系差异 | 「同一个人，换成『恋人』，**贺卡和话术会变**——但包装不变，因为约束一样。」 |
| 172–180 | 收束 | 「所以这个 Demo 的重点不是好看，是**每一步都可以被检查、被拒绝、被追溯**。谢谢。」 |

### 屏幕应出现什么（检查点）

- [ ] 四段顺序为 `style → packaging → card → giving`（**配色在包装之后**）
- [ ] 「恋人 vs 追求对象」对比时，屏幕差异落在 **`card` 与 `giving`** 两段
- [ ] 收束时**不要**停在还在加载的转圈画面上

> ⚠️ **不要说过头**：实测（mock 数据）对比结果是 `style` 不同、**`packaging` 完全相同**、`card` 不同、`giving` 不同。所以**不能说「四段都会变」**。安全说法就是上面那句：贺卡和话术变，包装不变。

### 额度依赖

⚠️ **部分依赖**：`/api/presentations` 在模式 A 下需要额度；模式 B/C 零额度。

### 离线兜底

模式 C：快照 **M-01**（三候选 + 四段呈现）与 **M-02**（追求对象 vs 恋人差异）块，均已内联在回放页里。

## 2. 哪些段落**真的**需要额度（供 PM 决策）

**当前额度存量：13 次调用 / 38,326 tokens**（必须留到 11-01）。

| 段 | 纯离线（模式 C） | 需要真实额度（模式 A） | 一次真实运行的代价 |
|---|---|---|---|
| S1 开场 | ✅ 完全够 | 不需要 | 0 |
| S2 输入 | ✅ 完全够（含真实校验） | 不需要 | 0 |
| S3 三方案 | ✅ 归档可替代 | 要 N2 一次模型调用 | 归档实测 **1,413–1,614 tokens** / 4.4–6.5 s |
| S3 规则门 | ✅ **本来就是本机代码** | 不需要 | 0 |
| S4 四段呈现 | ✅ 归档可替代 | 要呈现阶段调用 | v2 两次运行合计 2,712 tokens |

**结论与建议**：

- **S1、S2、S3 的规则门**：**零额度**，无论怎么演都不消耗。
- **真正烧额度的只有两处**：S3 的「生成三个候选」和 S4 的「生成四段呈现」。
- 归档里**已经有 v2（版本 #2）发布后的两次真实运行**（`v2-run1-demo-summary.json` 6.065 s / 1,514 tokens / End A；`v2-run2-boundary-summary.json` 4.419 s / 1,198 tokens / End A），**足以支撑模式 B 完整演完 S3+S4**。
- ⚠️ **建议**：正式演示**默认走模式 B**（零额度），只在**确有把握**时留 **1 次**真实运行作为「模式 A 彩蛋」。若 PM 决定真跑，**最多消耗 1 次 / 约 1,600 tokens**，剩余 12 次 / 36,726 tokens 仍然安全。
- ⚠️ **本机无法预演模式 A**（已复现，非场地结论）：本机 HTTPS 整体不可用，`curl https://…` → `schannel: SEC_E_NO_CREDENTIALS (0x8009030e)`，Python → `CERTIFICATE_VERIFY_FAILED`。**因此模式 A 在本机从未跑通，不能声称"已预演"**。场地能否跑通属**未核实**。

## 3. 时间超支的处置（按段）

| 段 | 上限 | 超了怎么办 |
|---|---|---|
| S1 | 30 s | 砍掉「GiftWise 只做一件事」那句，直接进 S2 |
| S2 | 60 s | **只演动作 1 和动作 2**（关系和预算确认），兴趣/排除口头带过 |
| S3 | 50 s | 规则门只演 `OVER_BUDGET` 一个错误码，另两个口述 |
| S4 | 40 s | 四段呈现不逐个讲，只说「包装→配色→贺卡→赠送方式」，直接收束 |

**总原则**：宁可少演一个错误码，**也不要静默超时**——超时会被主持人打断，比少讲一点更难看。
