## 0. 设计原则（先把这条说清楚）

脚本第四节把 0:45–1:45 这一段设计成**真实模型调用**，兜底方案是"临时切归档"。
本轮真跑之后，我建议把实现方式**反过来**，但**不改变脚本的主路径定性**：

| | 脚本原设计 | 本文建议的实现方式 |
| --- | --- | --- |
| 心态 | 主路径真实跑；跑挂了切兜底 | 兜底是默认就绪的；真实跑是**加分项**，随时可以被"已归档的真实运行"顶掉 |
| 理由 | — | ① 本机实测 **HTTPS 整体不可用**（见 §4），模式 A 在本机**根本无法预演**；② 现场一旦开始等模型，3 分钟就被吃掉 6–9 秒且不可控；③ 归档素材本身就是**真实模型输出**，说服力不比现场跑低，且**不会失败** |

**这不是降低标准**：现场发起真实调用仍然是加分项，只是把它放在"如果我这边顺利，我多给你看一次真实运行"的位置，而不是"整个 Demo 的成败系于此"。

### 1.1 这一版时间轴的三个硬约束

1. **0:30–1:00 只有 30 秒给模型**。N2 实测 3.9–6.0 s，加上界面渲染还有余量；但**超过 8 秒必须切**，不许现场等。
2. **1:15–2:00 这 45 秒是全场最可靠的**。它零模型、零公网，本轮实测 6 项用例全过、单次 2–20 ms。**即使 Dify 全挂、断网、没有额度，这 45 秒照样演。**
3. **2:00–3:00 全部是模拟数据，必须两次声明**。本轮实测确认：页面顶部「模拟数据 · 未接真实模型」是 **sticky 常驻**的（滚动 1800px 后仍在视口内 top=22px）——但它只有 **12 px**，投影上有看不清的风险，见 §5。

## 4. 本机实测的模型可用性结论（决定了上述设计）

| 检查 | 实测结果 | 证据 |
| --- | --- | --- |
| 明文 HTTP 出网 | **正常**（`http://www.baidu.com` → 200） | `preflight.sh` §5 |
| **HTTPS 出网** | **不可用**。curl(schannel) → `SEC_E_NO_CREDENTIALS 0x8009030e`，exit 35 | 同上 |
| HTTPS（Python 另一套 TLS 栈） | **不可用**。`CERTIFICATE_VERIFY_FAILED: unable to get local issuer certificate` | 同上 |
| DNS | `cloud.dify.ai` → `198.18.0.94`（198.18.0.0/15 保留段）+ `fdfe:dcba:9876::58` | `nslookup` |
| 结论 | 本机处于**拦截式代理**环境，HTTPS 链不受信。**本机无法预演模式 A** | — |

**因此**：
- 本机**没有**做过一次真实的 Dify 现场运行。时间轴里 0:30–1:00 的"真实模型"一栏，本轮**未能在本机验证**。
- 这**不能推断会场网络同样如此**——会场可能是正常网络。
- 但正因为**本机无法预演模式 A**，模式 C 的兜底必须做到万无一失：这一点已通过 [`fallback-verification.md`](fallback-verification.md) 逐个验证。
- **零模型调用纪律**：本轮**没有**发起任何模型调用。时间轴里出现的一切"真实模型"数据，全部来自 `workflow/evidence/**` 的归档。
