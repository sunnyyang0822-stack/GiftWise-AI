## 一天内上线约束下的修订建议

用户补充：必须争取一天内上线，不采用人工精选，不把等待电商接口审批作为前置依赖。因此本节取代下文人工精选优先的执行建议；下文保留为长期路线比较。

建议改为按请求自动检索公开网页，读取商品页后提取品牌、型号／规格、参考价格和链接，再由服务端校验与模型匹配。首版定位为“具体商品 + 有出处的参考价格 + 查看来源／购买入口”，不保证电商结算价、库存或送达。若必须对任意需求都返回三件可立即购买且价格精确的商品，本次尚无证据支持一天内保证实现。

候选工具：

- Tavily：官方定价页说明注册后可从控制台取得 API Key，有每月 1,000 免费积分且无需信用卡；搜索文档支持域名限制和正文返回。这是可以当天尝试的自助路径，不是开通、目标网站覆盖或生产可用性的承诺。需验证部署环境访问、账号限制和实际结果。
- Firecrawl：官方说明提供搜索、页面读取及 schema 引导 JSON 提取，可用于自动获取页面品牌、规格和价格。JSON 格式约束不证明提取值真实，仍要保留原文证据；目标电商页可能无法取得有效内容。
- 博查：官网列出开放平台和 API 文档，可作为国内中文检索候选；本次未确认账号准入、当前配额和正文读取能力，不将其作为已经开通的服务。

一天内的最小链路：生成多个送礼方向及查询词 → 搜索召回 → 并行读取少量高相关商品页 → 提取并检查商品身份、CNY 价格与原文证据 → 去重并生成三个不同方案 → 代码核算预算及校验禁忌 → 用户选择 → 详细赠送指南。读取失败时不能用模型记忆补价。来源只有历史促销、搜索摘要或“元起”时不进入已绑定规格的精确报价池。

可以先优先选择能够公开读取的品牌商品页，不强制所有结果都来自淘宝／京东。品牌展示页可能只有介绍或二维码，不能误标为一键购买；商品信息来源和实际购买入口应分别保存。仅做短期缓存并按需积累记录，不需要先建全量商品库。

建议时间盒（工程安排建议，不是交付承诺）：首小时验证生产候选服务在实际部署环境的端到端检索和读取；对恋人、追求对象及朋友需求各做一次代表性试查。若拿不到足够的品牌、规格、价格证据，立即判定该数据路线未过关，不耗费半天继续堆集成。其后约 3–4 小时接检索、提取和证据校验，约 2–3 小时接三方案与现有规则，余下时间做真实闭环、错误处理与部署验收。全产品能否一天上线仍取决于前端、模型、部署等现有进度。

本次通用网页搜索试查发现：KINTO 中文商品页可读取 `SCS-S03 手做陶瓷马克杯 320ml` 和页面列价 `￥168.00`。这只证明公开网页能提供某些具体商品及标价，不证明当前结算价、库存、品牌站身份已独立核验或 Tavily／Firecrawl 能读到同样结果。另一次京东钢笔查询混入历史促销及参考价内容，说明必须过滤来源，不能将联网搜索等同于实时商品接口。

## 结论

最终推荐应绑定可追溯的商品记录：品牌、商品名、明确规格、销售店铺、购买链接、价格类型及核价时间。模型负责匹配需求和解释理由；商品身份和价格由数据源及服务端提供，不能靠模型记忆生成。

建议采用「精选真实商品库 → 接通一个商品数据接口 → 扩大来源」的顺序。具体品牌商品可以先通过人工核价实现，不必等待全网实时搜索；人工记录必须明确标为核价时的参考价格。

用户本次明确提出最终产品需要具体品牌、商品与价格。公开 Issue #1 和现有需求仍写着“实时商品集成后置”，应由 PM 依据此次要求协调定位和契约；本报告不修改共享契约或既有代码。

## 数据怎样取得

### 第一阶段：精选真实商品

建议先选取约 30–60 个具体商品规格，这是试验规模建议，不是已建成数量。优先覆盖恋人、追求对象和朋友场景；品类可从杯具、文具、书籍、兴趣周边等开始，不能据关系或性别假定喜好。

维护者打开品牌官方商店或可核验商品页，逐项记录品牌、型号、颜色、容量或套装数量、店铺、商品 ID／SKU、购买链接、当前页面价格、价格条件和核价时间。品牌或店铺身份不清、只有“最低 XX 元起”而无法绑定规格的记录，不进入精确报价池。商品图片优先使用数据源允许展示的素材；没有依据时先用文字卡片。

可先用 CSV／JSON 存储受控商品清单，不必立即建设复杂数据库。人工维护入口与商品数据读取层分开，后续更换来源时保持相同内部结构。

### 第二阶段：试接一个接口

1. 在官方平台核查个人／企业资格、应用审核、导购场景、当前搜索与详情权限；若选择第三方，确认其提供范围和使用条件。
2. 凭证只放服务端。通过独立数据适配层调用搜索、详情与链接接口，保留来源和抓取时间。
3. 搜索只用于召回；对入选商品再次获取详情，核实品牌、规格、价格类型和可购买链接。
4. 使用少量人工挑选的品牌商品做覆盖测试，记录有无返回、规格能否定位、报价是否一致、延迟、失败率和实际调用消耗。
5. 根据实测确定供应商，再扩充商品池。未通过准入或质量测试时继续使用明确标注的人工参考价，不伪装实时。

本次没有可据以承诺的接口费用、审批时长或 QPS。预算应按「每次推荐的搜索调用 + 详情刷新 + 选择时复核 + 缓存命中」估算，取得当前报价和实测数据后再定。

## 推荐链路

用户约束 → 构建多个送礼方向与搜索条件 → 商品召回 → 服务端标准化与硬筛选 → 模型从已提供的商品 ID 中组织三个不同方案并解释 → 服务端重新绑定商品与价格、计算全量费用、执行规则检查 → 三方案比较 → 用户选择 → 刷新所选商品报价并检查 → 生成详细包装和赠送指南。

“送礼方向”是内部规划，不提前展示为已核价商品。第一阶段三个最终选项都应绑定真实商品记录；找不到足够合格项时如实返回不足，不能编造第三件或偷偷放宽预算和禁忌。候选不足的状态需要 PM 协调现有“恰好三项”契约。

模型可以输出允许列表内的商品 ID、推荐理由和事实引用，名称、规格、链接及金额由服务端从可信快照填入。服务端必须拒绝不存在的 ID、跨候选替换和模型自行修改价格。

Dify 可以调用服务端商品搜索工具，或由接入层先检索再传给 Dify。为统一密钥、缓存、报价快照和错误处理，建议数据适配层归最小服务端接入层；离线 validator 继续保持纯函数，不增加联网行为。

## 最小数据结构建议

以下是待协调的字段建议，不是现有接口承诺：

| 分组 | 建议字段及含义 |
| --- | --- |
| 商品身份 | 内部 product_id、source、source_product_id、可空 source_sku_id、brand、title、variant、shop_name、product_url |
| 身份依据 | brand_source、shop_identity_evidence；缺失时不自行推断为官方旗舰店 |
| 报价快照 | quote_id、product_id、amount、currency、price_type、conditions、observed_at、fetched_at、expires_at、source_url |
| 不确定成本 | shipping_amount／shipping_status、包装及贺卡估算；未知运费不能用零冒充 |
| 履约 | stock_status、delivery_status、对应地区和观察时间；无数据保持 unknown |
| 礼赠属性 | category、forbidden_tags、标签依据及人工审查状态；模型标签与已证实的商品属性分开 |

商品记录与报价快照分开保存。同一商品不同店铺、规格或价格条件不能混成一个价格；原始快照仅在来源许可范围内保留。金额统一转换为十进制字符串或整数分，适配层核对来源单位，避免元与分混淆。

observed_at 表示实际观察来源价格的时间，fetched_at 表示本系统取得记录的时间；从旧缓存取得记录不能重置实际核价时间。expires_at 是本系统的新鲜度策略，不代表商家承诺价格在此前不变。

## 价格、预算和页面展示

- 默认优先采用已绑定规格、无需未知会员／新人／拼团资格的价格。条件价单列条件，不把券后最低价写成人人可得价格。
- 检查优惠券门槛、有效期和适用规格；同一优惠不重复扣减。不以划线价、定金或赠品规格的最低价代替礼物实际价格。
- 商品报价、配送费、包装／贺卡估算分开展示，并由代码加总。价格未知或运费未确定时不能宣称“已确认预算内”；可展示有明确说明的预留估算与待确认状态。
- 人工核价标为“参考价／核价时间”；接口返回标为“来源报价／获取时间／适用条件”，不承诺与用户结算页完全一致。
- 价格新鲜度可先试验按 15–60 分钟缓存接口报价、每天复核人工重点商品，具体值需服从供应商要求、变化速度和成本。此处均为策略建议，不是平台规则。
- 展示前和用户选择时检查报价有效性。选择时变价应让用户看到新金额；超预算或需要替换商品时重新校验并取得用户明确选择。
- 数据刷新本身不消耗业务修订次数；修改推荐或包装方案属于业务修订，继续遵守同一任务最多一次。额度耗尽时返回冲突，不能暗中启动第二轮修订。
- 库存与送达单独标状态。准备天数、发货承诺和实际送达不是同一件事；缺少地区相关履约依据时不能承诺“两天到”。

现有 `business_data_verification: not_verified` 不能仅因某个商品查到价格就改成全量已验证。建议新增逐项证据状态，由 PM 协调契约；规则通过与商品事实验证应独立表达。

## 接入验收建议

开发自测后仍需独立测试复核，至少验证：

1. 商品链接、品牌、店铺及所选规格相互一致；标题不能单独证明品牌真实性。
2. 模型虚构商品 ID 或篡改金额时被服务端拒绝。
3. “XX 元起”、赠品价、定金、会员价、失效券、满减门槛与多规格价格不会误用。
4. 运费未知、接口超时、空结果、商品下架及报价过期均有真实状态，不用零或虚构商品补齐。
5. 选择后变价、总额超预算和修订额度耗尽时保持可信状态，不自动替用户换礼物。
6. 三方案仍有不同思路；排名不直接由佣金高低决定，避免把送礼决策变成促销商品榜。
7. 留存脱敏请求／响应、报价观察时间、人工页面对照和实际运行结果；密钥不进浏览器、仓库或日志。
