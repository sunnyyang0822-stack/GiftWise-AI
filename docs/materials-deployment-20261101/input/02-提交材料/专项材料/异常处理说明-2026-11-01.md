## 1. 工具调用失败（含三态降级 ⭐）

**大模型调用失败**的失败形状稳定：`outcome="failed"` + 英文 `code` + `attempts` + `elapsed_ms`（`gw-live/web/server/llm/ledger.mjs:69-83`）。原始账本 `gw-live/.tmp/fe/ledger-feparse.jsonl` 第 8 行【实测】：

```json
{"at":"2026-10-31T14:19:39.119Z","kind":"intake_parse","model":"deepseek-v4.1-flash-1017",
 "base_url_host":"127.0.0.1:9","http_status":null,"outcome":"failed",
 "code":"LLM_REQUEST_FAILED","attempts":3,"elapsed_ms":783,"usage":null}
```

**第 1 步解析的三态降级**（`gw-live/web/server/llm/intake-parse.mjs:48-59`）——三态**各实测一次**【实测】（`gw-live/docs/architecture/前端接入第1步解析-2026-11-01.md:134-138`）：

| 态 | 触发 | 原始结果 | 是否卡用户 |
|---|---|---|---|
| `ready` | 正常原话 | `status=ready`、`echo.budget_amount="800"` | 不卡，直接补齐 6 项 ⇒ **3 个候选** |
| `empty` | 「随便啦，你懂的」 | `status=empty`、`echo` 全 `null` | **一个字段都不改**（停在原题不猜）⇒ 用户自己点完 ⇒ **3 个候选** |
| `degraded` | `LLM_BASE_URL=http://127.0.0.1:9/`（真实传输失败） | `status=degraded`、`source=form`、`reason_code=LLM_REQUEST_FAILED`、`attempts=3`、`intake` 与提交表单**逐字段相同** | 不报错、不要求重填，回落原表单继续 |

关键实现：`degraded` 时 `source="form"`，**没有用猜测值顶替、也没有把失败伪装成成功**（`intake-parse.mjs:846,887-931`）。

⚠️ **必须如实说明的边界**：`LLM_BASE_URL` 指向关闭端口时，**推荐那一步用的是同一个 LLM**，那一轮最终停在错误页、**出不了 3 个候选**（`前端接入…:149-156`）。「`degraded` ⇒ 仍能到 3 候选」是用 **`GW_MODE=mock`**（推荐路径可用）补证的：`parseStatus="degraded"` + `candidateCount=3`（`…:174-176`）⇒ **不得**说成「degraded 一定出 3 候选」。

**空态分级**（不糊成一个空数组）：`DB_MISSING` / `DB_EMPTY` / `NO_MATCH` / `NO_CNY_PRODUCTS` / `NO_PRICED_PRODUCTS` / `DB_UNREADABLE`（`localdb-real/catalog.mjs:71-91,193-200`）。

## 2. 模型输出异常

**输出截断（独立错误码 + 上限提到 16384）⭐**【实测】：

- 上限 8192 → **16384**（`config.mjs:130-133`）；**拆成两个独立错误码**——残缺正文 = `LLM_OUTPUT_TRUNCATED`，正文为空 = `LLM_OUTPUT_REASONING_EXHAUSTED`（`provider.mjs:74,79`；`llm/errors.mjs:22-27`）。
- **故意不重试**（`provider.mjs:215`「重试同样会截断，只会白花一次额度」，命中即 `break`）；账本同步带 `finish_reason`+`usage`+生效的 `max_tokens`（`ledger.mjs:79-82`）。

⚠️ **诚实边界**：独立验收当时判定「磁盘已修，但 8903 是旧进程、运行中未生效」（`独立验收-汇总…:381,396`）；**本文实测该边界已解除**（`stale_process:false`，见附 4），但**没有**实测「该进程真的截断一次并如实报码」。

**其他输出异常**：候选数不是 3 ⇒ `INVALID_CANDIDATE_COUNT`（`checker.mjs:715`）；坏 JSON ⇒ `INVALID_JSON`；合并后缺必填 ⇒ `needs_input`；**识别不出任何可落地字段** ⇒ 明确标 `empty`，**不瞎猜**（`intake-parse.mjs:53,54`）。

## 4. 状态恢复

- **运行快照是进程内存**：`store.mjs:14-15,18`（`RUN_LIMIT=200`、`RUN_TTL_MS=10 分钟`）。恢复路径是**「重新推荐」，不是「假装可恢复」**，**多副本不可用**（`gw-live/docs/architecture.md:265,274`）。
- **`/api/media/assets/<task_id>` 只在创建进程活着时可用，重启即 404 ⭐**：【实测】重启后旧 `task_id` 返回 `404 {"code":"MEDIA_NOT_FOUND",…}`；原因在 `server.mjs:418-425`：先 `store.read(id)` 拿 `run_id`，再 `getRun(stored.run_id)`，而 **`getRun` 读的是进程内存里的运行表**（外加 `owner_scope` 会话校验），重启后自然查不到（`修复-…:442-446,557`）。⇒ **复核这张图请用本地那份字节**（sha256 `72d2da06…a60e`），或让当前进程重跑一次全流程。
- **状态自证**：只有 `/api/catalog` 带 `process{pid, started_at, running_code_revision, on_disk_code_revision, stale_process}`（`catalog.mjs:177-179`）；`/api/config` **不带**。
- **幂等**：同一 `recommendation key` 重复请求命中即返回整份 report（`pipeline.mjs:249-250`）；同一选择重复点击命中 `store.mjs:53` 的 `selections` 缓存，不重复消耗额度。
