一页读懂

四个问题，四个答案。

GiftWise 是一个“模型负责理解与表达、代码负责把关、用户负责决定”的送礼决策助手。架构围绕这条分工展开。

一个可信服务端密钥、状态、校验与修订额度全部只在服务端
生成与校验分开模型出方案，独立代码逐项检查，最多修订一次
慢任务异步化文字先到，效果图后台生成、原位补上
负载

当前负载怎么承载？

负载是等待型的：时间几乎都花在上游模型上，本机 CPU 很轻。

  • Compshare 单实例：Nginx :80 反代到 Node 单进程，systemd 守护
  • 请求体 256 KB、有界检索队列、单次模型尝试 120 s 等闸门
  • 只为选中的方案生成 1 张图，控制最贵的调用
→ 详见 05 · 06
状态

状态放在哪里？

决策流程在内存，产物与账本独立落盘，浏览器只持签名会话。

  • 运行、排除分析、选择与会话签名在内存，重启后旧流程失效
  • SQLite、文字缓存、媒体、审计与账本落到 /var/lib/giftwise
  • 落盘文件保留，但不能据此恢复旧会话
→ 详见 07
伸缩

怎么扩缩容？

现在是单实例；多副本是后续计划，需先外置状态、签名、幂等与执行归属。

  • 公网单实例已跑通一条真实流程，容量未测
  • 扩展信号看在途模型调用与排队，而不是 CPU
  • 历史规则容器实验不代表全站多副本
→ 详见 08
恢复

出故障怎么恢复？

每类故障都就地接住：可重试的重试，不可重试的明确告知，生图失败不影响文字指南。

  • 网络错误有限重试，业务修订全链路最多一次
  • 检索受阻时复用合法历史文字；没有可用素材就如实返回
  • 重启后不自动重发生图，任务标为“执行未知”

为什么这样设计

每个选择，都换来一样东西。

下面六个关键决定，逐条写清我们选了什么、为什么选、付出了什么代价。

01
选择

单一可信服务端：Node.js 24 单进程，Nginx 反代、systemd 守护

理由
业务是“等模型”的 I/O 型负载，异步单进程即可承载当前使用；只用内置模块，部署只需 Node + Nginx + systemd，不引入 Docker / K8s，密钥只有一个落点。
代价
单点运行；流程状态在进程内存，横向扩展前需要先外置（见 08）。
02
选择

生成、检查、决定三件事分开

理由
模型不给自己打分：预算、禁忌、结构交给独立代码；用户只能在通过检查的方案里选，选择权始终在人。
代价
多一道校验与可能的一次修订，换来结果可预期。
03
选择

全链路业务修订最多 1 次，输出格式重试最多 1 次

理由
把最坏情况的调用次数和耗时封顶，成本与等待都可预测，不会陷入“越修越多”的循环。
代价
极少数情况一次修不好，就明确告知，不硬凑结果。
04
选择

选定后才生图，且异步：文字先返回

理由
出图是最慢、最贵的一步。只为选中的方案生成一张；指南复核通过即返回，效果图在后台生成、原位补上，读指南不用等图。
代价
需要任务状态与幂等机制：状态刷新只读，不会重新付费。
05
选择

推荐有据：模型调用检索工具，真实素材先进入模型

理由
查什么由模型结合上下文决定；服务端用 HTTP 获取公开文字素材并复用来源缓存，同一批素材可支撑多个思路，减少重复检索。
代价
多一轮工具往返；没有可用素材或依据无法确认时，如实返回而不硬凑方案。
06
选择

可信状态只留服务端，浏览器只持签名会话

理由
修订计数、候选、选择都不能被前端篡改；任务和图片按会话隔离，他人不可读。
代价
会话密钥随进程生成，重启后需要重新开始一次会话。
一句话模型负责理解与表达，代码负责把关，用户负责决定；慢的、贵的、会失败的，都放到不挡路的位置。

一次请求的生命周期

从一句话，到一份指南。

一次完整的送礼决策会经过六步。右侧是每一步的调用次数、公网单样本耗时与它写入的状态。

需求解析 模型

用户和小礼聊天，模型把原话映射为固定字段，保留喜好原话；缺的关键信息自然追问。解析失败时用表单原值继续，不卡住用户。

0–1 次写入：解析审计块（只做交代，不参与校验）

确认要避开的 用户

识别“不要什么”并请用户确认，得到排除分析记录，后续推荐与校验都以它为准。

分析 ID写入：排除分析（内存，10 分钟）

三个方案 模型 + 工具

模型结合完整上下文生成三个方案；调用检索工具，用匿名 HTTP 获取公开文字并复用合法历史摘要，素材先进入模型，再形成创意。推荐卡不配网络图片。

独立校验与一次修订 代码

负载的性质

等待型主要耗时
在上游模型

耗时主要是模型推理与检索的网络等待，服务端异步处理。部署机购买配置为 8 核 / 64 GB / P40，模型与生图走远端 API，配置不代表实耗；公网单样本不推断吞吐或 P95。

入口与上游的闸门

256 KB请求体上限，超出立即拒绝
4 / 3 并行有界检索队列；不等于全站硬并发容量
120 s单次模型尝试；前端普通 120 s、解析 60 s，Nginx 读 900 s，分别设置，不是统一 SLA
≤ 2 次网络重试，硬上限 3；线性退避 250 ms 递增
200 条运行快照上限，超出淘汰最旧，10 分钟过期
1 张每次选择只生成一张图；生图默认关闭，需显式开启
断开取消推荐阶段取消在途模型与检索；解析、呈现与后台图不保证随退出停止
调用预算可配置调用计数上限，默认未设；不是严格费用封顶

控制手段

重复提交同一请求命中幂等键，不会再跑一遍生成
素材缓存复用同批真实资料，减少重复检索
修订封顶，最坏情况的调用次数可算
所有阈值集中在配置层，可按环境变量调整

状态管理

按寿命分层，按会话隔离。

每一份状态都回答三个问题：放在哪里、活多久、重启之后还在不在。流程状态在内存，产物在独立目录；文件还在，不等于旧会话还能读取。

热 · 进程内存运行、排除分析、选择与会话签名：快、可淘汰；重启后旧流程失效。
温 · /var/lib/giftwise/runtime文字缓存、媒体任务与图片、审计、LLM 账本：独立落盘，文件跨重启保留。
独立 · /var/lib/giftwise/db本次独立 SQLite，启动器建表；不使用、不写原演示库。
状态放在哪里生命周期与上限一致性手段重启后
会话身份浏览器 Cookie（HttpOnly · SameSite=Strict）随浏览器会话；签名密钥由进程随机生成HMAC-SHA256 签名，恒定时间比较重新签发
推荐运行快照内存 Map10 分钟过期，最多 200 条，淘汰最旧候选、校验、修订计数只在服务端；选择须命中可选列表重新推荐
排除项分析内存 Map10 分钟过期，最多 200 条绑定会话；推荐时校验归属重新确认
选择与呈现缓存运行快照内随运行快照同一选择重复点击返回同一份结果随快照
生图任务runtime tasks/<id>.json长期保留ID＝sha256(运行, 候选, 计划版本)；独占创建，临时文件 + 重命名文件保留 *
效果图runtime assets/<sha256>长期保留内容寻址；读取时重算哈希，不一致即拒绝文件保留 *
素材缓存runtime 文件最多 80 条，7 天过期按来源去重，写入前脱敏，保留观察时间保留
模型调用账本runtime JSONL长期保留逐行追加（非事务）；测试进程自动改道保留
独立数据库db 目录 SQLite（node:sqlite）本次部署新建启动器建表；在线备份 integrity_check=ok保留

* 图片与任务文件留在磁盘，但读取仍要求内存中的运行与会话归属；重启后旧流程失效，重启恢复未验收。runtime 备份为同盘逐文件复制，非事务、未异地。

可信状态不出服务端浏览器提交修订计数等派生字段会被直接拒绝，只能提交需求与“选哪一个”。
按会话隔离运行快照、生图任务、图片读取都校验会话归属，别人的任务一律 404。
花钱的落盘生图任务先落盘再执行；重启后未完成的任务标“执行未知”，不自动重发。

扩缩容

先纵向，再横向，一级一级上。

现在是 Compshare 单实例，已跑通一条公网真实流程，容量未测。L1–L3 是计划，尚未实现；每一级都要先完成共享状态、签名、幂等与执行归属的复核，才能声明安全。

L0 · 现在

单实例 · 已部署

  • Compshare · Nginx · systemd
  • Node 单进程异步 I/O
  • 流程在内存，产物独立落盘

现状：一条公网流程已验收，容量未测

L1 · 计划

多实例 · 会话粘滞

  • 负载均衡按会话 Cookie 粘滞
  • 会话签名密钥改为共享配置
  • 媒体文件挂共享卷

触发：在途模型调用长期接近配额上限

L2 · 计划

状态外置 · 无状态

  • 运行、排除分析、选择放入带 TTL 的共享存储
  • 签名密钥共享；媒体任务条件写入与执行归属
  • 原子费用控制后，任意副本接任意请求

触发：需要滚动发布不中断、重启不丢会话

L3 · 计划

弹性伸缩 · 队列解耦

  • 生图与检索进任务队列，独立工作者
  • 按排队深度与在途调用数扩缩
  • 模型调用走统一限流

触发：峰值明显、生图排队超过分钟级

故障恢复

每一类故障，都有接住它的地方。

按“怎么发现 → 怎么处理 → 用户看到什么”逐条排开。原则：可重试的有限重试，不可重试的明确告知，生图失败不挡文字指南。systemd 自动重启已配置；故障注入、重启恢复与回滚演练未测。
