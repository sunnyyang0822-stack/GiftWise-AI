# 开发流程：四线并行，分批集成

定位唯一来源为[产品定位 Issue #1](https://github.com/sunnyyang0822-stack/GiftWise-AI/issues/1)。产品负责人决定产品方向；PM 负责任务、共享契约、集成和验收。推荐阶段离线校验器已通过开发自测、阶段 B 套件和 PM 复核；其他能力按各任务的实际交付证据判断，不能由校验器通过推定完成。

**总控流程以[项目总控 Issue #4](https://github.com/sunnyyang0822-stack/GiftWise-AI/issues/4) 的「阶段 1–14」为权威**，下表是本文件的执行细则，不与阶段编号冲突。阶段门禁：**阶段 1–6 必须先完成并冻结契约，阶段 7–8 才可并行；阶段 9–11 在接口交付后执行；阶段 12–14 依赖真实运行闭环与提交要求。** 阶段 1 的需求冻结件见 [`docs/requirements-analysis.md`](requirements-analysis.md)；未决项在该文件第 9 节集中跟踪，不得由各线自行认定。

## 简单流程

PM 确定定位与接口 → 前端、规则、工作流、测试四线并行 → 开发自测交付 → 独立测试 → PM 集成 → 产品负责人体验验收 → 版本冻结与演示。

| 固定名称 | 工作与文件边界 | 交付和依赖 |
| --- | --- | --- |
| GiftWise｜前端开发 Agent | 中文表单、三方案对比、用户选择、赠送指南、加载/错误；`web/`（已交付：100 项浏览器验收 / 0 失败） | 先标记明确的模拟数据，接口确定后接入；同时负责最小服务端接入层的实现，具体目录由任务单确定 |
| GiftWise｜规则开发 Agent | 纯 Python 校验器、错误代码、选择后费用与时间复核；`validator/` | 第一任务仅推荐校验；完成后再承接呈现校验。先不加 API / 云部署 |
| GiftWise｜工作流 Agent | Dify 节点、生成和修订提示词、呈现阶段；`workflow/` | 先验证模型连接，按契约配置，接真实规则，不能伪造 DSL |
| GiftWise｜测试验收 Agent | 独立测试、缺陷和回归；`docs/test-plan.md`、`tests/acceptance/`、`docs/test-reports/`（均已创建并入库） | 先设计案例；依实现到位开展离线、Dify、前端和部署测试；报告真实证据 |

规则开发自测使用 `tests/test_validator.py` 和 `tests/test_cases.json`；独立测试不同时改这些文件，需增补时先协调。前端接入层负责安全调用 Dify、可信任务快照和全局修订计数，不让浏览器持有密钥或篡改状态。若必须增加独立 API 或云部署，PM 另开有边界任务并指定负责人，避免两个 Agent 各建一套后端。

## 集成和验收规则

每次交付给出任务编号、修改文件、实际命令与结果、限制和阻塞。开发 Agent 自测后，测试 Agent 独立复核；失败回原负责人修复，测试回归后由 PM 集成。产品负责人只需确认推荐和中文体验，账号操作由负责 Agent 提供逐步指引。

共享字段、文档或文件归属变更先交 PM 协调。并行聊天优先使用独立分支或工作树；同一工作区必须明确文件归属，任何人不得 `git add .` 混入他人未验收工作。合并和推送由当前任务明确授权的负责人执行。

前端模拟数据只用于搭建和联调准备，不能证明模型、规则或云部署成功。测试验收 Agent 的完整角色提示词可留在专用聊天，不必重复存仓库；测试规范和真实报告应入库。
